# Draw.io Architecture Diagram Pattern

适用于系统架构、技术架构、部署架构、微服务关系、云架构和平台集成图。

## 布局

1. 优先使用分层布局，常见顺序为：用户/渠道层、接入层、应用服务层、领域服务层、数据层、外部系统层。
2. 层级之间保持主方向一致，通常从上到下或从左到右。
3. 同一层内节点保持对齐，大小尽量一致；同一层内不要做过多横向连接。
4. 横向连接超过 4 条时，增加事件总线、共享服务区、网关或拆分为局部视图。
5. 外部系统放在图的一侧或底部，不混入内部核心链路。

## Shape 语义

架构图必须使用稳定的 shape 语义，不同对象类型不要混用同一种形状。

1. 圆角矩形：应用、入口、页面、业务能力。
2. 矩形：服务、组件、模块、作业。
3. 圆柱：数据库、缓存、数据湖、文件存储。
4. 云形：互联网、云平台、外部网络边界。
5. 容器/泳道：VPC、租户、业务域、数据域、安全边界。
6. 细长矩形或胶囊：消息队列、事件总线、API 网关。

## 连接

1. 实线箭头表示同步调用或强依赖；虚线箭头表示异步事件、监控、弱依赖。
2. 跨系统关系必须标注协议、数据或动作，例如 `REST/HTTPS`、`MQ event`、`SQL query`。
3. 避免线条穿越多个层级；跨层连接应走外侧通道。
4. 不使用无标注的“uses”或“调用”泛化标签。

## 抽象层级

1. 遵循 C4 思路，不把系统上下文、容器、组件和代码级细节混在同一张图。
2. 当前图如果是系统上下文图，只展示系统和外部角色/系统。
3. 当前图如果是容器图，只展示应用、数据存储、队列等容器级元素。
4. 当前图如果是组件图，只展示某个容器内部的主要组件。

## 质量门槛

1. 节点超过 20 个时，必须分层、分区或拆图。
2. 交叉线超过 3 处时，必须调整布局。
3. 每个层级、容器或边界必须有标题。
4. 默认使用克制商务风格：浅色填充、深灰文字、细边框、低饱和强调色。
