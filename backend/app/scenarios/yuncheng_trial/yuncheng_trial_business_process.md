# 运城市驻场试用场景小时数据盯守、告警后溯源上下文抓取与溯源分析业务流程说明

## 1. 文档目的

本文档完整描述运城市驻场试用场景从小时数据抓取、告警规则判定、证据留存、告警后溯源上下文抓取、事件任务触发、专家分析、业务报告生成到微信投递的端到端业务流程。

本文档以结构化文字描述流程节点、参与角色、输入输出、判断条件、状态变化和异常分支，供业务人员、产品经理、研发人员和流程图设计人员据此绘制业务流程图、泳道图或数据流图。

本文档描述的是当前代码中的现行流程。场景早期文档中“社交模式每小时扫描最新证据目录”的定时检查方式属于旧口径；当前正式链路以 `yuncheng.alert.created` 事件直接触发溯源分析任务为主。

## 2. 场景目标

本场景服务于运城市第三方驻场团队的空气质量小时盯守，目标包括：

1. 每小时获取运城市城市级空气质量监测数据。
2. 依据可配置规则自动识别污染物快速上升、AQI 进入污染水平或污染物持续高值等情况。
3. 无论是否告警，均保存当次判断结果，形成可回溯的证据目录。
4. 发生告警时，自动补充目标城市、周边城市、气象、轨迹、火点和预报等溯源上下文。
5. 上下文准备完成后，通过可信事件触发溯源分析任务。
6. 由气象分析专家和常规监测分析专家分别形成专业草稿。
7. 由助手模式主 Agent 审核整合，生成面向驻场团队的业务报告、Word 附件和微信摘要。
8. 由事件任务服务统一向配置的微信用户发送摘要和 Word 报告，并保存用户对话上下文。

## 3. 业务范围与结论边界

### 3.1 当前纳入的数据

- 运城市城市小时空气质量数据。
- 临汾市、渭南市、三门峡市、洛阳市、晋城市等周边城市小时空气质量数据。
- 运城市告警前后气象历史数据。
- 本地生成的后向轨迹分析结果和轨迹图。
- 区域风场、能见度、降水、雷达、水汽、温度和预报类图片。
- 周边卫星火点明细、摘要和分布图。
- 未来气象预报。
- 未来 24 小时空气质量预报。

### 3.2 当前未纳入的数据

- 运城市站点小时监测数据。
- 本地污染源清单。
- 企业生产工况和企业门禁数据。
- 道路卡口和移动源轨迹。
- 走航监测数据。
- 执法巡查记录。
- 足以确认具体企业或具体污染源贡献的本地证据。

### 3.3 结论约束

- 报告只能形成提示性来源研判，不能确认具体污染源或责任主体。
- 不得写出“某企业导致污染”等确定性归因。
- 第一版未接入站点小时数据，不得形成站点异常或站点质控结论。
- 后向轨迹、风场、周边城市同步变化和卫星火点只能作为输送、区域过程或燃烧活动线索。
- 告警是否成立完全以小时盯守脚本生成的告警 JSON 为准，溯源分析 Skill 不重新计算或推翻告警。
- 报告必须区分监测事实、气象提示、溯源推断和需要本地数据核实的事项。

## 4. 参与系统与角色职责

### 4.1 Fetcher 调度器

- 注册 `yuncheng_trial_fetcher`。
- 按 `0 * * * *` 在每个小时整点调度执行。
- 负责启动一轮小时数据盯守流程。

### 4.2 YunchengTrialFetcher

- 确定本轮整点结束时间和查询窗口。
- 获取运城市城市小时监测数据。
- 调用规则引擎判定是否告警。
- 保存告警或静默状态证据。
- 有告警时调用上下文采集器。
- 上下文 manifest 成功落盘后发布告警事件。

### 4.3 告警规则引擎

- 计算污染物最新值与三条记录前数值的差值。
- 判断 AQI 小时值是否进入污染盯守范围。
- 判断最近三条记录是否持续达到关注水平。
- 区分主告警规则和辅助研判规则。
- 生成统一结构的 `AlertState`。

### 4.4 溯源上下文采集器

- 根据告警时间和回看窗口创建上下文采集清单。
- 调用数据查询、气象、轨迹、图片、火点和预报工具。
- 保存成功获取的 JSON 和图片资产。
- 记录缺失资产、抓取错误和建议补证事项。
- 生成 `tracing_context_manifest.json`。

### 4.5 定时任务事件服务

- 接收 `yuncheng.alert.created` 事件。
- 匹配已启用、事件类型和过滤条件均符合的事件任务。
- 按“任务 ID + 事件 ID”建立幂等声明，防止同一任务重复处理同一事件。
- 执行助手模式事件任务。
- 解析任务最终返回的广播 JSON。
- 统一负责微信接收人解析、正文和附件投递、对话上下文持久化。

### 4.6 助手模式主 Agent

- 读取可信事件上下文和正式溯源分析 Skill。
- 校验告警、manifest 和证据目录的一致性。
- 同步调用两个 expert 模式子 Agent。
- 审核两个专家草稿。
- 生成最终业务报告、Word 文档和微信摘要。
- 只返回事件任务服务规定的 JSON，不直接调用微信或广播工具。

### 4.7 气象分析专家 Agent

- 分析气象实况、扩散条件、后向轨迹、区域风场、降水、雷达、水汽和未来气象条件。
- 判断证据是否提示本地累积、区域输送、湿清除或光化学生成条件。
- 给出适合挂接到污染过程时间线的图片和业务化图注建议。
- 生成 `weather_analysis_draft.md`。

### 4.8 常规监测分析专家 Agent

- 分析目标城市小时变化、AQI 口径、首要污染物、周边城市同步性、火点线索和未来空气质量风险。
- 按目标城市小时数据建立污染过程主时间轴。
- 提出驻场盯守、核查和升级建议。
- 生成 `routine_analysis_draft.md`。

### 4.9 报告包服务

- 保存标准报告包。
- 将 `report.qmd` 渲染为 `report.docx`。
- 校验报告包和 Word 文件是否满足交付要求。

### 4.10 微信广播服务

- 仅选择已激活且已绑定微信的目标用户。
- 发送 500 字以内摘要和 Word 附件。
- 保存事件任务、执行记录和事件标识等上下文元数据。

## 5. 端到端主流程

### 阶段 A：整点调度和小时数据抓取

1. Fetcher 调度器在每小时整点触发 `yuncheng_trial_fetcher`。
2. Fetcher 将当前本地时间向下取整到整点，作为本轮 `end_time`。
3. 默认回看时长为 12 小时，查询起点为 `end_time - 11 小时`，查询区间包含起止时刻。
4. Fetcher 从 `CityAQIPublishHistory` 查询运城市数据，并按 `TimePoint` 升序返回。
5. 查询结果被标准化为统一字段，包括时间、城市、PM2.5、PM10、O3、NO2、SO2、CO、AQI、首要污染物和空气质量等级。

### 阶段 B：告警规则判定

1. 规则引擎接收按时间升序排列的城市小时记录。
2. 如果记录数少于 4 条，直接生成静默状态，摘要为“数据不足，未触发告警”。
3. 如果记录数不少于 4 条，计算 O3、PM2.5、PM10、CO 和 NO2 的最新值与三条记录前数值之差。
4. 依次检查快速上升规则、AQI 规则、辅助研判规则和连续高值规则。
5. 如果没有任何主告警规则命中，生成 `has_alert=false`、`status=silent` 的静默状态。
6. 如果至少一个主告警规则命中，生成 `has_alert=true`、`status=pending_trace` 的告警状态。
7. 多条主规则同时命中时，全部写入 `rule_hits`，但目标污染物取第一条命中规则对应的污染物。

### 阶段 C：证据落盘

1. 系统以实际检查时间 `checked_at` 创建独立证据目录。
2. 目录格式为 `backend/backend_data_registry/scenarios/yuncheng_trial/{YYYYMM}/{YYYYMMDD_HHMMSS}/`。
3. 系统将本轮状态写入 `{YYYYMMDD_HHMMSS}_alert.json`。
4. 无告警和有告警都会生成独立证据目录，不覆盖以前的结果。
5. 此时进入判断节点：本轮是否满足 `has_alert=true` 且 `status=pending_trace`。

### 阶段 D1：无告警分支

1. 如果判断结果为否，不采集溯源上下文。
2. 不生成 `tracing_context_manifest.json`。
3. 不发布 `yuncheng.alert.created` 事件。
4. 记录 Fetcher 完成日志并返回静默结果。
5. 本轮流程结束，等待下一小时调度。

### 阶段 D2：有告警分支

1. 如果判断结果为是，调用溯源上下文采集器。
2. 根据告警时间、目标污染物和 12 小时分析窗口创建 manifest 初始结构。
3. 按资产清单逐项调用数据或图片工具。
4. 单项资产失败时记录缺失和错误，但继续采集其他资产。
5. 生成依赖其他资产的派生图件，例如城市污染物空间分布图、火点摘要和火点分布图。
6. 将所有成功、缺失和失败信息写入 `tracing_context_manifest.json`。
7. 此时进入判断节点：manifest 路径是否返回且文件真实存在。
8. 如果 manifest 不存在，不发布告警事件；本次 Fetcher 返回告警状态和空 manifest 路径，由运行日志暴露异常。
9. 如果 manifest 存在，构建并发布 `yuncheng.alert.created` 事件。

### 阶段 E：事件匹配与幂等处理

1. 事件服务接收告警事件。
2. 事件服务筛选满足以下全部条件的任务：任务已启用、触发类型为事件、事件类型一致、事件属性满足过滤条件。
3. 当前正式任务按 `city=运城市` 过滤。
4. 对每个匹配任务，查询是否已存在相同“任务 ID + 事件 ID”的事件声明。
5. 如果声明已存在，默认判定为重复事件，本次不再执行该任务。
6. 如果声明不存在，创建持久化声明并接受执行。
7. 如果没有匹配任务，事件发布完成，但不会执行溯源分析或微信推送。

### 阶段 F：接收人预检与助手任务执行

1. 如果事件任务开启广播，先解析目标用户。
2. 只有状态为 active、已绑定社交账号且渠道为微信的用户才能成为接收人。
3. 如果没有有效接收人，事件执行直接失败，声明状态更新为 failed。
4. 如果存在有效接收人，事件任务执行器将任务提示词与完整可信事件 JSON 合并，启动助手模式。
5. 助手模式从事件 payload 获取告警 JSON、manifest 和证据目录路径。
6. 助手模式按正式 `yuncheng_alert_tracing_skill.md` 执行后续流程。

### 阶段 G：溯源分析和专家协作

1. 助手模式校验输入路径和告警状态。
2. 助手模式读取所有可用上下文资产及缺失资产记录。
3. 助手模式同步调用气象分析专家，等待其写出气象草稿。
4. 助手模式同步调用常规监测分析专家，等待其写出常规分析草稿。
5. 两个专家都只输出各自领域草稿，不直接生成最终结论或推送消息。
6. 助手模式读取两个草稿，检查证据边界、时间口径、AQI 口径、结论冲突和建议可执行性。
7. 助手模式以目标城市小时数据为主时间轴，整合监测、周边、气象、轨迹、火点和预报证据。
8. 助手模式生成 `report.qmd`。
9. 报告包服务渲染并校验 `report.docx`。
10. 助手模式生成 500 字以内微信摘要。
11. Word 文件不存在或验收失败时，只返回失败 JSON。
12. 全部成功时，只返回包含微信正文和 Word 绝对路径的广播 JSON。

### 阶段 H：微信投递和状态收口

1. 事件任务服务解析助手模式最终输出。
2. 输出不是合法 JSON、`success=false`、报告附件无效或任务执行失败时，执行记录和事件声明更新为 failed。
3. 输出合法且执行成功时，广播服务向所有有效微信接收人发送摘要和 Word 附件。
4. 广播服务将发送结果和事件上下文写入用户社交主会话。
5. 投递服务返回至少一条接收人结果后，当前事件服务继续按成功路径收口；如果所有接收人均发送失败，只会在执行记录中写入错误信息，当前实现仍会继续标记事件声明为 succeeded。
6. 事件声明更新为 succeeded，保存执行 ID 和最终状态。只有投递服务没有返回任何接收人结果或直接抛出异常时，才进入 failed 分支。
7. 端到端流程结束。

## 6. 告警判定规则明细

### 6.1 数据不足规则

- 判断条件：输入记录少于 4 条。
- 输出：`has_alert=false`、`status=silent`。
- 业务含义：当前数据不足以计算最新值相对三条记录前的变化。
- 后续动作：只保存告警状态 JSON，不采集上下文，不发布事件。

### 6.2 主告警规则

以下任一规则命中即可产生告警：

| 规则 ID | 业务名称 | 判定条件 | 告警等级 |
| --- | --- | --- | --- |
| `o3_3h_rising` | O3 快速上升 | 最新 O3 减三条记录前 O3 大于等于 40 μg/m³ | medium |
| `pm25_3h_rising` | PM2.5 快速上升 | 最新 PM2.5 减三条记录前 PM2.5 大于等于 25 μg/m³ | medium |
| `pm10_3h_rising` | PM10 快速上升 | 最新 PM10 减三条记录前 PM10 大于等于 40 μg/m³ | medium |
| `aqi_hourly_over_100` | AQI 进入污染盯守 | 最新 AQI 严格大于 100 | medium |
| `o3_3h_sustained_high` | O3 连续高值 | 最近三条 O3 均大于等于 160 μg/m³ | medium |
| `pm25_3h_sustained_high` | PM2.5 连续高值 | 最近三条 PM2.5 均大于等于 75 μg/m³ | medium |
| `pm10_3h_sustained_high` | PM10 连续高值 | 最近三条 PM10 均大于等于 150 μg/m³ | medium |
| `no2_3h_sustained_high` | NO2 连续高值 | 最近三条 NO2 均大于等于 100 μg/m³ | medium |
| `co_3h_sustained_high` | CO 连续高值 | 最近三条 CO 均大于等于 2.0 mg/m³ | medium |

### 6.3 辅助研判规则

辅助规则只形成分析线索，不能单独触发告警：

| 规则 ID | 判定条件 | 业务提示 |
| --- | --- | --- |
| `pm25_pm10_co_rising` | PM2.5 上升大于等于 15 μg/m³，且 PM10 上升大于等于 40 μg/m³ | 颗粒物同步上升线索 |
| `pm25_co_combustion_clue` | PM2.5 上升大于等于 15 μg/m³，且 CO 上升大于等于 0.2 mg/m³ | 不完全燃烧等影响线索 |
| `no2_rise_o3_drop_titration_clue` | NO2 上升大于等于 20 μg/m³，且 O3 下降 | 局地 NOx 滴定影响线索 |
| `no2_o3_both_rising_photochemical_precursor_clue` | NO2 上升大于等于 20 μg/m³，且 O3 上升 | 前体物累积叠加光化学生成风险线索 |

### 6.4 多规则命中时的目标污染物选择顺序

主规则按以下顺序检查：O3 快速上升、PM2.5 快速上升、PM10 快速上升、AQI 超过 100、O3 持续高值、PM2.5 持续高值、PM10 持续高值、NO2 持续高值、CO 持续高值。

`target_pollutant` 取第一条命中规则对应的污染物。因此，多条规则同时命中时，所有命中规则都会保留，但事件 ID、报告目标污染物和告警摘要以第一条规则为主。

### 6.5 告警标识

告警 ID 格式为：

`yuncheng-{目标数据日期}-{目标数据小时}00-{目标污染物}`

例如：`yuncheng-20260713-1700-o3`。

该 ID 同时作为事件 ID，是后续事件任务幂等处理的关键字段。

## 7. 告警状态与状态变化

### 7.1 告警 JSON 状态

| 状态 | 条件 | 含义 | 后续动作 |
| --- | --- | --- | --- |
| `silent` | 数据不足或无主规则命中 | 本轮不需要业务推送 | 保存证据后结束 |
| `pending_trace` | 至少一条主规则命中 | 等待上下文采集和后续溯源分析 | 采集上下文并尝试发布事件 |

当前 Fetcher 不会在报告完成后回写告警 JSON，因此告警文件中的 `pending_trace` 不会自动变成 `traced` 或 `completed`。后续是否成功由事件声明和事件执行记录表达。

### 7.2 事件声明状态

| 状态 | 含义 |
| --- | --- |
| `claimed` | 事件已被任务声明，尚未正式执行 |
| `running` | 事件任务正在执行 |
| `succeeded` | 分析和报告成功，且投递服务至少返回一条接收人结果；当前实现中不保证至少一人实际发送成功 |
| `failed` | 接收人、任务输出、报告、投递或其他环节失败 |

### 7.3 幂等和重复告警

- 幂等键是“任务 ID + 事件 ID”。
- 相同目标小时、相同首要命中污染物形成相同事件 ID，重复发布时不会重复执行同一任务。
- 下一目标小时即使污染过程仍在持续，也会形成新的事件 ID，因此可能再次触发报告和推送。
- 当前没有跨小时污染过程合并、告警冷却期或恢复通知机制。
- 失败事件默认不会在普通重复发布时自动重试；只有显式强制重试流程才能重新处理 failed 声明。

## 8. 证据目录与数据产物

### 8.1 目录规则

每轮抓取创建独立目录：

`backend/backend_data_registry/scenarios/yuncheng_trial/{YYYYMM}/{YYYYMMDD_HHMMSS}/`

其中时间戳来自本轮规则检查时间，而不是目标数据小时。

### 8.2 无告警目录

无告警目录至少包含：

- `{YYYYMMDD_HHMMSS}_alert.json`

该文件包含 `has_alert=false`、`status=silent`、检查时间、摘要和可能存在的辅助研判线索。

### 8.3 有告警目录

有告警目录可能包含：

- `{YYYYMMDD_HHMMSS}_alert.json`
- `tracing_context_manifest.json`
- 目标城市和周边城市监测 JSON
- 气象、轨迹、火点和预报 JSON
- 各类业务分析图片
- `weather_analysis_draft.md`
- `routine_analysis_draft.md`
- `report.qmd`
- `report.docx`

所有上下文、草稿和正式报告均写回同一证据目录，确保告警、证据、分析和交付产物能够按一次运行完整回溯。

## 9. 溯源上下文采集流程

### 9.1 Manifest 初始化

上下文采集器从告警 JSON 读取：

- 告警 ID。
- 目标城市。
- 目标污染物。
- 告警目标时间。
- 回看时长。
- 主规则和辅助规则。

系统以告警目标时间为分析结束时间，默认向前回看 12 小时，并预置资产清单、资产请求参数、缺失资产列表、抓取错误列表、补证建议和业务限制。

### 9.2 目标城市与周边城市监测资产

- `target_city_pollutants.json`：运城市分析窗口内小时污染物数据。
- `nearby_city_pollutants.json`：临汾、渭南、三门峡、洛阳、晋城等周边城市小时数据。
- `city_pollutant_choropleth.png`：基于目标城市和周边城市数据生成的目标污染物空间分布图。

该组资产用于确定目标城市污染变化主时间轴、判断周边城市同步性以及展示区域空间差异。

### 9.3 气象历史与后向轨迹资产

- `meteorology_history.json`：告警前后温度、湿度、风、降水等气象数据。
- `trajectory_analysis.json`：以运城市为受体点的 72 小时后向轨迹分析结果。
- `trajectory.png`：后向轨迹图。
- 后向轨迹默认高度包括 10 米、500 米和 1000 米。

该组资产用于提示扩散条件、本地累积可能性和潜在输送方向，不能用于确认具体污染源。

### 9.4 实况和预报图片资产

- `wind_field.png`：逐小时区域风场。
- `visibility.png`：能见度实况。
- `rainfall_24h.png`：过去 24 小时降水。
- `radar_mosaic.png`：雷达拼图。
- `radar_composite_reflectivity_003.png`：雷达组合反射率预报或产品图。
- `precipitable_water_000.png`：可降水量背景。
- `precipitation_forecast.png`：告警附近时段降水预报。
- `hourly_precipitation_forecast.png`：逐小时降水预报。
- `wind_forecast_024.png`、`wind_forecast_048.png`、`wind_forecast_072.png`：未来 24、48、72 小时风场预报。
- `precipitation_forecast_024.png`、`precipitation_forecast_048.png`、`precipitation_forecast_072.png`：未来 24、48、72 小时降水预报。
- `national_tmax_forecast.png`、`national_tmin_forecast.png`：全国最高和最低温度预报。

图片产品的业务有效时次可能与告警时间不同。后续报告必须使用图中或元数据中的实际有效时次，不得把文件抓取时间当作业务时次。

### 9.5 火点资产

- `fire_hotspots.json`：告警前 6 小时、指定区域范围内、置信度不低于 50 的卫星火点明细。
- `fire_hotspots_summary.json`：火点数量、方向、距离、时次和强度摘要。
- `fire_hotspots_map.png`：火点相对运城市的空间分布图。

火点只能作为生物质燃烧、露天焚烧或热异常活动线索。是否影响运城市必须结合实际观测时间、风场和后向轨迹综合判断。

### 9.6 未来预报资产

- `forecast_meteorology.json`：未来气象预报。
- `air_quality_24h_forecast.json`：告警后未来 24 小时空气质量预报。

空气质量预报保留 AQI、首要污染物、触发污染物以及未来可能达到关注阈值的污染物字段，用于判断风险是否延续和是否需要加密盯守。

### 9.7 单项失败处理

1. 工具调用失败或没有返回有效文件时，不中断整个上下文采集流程。
2. 将资产名加入 `missing_assets`。
3. 将错误来源、严重性和错误原因加入 `fetch_errors`。
4. 将资产缺失造成的判断影响加入 `suggested_evidence_gaps`。
5. 继续处理下一项资产。
6. 最终仍然生成 manifest，供后续 Agent 明确降低相关结论置信度。

## 10. 告警事件内容

### 10.1 事件基本字段

- `event_id`：使用告警 ID。
- `event_type`：固定为 `yuncheng.alert.created`。
- `occurred_at`：使用告警检查时间 `checked_at`。

### 10.2 事件属性

- `city`：运城市。
- `alert_level`：当前为 medium。
- `target_pollutant`：第一条命中主规则对应的目标污染物。

事件属性用于匹配事件任务过滤条件。

### 10.3 事件 Payload

- `alert_json_path`：本轮告警 JSON 路径。
- `tracing_context_manifest_path`：本轮 manifest 路径。
- `evidence_dir`：本轮证据目录。

这些路径属于可信事件上下文，是助手模式执行溯源分析时的正式输入。报告目录必须与证据目录完全相同。

## 11. 溯源分析 Skill 执行流程

### 11.1 输入校验

助手模式必须依次校验：

1. `evidence_dir` 存在。
2. `alert_json_path` 存在且文件名符合 `*_alert.json`。
3. `tracing_context_manifest_path` 存在。
4. `report_dir` 与 `evidence_dir` 相同。
5. 告警 JSON 同时满足 `has_alert=true` 和 `status=pending_trace`。

任何条件不满足都返回失败 JSON，不生成正式报告。

### 11.2 固定输出路径

- `{evidence_dir}/weather_analysis_draft.md`
- `{evidence_dir}/routine_analysis_draft.md`
- `{evidence_dir}/report.qmd`
- `{evidence_dir}/report.docx`

### 11.3 读取证据

1. 读取正式运城告警溯源 Skill。
2. 读取告警 JSON。
3. 读取 manifest。
4. 读取 manifest 中所有真实存在的 JSON 和图片资产。
5. 读取 `missing_assets`、`fetch_errors` 和 `suggested_evidence_gaps`。
6. 不重新判断脚本告警是否应当成立。

### 11.4 调用气象分析专家

1. 使用同步 `call_sub_agent`。
2. `target_mode` 必须为 `expert`。
3. Prompt 必须明确要求先读取 `weather_analysis_expert.md`。
4. Prompt 必须列出气象专家负责的实际资产路径，不能只要求“读取 manifest”。
5. 专家按实际时间顺序分析气象实况、轨迹和预报。
6. 轨迹必须写明受体时刻；预报必须写明起报时间和预报时效；图片必须写明实际有效时次。
7. 核心问题包括静稳或弱风、湿清除、高温强辐射、潜在输送方向和未来扩散条件。
8. 专家生成 `weather_analysis_draft.md`。
9. 专家只返回包含 `expert_type=weather` 和草稿路径的最小 JSON。

### 11.5 调用常规监测分析专家

1. 使用同步 `call_sub_agent`。
2. `target_mode` 必须为 `expert`。
3. Prompt 必须明确要求先读取 `routine_monitoring_analysis_expert.md`。
4. Prompt 必须列出常规专家负责的实际资产路径。
5. 以目标城市小时数据作为主时间轴，分析 AQI、分项污染物、首要污染物和变化阶段。
6. 对比周边城市同一时段数据，判断区域同步性。
7. 分析火点时只能形成燃烧活动线索。
8. 分析未来 24 小时空气质量风险和加密盯守需求。
9. 专家生成 `routine_analysis_draft.md`。
10. 专家只返回包含 `expert_type=routine` 和草稿路径的最小 JSON。

### 11.6 专家调度约束

- 禁止使用后台 `spawn`、`wait_task` 或异步等待方式替代同步专家调用。
- 助手模式必须等待两个专家调用全部完成。
- 两个草稿文件必须真实存在并经过读取校验。
- 在草稿、正式报告和 Word 全部完成前，不得向事件任务服务返回“正在处理”或“是否继续”等中间状态。

## 12. 专家分工与证据使用

### 12.1 气象分析专家主责资产

- `meteorology_history.json`
- `trajectory_analysis.json`
- `trajectory.png`
- `wind_field.png`
- `visibility.png`
- `rainfall_24h.png`
- `radar_mosaic.png`
- `radar_composite_reflectivity_003.png`
- `precipitable_water_000.png`
- 各类降水预报图片
- 各类风场预报图片
- 最高和最低温度预报图片
- `forecast_meteorology.json`

气象草稿必须包含监测事实引用、气象提示、传输推断、图片图注建议和需本地数据核实等内容。

### 12.2 常规监测分析专家主责资产

- 告警 JSON。
- `target_city_pollutants.json`。
- `nearby_city_pollutants.json`。
- `city_pollutant_choropleth.png`。
- `fire_hotspots_summary.json`。
- `fire_hotspots.json`。
- `fire_hotspots_map.png`。
- `air_quality_24h_forecast.json`。

常规草稿必须包含告警事实、污染变化、周边联动、火点线索、未来风险、现场建议和证据边界等内容。

### 12.3 共同约束

- 两个专家都要读取告警状态和目标时间。
- 所有证据必须按实际有效时次挂接。
- 不得使用文件创建时间替代业务有效时间。
- 不得强行把不同时次的数据描述成同一时刻。
- 资产缺失时必须说明对业务判断的影响。
- 专家不生成最终结论，最终结论由助手模式审核整合。

## 13. 主 Agent 审核与报告整合

### 13.1 草稿审核

主 Agent 读取两个专家草稿后检查：

- 是否存在确认具体污染源的越界结论。
- 是否把 AQI 当作单项污染物浓度。
- 是否遗漏首要污染物或主要贡献污染物说明。
- 是否把轨迹、火点或风场当成确定性来源证据。
- 是否遗漏关键资产或没有说明资产缺失。
- 是否错误对齐不同有效时次的数据。
- 驻场建议是否包含明确时间窗、核查范围和现场动作。
- 两个专家结论是否冲突。

如果专家结论冲突，应在报告中写明证据不一致或不足，不得强行形成确定结论。

### 13.2 污染过程主时间轴

最终报告以 `target_city_pollutants.json` 为主时间轴，动态识别以下候选阶段：

- 告警前背景。
- 污染开始变化。
- 污染加速或持续。
- 告警触发时刻。
- 告警后最新变化。
- 未来数小时趋势。

没有数据支撑的阶段不生成，相邻阶段无法区分时合并处理。每个阶段按“变化—同期情况—业务意义”组织：先说明污染变化，再说明同时段气象、周边、轨迹或火点情况，最后说明下一时段应关注或采取的行动。

### 13.3 不同资产的时间挂接规则

- 目标城市小时数据：作为主时间轴。
- 周边城市小时数据：优先挂接同一小时，没有同一小时则说明时间差。
- 气象小时数据：优先挂接同一小时，没有同一小时则说明时间差。
- 后向轨迹：按轨迹受体时刻挂接。
- 火点：按卫星观测时刻挂接。
- 实况图片：按图片或元数据中的有效时次挂接。
- 预报：统一放在未来阶段，写明起报时间、预报时效和对应未来时间窗。
- 无法确认有效时次的资产：不得推动正文结论，只能列入附件或需要补充确认的信息。

## 14. 最终业务报告结构

### 14.1 本次告警概览

用 3 至 5 句话说明告警时间、目标污染物、告警等级、当前关注点和是否建议现场加密盯守，并给出不越界的业务判断。

### 14.2 污染过程时间线

这是报告主体。按实际时间点或时间范围串联目标城市监测、同期气象、周边城市、轨迹、火点和关键图片。每个节点回答：发生了什么、同期情况如何、下一时段意味着什么。

### 14.3 当前情况与未来趋势

说明最新监测数据更新到何时，当前过程处于持续、转折还是缓解状态；结合明确起报时间和时效的预报说明未来风险。

### 14.4 可能影响因素

可讨论本地累积、区域传输、光化学生成、颗粒物二次转化和燃烧活动线索。每项因素必须同时说明支持依据和仍需补充的本地信息。

### 14.5 现场行动安排

每条建议至少包含：

- 执行时间窗，例如立即、未来 1 至 2 小时或当天夜间。
- 核查范围，例如上风向、周边联动方向、重点道路、工业片区或施工区域。
- 现场动作，例如巡查、走航、企业工况核实、扬尘排查、移动源管控或加密会商。
- 需要补充的数据。
- 触发升级会商或现场核查的条件。

### 14.6 需要补充确认的信息

用业务语言说明当前缺少哪些数据、哪些结论还不能确认，以及补齐相应数据后可以解决什么问题。业务报告不使用“数据缺口与不确定性”作为章节标题。

### 14.7 附件与数据来源

列出本次使用的告警、manifest、监测、气象、轨迹、火点、预报和图片资产，并注明实际有效时次或时间范围。

## 15. 报告生成与验收流程

1. 主 Agent 在证据目录生成带有效 YAML header 的 `report.qmd`。
2. 图片使用相对路径，并紧跟对应的污染过程时间节点。
3. 图片必须有业务化图注，包括实际有效时次、图上主要情况和现场意义。
4. 读取标准报告包使用说明。
5. 调用 `create_report_package` 保存报告包。
6. 调用 `render_report_package(format="docx")` 导出 Word。
7. 调用 `validate_report_package(require_docx=true)` 验收。
8. 检查 `{evidence_dir}/report.docx` 是否真实存在。
9. Word 不存在或验收失败时返回失败，不允许返回成功状态。

## 16. 微信摘要与投递流程

### 16.1 助手模式输出

成功时，助手模式只返回结构化 JSON，包含：

- `success=true`。
- `broadcast.message`：500 字以内微信摘要。
- `broadcast.media`：只包含 `report.docx` 的绝对路径。

助手模式不直接调用微信、广播或通知工具。

### 16.2 微信摘要内容

摘要应包括：

- 运城市空气质量告警标题。
- 告警时间。
- 目标污染物。
- 告警等级。
- 简短研判结论。
- 驻场行动建议。
- Word 报告附件提示。

### 16.3 事件任务服务投递

1. 解析助手模式输出。
2. 校验输出为合法事件任务 JSON。
3. 调用微信广播服务发送正文和附件。
4. 对每个接收人记录是否发送成功、是否保存上下文和错误原因。
5. 将任务 ID、执行 ID、事件 ID 和事件类型作为上下文元数据保存。

## 17. 异常与降级分支

### 17.1 小时数据查询失败

- 当前 Fetcher 没有在自身逻辑中吞掉数据库异常。
- 异常向调度器传播，由调度层记录本轮执行失败。
- 本轮通常无法生成告警 JSON，也不会发布事件。

### 17.2 数据少于四条

- 输出静默状态。
- 保存“数据不足”证据。
- 不采集上下文，不触发报告。

### 17.3 单项上下文资产失败

- 不终止其他资产采集。
- 在 manifest 记录缺失、错误和补证建议。
- 后续报告可以继续生成，但必须降低相关机制判断置信度，并写入需要补充确认的信息。

### 17.4 Manifest 未落盘

- 不发布告警事件。
- 不执行溯源分析和微信推送。
- 告警 JSON 仍保持 `pending_trace`，需要通过 Fetcher 日志定位原因。

### 17.5 没有匹配的事件任务

- 告警事件已发布，但没有后续分析任务执行。
- 告警和上下文证据仍然保留。

### 17.6 没有有效微信接收人

- 在启动助手分析前失败。
- 事件声明更新为 failed。
- 不执行报告生成。

### 17.7 输入路径或告警状态不一致

- 助手模式返回失败 JSON。
- 不调用专家，不生成正式报告。

### 17.8 专家调用或草稿生成失败

- 缺少任一专家草稿即视为失败。
- 不得用单一专家草稿冒充完整流程。
- 不得提前返回处理中状态。

### 17.9 报告渲染或 Word 验收失败

- 返回失败 JSON。
- 不允许只生成 QMD 就宣告成功。
- 不允许向用户发送不存在的附件。

### 17.10 助手输出不是合法 JSON

- 事件任务服务无法解析广播产物。
- 执行记录标记失败。
- 事件声明标记 failed。

### 17.11 微信部分发送失败

- 为每个接收人分别记录发送状态。
- 投递服务没有返回任何接收人结果时，事件执行标记 failed。
- 投递服务返回结果但所有接收人均为 `sent=false` 时，当前实现会记录“所有接收人投递失败”的错误信息，但仍继续将事件声明标记为 succeeded。
- 因此，事件声明为 succeeded 不等同于至少一名微信用户实际收到消息；核查投递效果时还应检查每条 `delivery_results`。

## 20. 当前实现中需要在流程图旁注说明的事项

### 20.1 “三小时上升”是记录差值，不是逐小时单调上升

代码使用“最新记录值减三条记录前的值”计算变化，没有逐一检查中间两小时是否持续上升。流程图宜标注为“相对三条记录前上升达到阈值”，避免被理解为三个相邻小时均单调上升。

### 20.2 “连续三小时高值”没有验证时间连续性

代码检查最近三条记录是否均达到阈值，但没有额外验证三条记录的时间间隔都恰好为一小时。正常数据库数据按小时齐全时等价于连续三小时；存在缺测时不完全等价。

### 20.3 缺失污染物值按 0 参与规则计算

无法转换为数字的污染物值会被读取为 0。较早记录缺失可能放大上升差值，最新记录缺失则可能压低差值。流程图可将“数据质量检查”列为当前规则引擎前的潜在改进节点，但不能画成现行已实现步骤。

### 20.4 告警状态与任务状态是两套状态

告警 JSON 的 `pending_trace` 只表示需要溯源，并不代表报告任务仍在运行。报告是否成功应查看事件声明和执行记录。当前没有把任务结果回写告警 JSON 的闭环。

### 20.5 上下文采集允许部分成功

只要上下文采集器最终写出 manifest，即使其中存在缺失资产，也会发布告警事件。后续报告必须基于 manifest 中的缺失记录主动降低结论置信度。

### 20.6 事件级去重不等于污染过程级去重

同一事件 ID 对同一任务只处理一次，但持续污染在下一小时会产生新的事件 ID，可能再次生成报告并推送。目前没有告警合并、冷却期和解除告警流程。

### 20.7 旧式定时扫描与现行事件触发的区别

早期说明曾建议社交模式每小时扫描最新证据目录。当前实际启用任务使用 `trigger_type=event`，由 Fetcher 在上下文准备完成后直接发布事件。绘制现行流程图时不应再增加“每小时第 10 分钟扫描 latest_alert.json”的节点。

### 20.8 succeeded 不保证微信实际发送成功

当前事件服务只要求投递服务返回非空结果列表。所有接收人的结果均为 `sent=false` 时，执行记录会保留错误信息，但事件声明仍被标记为 succeeded。流程图宜在投递节点旁标注“最终送达状态以 delivery_results 为准”，不要把 succeeded 直接解释为用户已收到消息。

## 22. 流程终点定义

本业务流程存在以下终点：

1. 静默结束：无告警，只保存告警状态证据。
2. 告警证据结束：有告警但 manifest 未生成，保留告警 JSON 并通过日志排查。
3. 上下文准备结束：manifest 已生成，但没有匹配的事件任务。
4. 重复事件结束：同一任务已处理过相同事件 ID，不重复分析和投递。
5. 分析失败结束：输入、专家草稿、报告渲染、Word 验收或输出格式失败。
6. 投递失败结束：没有有效接收人、投递服务没有返回结果或投递过程抛出异常。
7. 成功结束：告警证据、上下文、专家草稿、QMD、Word、微信摘要和投递结果全部形成，事件声明状态为 succeeded；是否实际送达还需读取 `delivery_results`。
