# Diagram Visual Checklist

调用 `create_diagram_artifact` 前后都要检查。违反 P0 项时，先重写结构，不要靠多加颜色或连线补救。

## P0 结构检查

- 已读取 `index.md`、对应类型模板和本 checklist。
- 已明确 `diagram_type`，没有把架构图、流程图、数据流图混成一张。
- 已写出主阅读方向：`TB` 或 `LR`。
- 架构图、分层系统图必须优先使用 `layers/groups/items`，不要只给普通节点加 `group`。
- 思维导图必须使用一个中心主题和 `parent_id`/`parent` 父子关系，不使用复杂交叉边。
- 甘特图必须给主要任务写 `start`/`end` 或 `duration`，不要用无时间范围的任务列表冒充排期。
- 每个 layer/group 有清晰名称，且模块数优先在 3-7 个。
- 单个 group 超过 7 个模块时，Agent 已按语义拆成二级分组或合并成更高层能力项；模板不会自动伪造业务分组。
- 单层明显比其他层更重时，已合并同类项或拆分 group；不能只靠高亮和颜色处理信息密度。
- 总节点数优先控制在 8-28 个；超过时合并同类模块。
- 主干关系控制在 3-10 条；复杂依赖拆成子图。
- 展示标签默认只使用中文；不要在 `label` 中加入英文括注、拼音解释或长说明。
- 已确认视觉强调来自显式语义字段，而不是 `label` 关键词：模块高亮用 `emphasis`，层变体用 `variant`，主干流向用 `flow_strength`。
- 单层 `emphasis="high"` 不超过 1-3 个；高亮过多时先重新判断核心模块。
- 已确认 `edges.from/to` 和真实流向或依赖方向一致；如果展示顺序与数据流方向相反，不为了箭头朝下而反写边。
- 分层架构图采用传统 draw.io 风格：白色画布、浅色层容器、白底模块、细边框。
- 数据库、存储、队列、文档、云服务等明确组件类型没有全部画成默认方框。
- 使用图例时已读取 `icon-catalog.md`，且只给底部固定类型层或关键模块选择语义匹配的通用 `icon`。
- 分层架构图上层业务/支撑层默认不展示图标；如确需展示，已显式设置 `icon_policy="show"` 并确认图标不会误导。
- 底部传输、数据存储、感知等固定类型层可保留图标；如果语义不确定，宁可省略 `icon`。

## 视觉层级检查

- 图标题、组名、节点、边标签形成 4 级层级，不要全部同等权重。
- 独立展示时标题足够明确，不使用“系统架构图”这种缺少对象的泛标题；应写清楚系统或产品名称。
- 节点标题不超过 12 个中文字符；最多两行。
- 分层图层高已明显压缩，节点文字足够大；不能出现大面积空白挤压文字识别。
- 分层架构图字体与 Python 报告图表保持一致，优先使用 `FZXiaoBiaoSong-B05S`。
- 边标签不超过 6 个中文字符，优先写动作或数据类型。
- 分层图的层名优先 2-6 个中文字符；组名和模块名优先 2-8 个中文字符。
- 使用不超过 3 个语义颜色：主干、支撑、外部/异常。
- 同一类型节点使用一致形状，不随意混用。
- 图例用于辅助识别，不替代文字；同一组内图例风格和密度保持一致。
- 图标选择语义优先，不要为了去重乱选图标；不能自然解释的图标应省略。
- 层/组之间的留白大于组内节点间距。
- 高密度层允许模板自动缩小图标、字号和间距作为视觉保护，但输出后仍应检查是否需要由 Agent 重新拆组或合并。

## 布局检查

- 分层图必须像横向 band，不是散点图。
- 分层图产物应包含稳定的层级容器，不依赖自动铺点。
- 架构图必须有区域边界，不是普通步骤链。
- 架构图模块应像 draw.io 节点，不要像网页 dashboard 卡片。
- 外部系统、人工服务、第三方依赖应放入独立边缘容器，不混入内部主干层。
- 流程图必须有起点和终点。
- 决策树的每条判断边都有条件标签。
- 数据流图的每条边都有数据或处理动作标签。
- 不依赖横向滚动才能读懂全图。

## 可读性检查

- 图表不依赖 notes 或底部说明解释设计逻辑；主图必须自解释。
- 普通节点不要使用长句。
- 不把中英文对照放进层名或模块名；如需英文术语，放入图外正文。
- 不使用低对比颜色承载关键信息。
- 不用图标替代文字；如果用云厂商图标，旁边必须写产品名。
- 外部系统和内部模块有明显边界。
- 核心模块如果需要优先吸引视线，已由 Agent 显式写入 `emphasis="high"`；模板不通过“核心、重点、监测、平台”等文字猜测。
- 分组、合并、图标选择、核心判断、箭头语义均由 Agent 按规范显式给出；模板只消费结构化字段并提供可读性兜底。

## 失败信号

- SVG 宽度远大于高度，且读者需要横向拖动。
- 一层里有 10 个以上并列模块。
- 单个 group 平铺超过 7 个模块，且没有拆成二级分组。
- 某一层面积或节点密度明显压过其他层，读者第一眼只能看到这一层。
- 层名出现括号英文，或模块名长到需要频繁换行。
- 所有节点都在同一行或同一列。
- 线条交叉比节点还抢眼。
- 看不出哪个是主路径、哪个是辅助关系。
- 一组模块全部使用同一个 `app`、`sensor` 或 `device` 图标，导致视觉上像重复图例。
- 上层业务/支撑层出现大量图标或空心圆点，导致读者优先看图标而不是文字。
- 层 band 高度远大于文字需要，放入方案/PPT 后文字偏小、空白偏多。
- 架构图出现厚阴影、渐变背景、胶囊编号、hover 样式。
- 样式选择依赖中文关键词或行业词，导致同一业务词在不同图中被固定高亮。
- 主图方向和底部说明、边标签或真实数据流互相矛盾。
