# Freeform Architecture Diagram Guide

使用 `diagram_mode="freeform"` 绘制架构、平台、分层系统、设备拓扑或数据链路图时，先读取 `freeform-index.md` 和 `freeform-primitives.md`，再读取本文件。输入必须使用 `canvas/shapes/connectors/groups`。

本文只定义架构图的设计判断、软约束和视觉理念；通用 `shape.type`、`connector.type`、布局原语、groups 和 style 字段以 `freeform-primitives.md` 为准。

## 架构表达目标

- 架构图首先表达“系统如何被组织”，其次才表达“节点如何互相调用”。
- 一张架构图只服务一个阅读任务：总体分层、业务域协作、数据链路、部署拓扑、设备接入不要混在同一张图里。
- 读者应能在 3 秒内识别主结构，在 10 秒内理解主要依赖，在 30 秒内找到关键实体。
- 自由画布不是关系网画布；它应呈现架构边界、层级秩序、输入输出和支撑能力。

## 架构软约束

- 优先画层、域、边界和主干通路；普通模块是这些结构里的内容，不是图的骨架。
- 分层架构图默认按自下而上绘制：底部是基础设施/数据/感知等基础层，中间是传输、治理、平台能力，上方是业务应用、决策和用户触达。
- 每层或每个域保留 3-8 个核心节点。超过 8 个先合并成能力簇、实体类别或子域。
- 设备、站点、传感器、第三方系统数量多时先抽象为类别或接入边界，不逐个展开。
- 左侧/上侧适合外部输入：用户、设备、第三方、数据源、入口网关。
- 右侧/下侧适合输出消费：驾驶舱、报告、告警、API、监管推送。
- 底部或侧边适合支撑能力：云资源、存储、消息总线、监控、安全、权限、运维。
- 数据库、队列、缓存、模型、规则、监控等实体需要可识别，但它们不应把主结构切碎。
- 同一层内部默认不连线；只有会改变读者理解的关键调用才保留。
- 架构图的连线默认连接层、域、系统边界或代表性容器；普通节点级连线应是少量例外。

## 架构取舍策略

- 当“完整性”和“清晰性”冲突时，优先清晰性。用聚合节点、注释或子图承载次要细节。
- 当“真实调用链”和“架构主干”冲突时，优先主干。详细调用链适合流程图或链路图。
- 当多个模块功能相近时，合并为能力簇；不要为了列全名词牺牲版面秩序。
- 当同一目标出现高扇入时，添加接入网关、数据总线、消息队列或汇聚服务作为中转。
- 当系统既有业务层又有数据层时，先确定数据流方向，再安排业务能力；不要让箭头反复上下穿越。
- 当外部系统很多时，使用侧栏或外部边界统一承载，不把外部实体散落在主系统内部。
- 当需要展示监控、安全、运维时，把它们作为横切支撑域或观察线，不让它们压过主业务流。

## 空间组织

- 先画大结构，再放节点：先确定层带、域区、外部侧栏、底部支撑带，再填充具体能力。
- 主阅读方向只能有一个：分层架构图默认自下而上表示数据/资源向应用汇聚；只有用户明确要求时才改为自上而下或左右流向。
- 层级标题和层级说明必须放在独立左侧栏/左侧小容器内，模块放在右侧内容区；不要把标题文字和模块节点放在同一个可重叠区域。
- 左侧层级说明栏应有固定宽度，右侧模块区从说明栏右侧开始排布并整体居中；模块不得遮挡层级名称、层级描述或说明文字。
- 容器之间留出明显空隙；容器内部节点对齐到稳定网格，避免“散点图”观感。
- 同一层节点高度、间距、文字长度尽量一致；少量宽节点用于承载网关、总线、平台等汇聚角色。
- 侧栏节点与主干节点要有视觉距离，避免读者误认为外部实体属于主系统内部。
- 重要路径应形成一条可追踪的主线；支撑关系和观察关系放在视觉次级通道。
- 大画布中不要把内容平均铺满，留白要服务分组、主次和阅读停顿。

## 视觉设计理念

- 架构图应“安静、有层次、可扫描”，避免像流程图一样满屏箭头，也避免像清单一样只有方块。
- 色彩用于区分层级和域，不用于装饰。不同层级必须有可辨识的色彩差异，优先使用偏深的层级标题栏/边框承载语义，模块区域用浅底保证可读。
- 不要所有层都使用同一种浅蓝/浅灰；至少通过左侧层级栏、边框或标题条体现不同层级的语义色。
- 主系统区域最稳定，外部系统次之，支撑域更弱；视觉权重应符合架构主次。
- 节点形态要帮助识别实体类别，但不要为了丰富而过度混用。重要类别可差异化，普通服务保持一致。
- 连线必须弱于节点和层级标题；主数据流可以清晰，辅助依赖必须退后。
- 同一语义的节点和连线保持一致，不要让颜色、线型、圆角同时变化造成噪声。
- 强调节点控制在 10%-20%；每个节点都强调等于没有强调。
- 标签优先使用短名词或短动宾结构；说明性文字放到 note/callout，不塞进节点标题。

## 架构连线理念（CRITICAL）

- **架构图只画层级之间的连线，不画层内模块之间的连线。** 连线只连接 group（层/域/边界容器），不连接 group 内部的 shape。连线数量应控制在 3-8 条。
- 连线的作用是解释层级/域/边界之间的依赖，不是证明每个元素有关联。
- 典型连线模式：感知层→传输层→平台层→应用层（每层之间一条粗箭头），支撑体系⇢各层（虚线横切）。
- 主数据流保留连续主线；同步调用、异步事件、批处理、监控告警用不同弱视觉通道表达。
- 多个普通节点到同一目标的关系应先聚合，再连接；避免扇形箭头遮蔽层级。
- 跨层连线优先连接代表节点、边界容器或汇聚节点；不要从多个源节点逐条穿过层带。
- 反馈闭环最多 1-2 条，并应放在图边缘或外侧通道，避免打断主阅读方向。
- 重复线标签删除；必要标签保持短文本，不压住节点、容器标题或层边界。

## 架构质量自检

- 是否一眼能看出主层级、主域或主系统边界？
- 是否存在大量普通节点之间的连线，让图退化成关系网？
- 是否有明确的输入侧、输出侧和支撑能力位置？
- 是否把数据库、队列、缓存、外部系统、监控等实体做了可识别区分？
- 是否存在同层长链、中心汇聚扇形、高密度交叉线或重复标签？
- 是否能删除 20% 的节点/连线而不影响主干理解？如果可以，先删或合并。
- `.drawio` 源文件是否保留可编辑结构，SVG/PNG 预览是否清晰可读？

## 后处理边界

- 后处理只负责网格对齐、画布边界扩展、默认样式补齐和质量告警。
- 后处理不负责重写架构语义，不会自动删除、合并或改向连线。
- 如果返回 `architecture_shape_level_connectors`、`high_fan_in`、`layer_internal_long_chain`、`overlap_detected` 或 `label_too_long`，Agent 必须通过 `diagram_patch` 重构节点、边界或连线。

## 常见失败模式

- 把架构图画成普通关系图：每个元素都有线，但没有层、域、边界和输入输出。
- 把架构图画成节点清单：节点排列整齐，但没有主干依赖和系统组织逻辑。
- 把设备、站点、传感器全部展开，导致主系统能力被噪声淹没。
- 把监控、安全、运维、告警画得和主业务流同权重，破坏阅读重点。
- 为追求“丰富”混用过多颜色、形态和线型，导致图面不专业。
- 依赖后处理救图，而不是在设计阶段完成抽象、布局和连线取舍。
