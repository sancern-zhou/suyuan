# 许昌业务场景层梳理

## 1. 文档定位

- 文档目的：按业务场景说明许昌项目的触发条件、数据输入、处理流程、工具、架构组件、输出和质量边界。
- 项目范围：`projects/xuchang/`、许昌专属 Fetcher、Scenario、API、工具及其调用的共享领域能力。
- 核心原则：业务规则、算法、阈值、质量门控和证据链采用确定性代码；Agent 负责自然语言入口、任务编排、补证、解释和交付。

## 2. 项目能力总览

许昌项目通过 `projects/xuchang/project.yaml` 启用：

- Agent 模式：`query`、`knowledge`、`expert`、`report`。
- 专属工具：GEMS 影像、Sentinel-5P 影像、许昌上风向排污许可企业筛查。
- 数据采集：实况气象、天气图、空气质量预报、日/年度达标预测、国控站小时数据、站点偏离告警、输送分析、GEMS 影像。
- 知识库集合：`xuchang`。
- 项目地域：许昌市，行政区代码 `411000`，时区 `Asia/Shanghai`。

```text
数据采集与存储
    |
    +-- 空气质量实况/预报 --------> 小时展示、日达标、年度达标
    +-- 站点小时浓度 ------------> 场景一站点偏离告警
    +-- 气象观测/预报 ------------> 上风向筛查、污染机制研判
    +-- 排污许可证企业 ----------> 本地候选源筛查
    +-- NOAA 后向轨迹 ------------> 场景二输送诊断、CWT
    +-- GEMS/Sentinel-5P ---------> 遥感空间线索
    +-- 项目知识文档 ------------> 知识问答、专家会商、报告
```

## 4. S0：问数生图

### 4.1 业务目标

让用户通过自然语言查询许昌空气质量、气象、预报、站点和统计数据，并生成可核验图表。

### 4.2 流程

```text
用户问题
  -> 识别城市、时间、指标、粒度和输出形式
  -> 选择业务查询工具
  -> 校验数据来源、字段、单位、时间范围和缺失值
  -> 必要时执行统计计算
  -> 用户要求制图时选择合适图表
  -> 注册数据文件/图表资源
  -> 返回核心结论和可追溯产物
```

### 4.3 涉及能力

- Query Agent 与许昌 query 提示词。
- 城市和站点空气质量查询工具。
- 气象、天气预报、空气质量预报工具。
- Python 统计分析、图表和地图工具。
- 前端右侧资源面板。

### 4.4 质量边界

- 所有具体数值必须来自工具结果、上传材料或已读取文件。
- 用户未指定地点时默认许昌市；明确指定其他地区时不得强制改为许昌。
- 图表必须保留口径、单位、时间范围和数据来源。
- 不允许把服务器本地路径作为用户下载地址。

## 5. S1：小时空气质量实况与预报

### 5.1 业务目标

在统一时间轴上展示许昌最近24小时空气质量实况和未来空气质量预报，为日内趋势判断和日达标预测提供基础。

### 5.2 数据输入

- `CityAQIPublishHistory`：许昌城市小时实况。
- `OpenMeteoAirQualityForecast72h`：许昌小时预报。
- 指标：AQI、PM2.5、PM10、O3、NO2、SO2、CO。

### 5.3 流程

```text
前端请求 /api/air-quality-forecast/xuchang-hourly
  -> 查询最近24小时城市实况
  -> 查询许昌预报时序
  -> 统一字段名和 ISO 时间
  -> 返回 reference_time、observations、forecasts
  -> 前端绘制实况/预报连续曲线
```

### 5.4 架构与工具

- FastAPI：`backend/app/api/xuchang_air_quality_routes.py`。
- SQL Server/pyodbc：实况和预报存储。
- OpenMeteo Fetcher：预报数据采集。
- Vue：`frontend/src/views/AirQualityForecastView.vue`。

### 5.5 当前边界

- 接口失败统一返回 503，但当前缺少数据新鲜度、预报批次和单指标缺测说明。
- 建议增加 `data_updated_at`、`forecast_run_time`、`completeness` 和来源字段。

## 6. S2：日达标预测

### 6.1 业务目标

滚动预测许昌当日 PM2.5 日均和 O3 最大8小时平均是否达标，并在首次预测超标或预测值明显改善时触发业务事件。

### 6.2 触发与标准

- 调度：每小时25分。
- PM2.5 日均限值：75 µg/m3。
- O3 最大8小时平均限值：160 µg/m3。
- “改善机会”阈值：相对于上次预测下降至少5 µg/m3。

### 6.3 流程

```text
读取当日已完成小时实况
  + 读取当日剩余小时预报
  -> 以实况覆盖相同小时的预报
  -> 构造完整24小时序列
  -> 计算 PM2.5 日均
  -> 计算 O3 连续8小时滑动平均最大值
  -> 判断缺失小时和达标状态
  -> 保存 SQL Server 和 JSON 快照
  -> 与通知状态比较
  -> 发布首次超标或改善机会事件
```

### 6.4 涉及组件

- `backend/app/fetchers/xuchang_daily_attainment_forecast.py`。
- 城市实况 SQL 客户端。
- OpenMeteo 72小时空气质量预报表。
- `XuchangDailyAttainmentPrediction` 结果表。
- Scheduled Task Event：`xuchang.daily_attainment.predicted_exceedance`。

### 6.5 质量边界与建议

- 当前 PM2.5 日均会使用所有非空小时计算，需要明确最少有效小时数和法规口径。
- O3 必须至少存在一个完整8小时窗口，否则不得给出确定达标结论。
- 需要区分“预测达标”“预测超标”“数据不足”，避免把缺测解释为达标。
- 建议将限值、有效性规则和改善阈值迁移到带版本的项目业务配置。

## 7. S3：年度达标预测

### 7.1 业务目标

结合本年度截至当前的实况和历史年份剩余季节，构造年度 PM2.5、O3和 AQI 达标天数预测区间。

### 7.2 触发与指标

- 调度：每月1日06:35。
- PM2.5 年均目标：30 µg/m3。
- O3 日最大8小时第90百分位目标：160 µg/m3。
- AQI 达标日：AQI <= 100。
- 历史候选：最近5年；至少3个有效历史情景。

### 7.3 流程

```text
读取本年1月1日至最近完整日的数据
  -> 确定当前截止日期
  -> 对过去5年读取“同月同日之后至年末”的数据
  -> 每个历史年份形成一个剩余季节情景
  -> 当前实况 + 历史剩余季节
  -> 计算 PM2.5 年均、O3 P90、AQI达标天数/比例
  -> 汇总多个情景的上下界
  -> 保存数据库和 JSON 快照
```

### 7.4 涉及组件

- `backend/app/fetchers/xuchang_annual_attainment_forecast.py`。
- `CityDayAQIPublishHistory` 日数据。
- 百分位计算服务。
- `XuchangAnnualAttainmentPrediction` 结果表。

### 7.5 质量边界与建议

- 该方法本质是历史情景法，不是数值预报模型；对外必须标注方法和不确定性。
- 历史年份可能存在政策、排放和气候结构变化，建议增加相似气象年筛选或权重。
- 应展示情景数量、历史年份、当前有效日数和缺失日数，而不仅是上下界。
- 标准版本必须带生效时间，避免政策更新后旧结果失去解释依据。

## 8. S4：场景一——局地站点异常与上风向候选源

### 8.1 业务目标

快速识别许昌单个站点相对全市其他站点显著偏高的污染事件，并结合风场和排污许可证企业形成局地候选源线索。

### 8.2 触发规则

- 调度：每小时15分，分析上一个完整小时。
- 污染物：PM2.5、O3、NOX；其中 NOX 使用 NO2 小时浓度作为筛查代理。
- 最少有效站点：3个。
- 最低数据完整率：80%。
- 基线：排除目标站点后的其他站点中位数。
- 相对偏差阈值：目标站点高于基线50%以上。
- 绝对差阈值：PM2.5 10、O3 30、NOX 15 µg/m3。
- 告警必须同时满足相对偏差和绝对差条件。

### 8.3 完整流程

```text
读取 dat_station_hour 上一个完整小时
  -> 计算预期站点数和数据完整率
  -> 对每个污染物执行留一法中位数比较
  -> 相对偏差 + 绝对差双阈值
  -> 生成 station_deviation 告警事件
  -> 按污染物确定时间窗口和候选半径
       PM2.5：回看1小时，10 km
       O3：回看2小时，20 km
       NOX：当前小时，5 km
  -> 获取代表气象站风向风速并用邻近站校验
  -> 查询半径内排污许可证企业
  -> 计算方向、距离、污染物关联和行业先验评分
  -> 输出候选企业，不输出贡献率
  -> 收集空气质量、实况气象和预报气象证据
  -> 保存事件、快速分析和证据包
  -> 将事件送入场景二连续性状态机
  -> 发布任务事件
```

### 8.4 涉及工具和服务

- 异常检测：`backend/app/scenarios/xuchang_station_deviation/service.py`。
- 证据收集：`backend/app/scenarios/xuchang_station_deviation/evidence.py`。
- Fetcher：`backend/app/fetchers/xuchang_station_deviation_alert.py`。
- 专属工具：`analyze_xuchang_upwind_permit_sources`。
- 排污许可仓储：`backend/app/tools/analysis/xuchang_upwind_permit_sources/repository.py`。
- 风场、稳定度和候选评分：`backend/app/tools/analysis/xuchang_upwind_permit_sources/engine.py`。
- 事件：`xuchang.station_deviation.alert_created`。

### 8.5 输出

- 原始告警 JSON。
- 场景一快速分析 JSON。
- 综合证据包 JSON。
- 候选企业列表、风场证据、分值及置信度。
- 场景二升级状态。

### 8.6 质量和结论边界

- 快速分析 SLA：5秒。
- 风速过低或缺少一致性验证站时，必须排除该小时或降低证据等级。
- 许可证只有污染物类别，没有可靠排放量时，置信度不得提升到高。
- `final_score` 是无量纲筛查分，不是排放贡献率。
- 单小时风向和空间相交只能产生候选线索，不能认定企业为污染来源。

## 9. S5：场景二——连续异常输送溯源

### 9.1 业务目标

当同一站点、同一污染物连续异常时，升级执行后向轨迹、输送通道、企业空间相交和 CWT 分析，区分本地积累、区域输送或混合影响。

### 9.2 升级条件

- 同站点、同污染物连续至少2个小时出现有效场景一告警。
- 场景一数据完整率必须达标。
- 重复小时不重复计数；中断后结束旧过程并新建过程。

### 9.3 污染物配置

| 污染物 | 回溯时间 | 轨迹高度 AGL | 近地证据窗口 | 近地最大高度 |
|---|---:|---|---:|---:|
| PM2.5 | 48小时 | 100/500/1000 m | 6小时 | 500 m |
| O3 | 48小时 | 100/500/1000 m | 6小时 | 500 m |
| NOX | 24小时 | 100/300/500 m | 6小时 | 300 m |

### 9.4 完整流程

```text
场景一告警进入连续性状态机
  -> 去重并检查是否连续
  -> 连续2小时后创建 pending job
  -> 每小时25分获取一个待执行任务
  -> 对污染时段运行 NOAA/HYSPLIT 多高度后向轨迹
  -> 对前6小时控制时段运行对照轨迹
  -> 合并过程级轨迹缓存
  -> 轨迹质量门控
       有效轨迹 >= 6
       成功率 >= 80%
       覆盖回溯时间 >= 80%
  -> 近地轨迹50 km停留比例初判
       >= 0.60：local_accumulation
       <= 0.35：regional_transport
       其他：mixed
  -> 识别不同高度的主要输送方向和通道
  -> 轨迹与排污许可企业空间相交
  -> 积累轨迹样本并计算加权 CWT
  -> 生成污染期/对照期轨迹地图、企业地图和交互地图
  -> 保存过程输出并发布 completed 事件
```

### 9.5 涉及工具和架构

- 状态机与任务：`backend/app/scenarios/xuchang_transport_escalation/service.py`。
- NOAA/HYSPLIT：`TrajectoryRunner`。
- 输送通道和企业筛查：`spatial_analysis.py`。
- CWT/WCWT：`cwt_analysis.py`。
- 静态地图：`visualization.py`。
- 交互地图程序：`interactive_map.py`。
- Fetcher：`backend/app/fetchers/xuchang_transport_analysis.py`。
- 事件：`xuchang.station_deviation.escalated`、`xuchang.transport_analysis.completed`。

### 9.6 输出

- 污染期和控制期后向轨迹端点。
- 轨迹质量报告。
- 本地积累/区域输送/混合初判。
- 分高度输送通道。
- 与轨迹空间相交的企业候选。
- CWT/WCWT 网格结果及样本成熟度。
- PNG 地图和交互式地图程序。

### 9.7 质量和结论边界

- 轨迹质量不达标时输出 `insufficient_evidence`，不得继续给出强输送结论。
- 50 km停留比例只是轨迹特征，不是本地或区域贡献比例。
- CWT 至少需要每高度16条轨迹，30条以上才达到推荐样本量。
- 后向轨迹、风向和企业相交均是来源线索，需结合浓度时序、排放和遥感证据。
- 外部 NOAA 失败必须保留失败任务、错误原因和可重试状态。

## 10. S6：遥感污染研判

### 10.1 业务目标

利用 GEMS 和 Sentinel-5P 等卫星产品识别污染物空间分布、潜在输送带和高值区域，为地面监测及轨迹分析补充空间证据。

### 10.2 流程

```text
确定污染物、日期、区域和卫星产品
  -> 查询本地卫星目录
  -> 检查覆盖时间、云量和缺测
  -> 获取 GEMS/Sentinel-5P 图像或数据
  -> 与地面站点、气象场和后向轨迹对齐
  -> 标记空间高值和输送方向一致性
  -> 输出“支持/不支持/证据不足”的线索判断
```

### 10.3 工具

- `get_gems_image`。
- `get_sentinel5p_image`。
- `gems_xuchang_image_fetcher`。
- 气象查询、空气质量查询、轨迹和地图工具。

### 10.4 结论边界

- 柱浓度、AOD和火点不能直接等同于地面浓度或排放量。
- 卫星过境时间与地面异常时间不一致时，只能作为背景证据。
- 云覆盖、反演误差和空间分辨率必须在结论中说明。

## 11. S7：项目知识问答

### 11.1 业务目标

基于用户有权限访问的许昌知识库回答政策、标准、项目资料和业务规则问题，并提供可追溯原文依据。

### 11.2 流程

```text
用户问题
  -> 确定可访问知识库
  -> 混合检索和重排
  -> 简单事实直接回答
  -> 条款/数字/上下文敏感问题补读相邻原文
  -> 向量检索不足时查询知识图谱和业务规则
  -> 输出回答、文档名称、章节、分块或图谱路径
```

### 11.3 涉及能力

- `knowledge_qa_workflow`。
- `knowledge_document_reader`。
- `knowledge_graph_query`。
- PostgreSQL 元数据、Qdrant 混合检索和图谱仓储。

### 11.4 质量边界

- 用户选择知识库后不得越界检索。
- 上传材料与正式知识库来源必须区分。
- 无结果时明确证据不足，不使用模型常识伪装成知识库结论。
- 制度条款和关键数字应补读原文，而不是只依赖向量摘要。

## 12. S8：专家会商

### 12.1 业务目标

围绕污染过程组织气象、空气质量、源解析、遥感等专家进行基于事实的多轮研判，并保留不同意见和证据缺口。

### 12.2 流程

```text
导入会商表、报告、数据文件和工具结果
  -> LLM 提取结构化事实并写入事实账本
  -> 主持人发布议题
  -> 各领域专家并行初判
  -> 专家交叉提问
  -> 对缺失证据生成补证计划并调用工具
  -> 第二轮修正意见
  -> 审查员核验结论边界
  -> 形成共识、异议、禁止性结论和证据矩阵
  -> 生成会商报告和过程时间线
```

### 12.3 涉及组件

- `backend/app/services/expert_deliberation/`。
- 许昌 expert 提示词。
- 空气质量、气象、卫星、轨迹、企业和知识工具。
- ExpertDeliberationView 和报告生成能力。

### 12.4 质量边界

- 事实、专家判断和最终共识必须分层存储。
- 每条关键结论应关联事实 ID 或工具证据。
- 对证据不足、仅有相关性或存在反例的判断生成禁止性结论。
- 工具补证失败不能被文本生成掩盖。

## 13. S9：综合报告

### 13.1 业务目标

把查询结果、业务事件、图表、地图、专家结论和证据文件整理为可交付的正式报告。

### 13.2 流程

```text
确定报告主题、时段、对象和模板
  -> 收集结构化结果与证据资源
  -> 校验关键数字、单位、来源和图片
  -> 组织摘要、过程、成因、风险、建议和附录
  -> 生成报告包
  -> 渲染 DOCX/PDF
  -> 校验缺图、断链、空章节和引用
  -> 通过前端资源面板交付
```

### 13.3 质量边界

- 报告文本不得产生工具结果中不存在的数字。
- 结论等级必须继承场景一、场景二和专家会商的证据等级。
- 所有图表和地图应记录数据范围、生成时间和来源文件。
- 报告产物应注册为前端可访问资源，不暴露服务器绝对路径。

## 15. 共用业务契约

所有场景建议统一以下字段：

- 身份：`event_id`、`event_type`、`process_id`、`job_id`、`schema_version`。
- 范围：城市、行政区代码、站点、污染物、开始和结束时间、时区。
- 数据质量：完整率、缺测数、数据新鲜度、质量状态和排除原因。
- 方法：算法名称、参数版本、标准版本和代码版本。
- 证据：输入记录、工具结果、文件路径、来源系统和生成时间。
- 结论：分类、置信度、适用范围、限制条件和禁止解释。
- 运行：状态、耗时、重试次数、错误、是否满足 SLA。

这些字段应由确定性服务生成，Agent 只能读取和解释，不应自行补造。

## 16. 优先改进建议

### P0：业务正确性

1. 明确日达标预测的有效小时数和缺测处理法规口径。
2. 将所有阈值、标准和算法版本集中到许昌项目配置，并记录进结果。
3. 为场景一和场景二建立业务事件 JSON Schema。
4. 保证所有数值结论均能回到数据库记录或证据文件。

### P1：流程可靠性

1. 将场景二文件状态机迁移为可恢复任务，但保持算法服务不变。
2. 为外部 NOAA、卫星和预报服务增加幂等、重试、熔断及降级状态。
3. 建立污染期、无污染期、缺测期和外部服务失败期回归样本。
4. 前端统一展示“数据不足”“分析失败”和“低置信度”，不能只显示最终文字。

### P2：分析能力

1. 年度预测增加相似气象年筛选和情景权重。
2. 场景一补充企业排放量、生产工况和执法记录后再提升置信度。
3. 场景二引入周边城市浓度时序和更多对照过程。
4. 将卫星、轨迹、站点、企业和专家结论汇总为统一证据矩阵。
