# 工单审核自我迭代复盘技能

## 概述

统计与对账由确定性工具完成，Agent 负责清单结构化、口径确认和报告叙事。**计数永远来自工具返回，Agent 不得自行数台账。** 红线：本技能全链路只读规则配置，不修改 `configs/*.yaml`、不调用 `ops_audit_run_rules` 改写审核产物。

## 通道2：用户核对清单对账

### 1. 前置确认（缺一不可）

- 对账目标期次：让用户提供（或从上下文取）当期审核的 `final_issue_list` 路径，优先用工具结果原值；找不到时先检索最近执行目录，不猜测路径。
- **全量/部分声明**：清单是否覆盖当期全部问题工单的核对。这决定 tacit 信号是否成立与错误率是否可算，用户没说就问一句；用户说"只核对了部分/只看了几个站"即 partial。
- 数据集路径（可选但推荐）：用于识别不在期次的工单号。

### 2. 清单结构化

用户上传 Excel/Word/文本清单后，逐行转成工具条目：

- `order_code`：工单编号原文；明显笔误先向用户确认，不自作主张改。
- `verdict`：用户**说**有问题 → `problem`；用户**说**没问题 → `ok`。只反映清单原文，不掺审核结果。
- `problem_category`：把用户的问题描述归入规则目录分类词表（一致性问题/完整性问题/异常说明问题/数值逻辑问题/时间合理性问题/表单完整性问题/规范性问题/附件质量问题）。归不进去就省略该字段（=工单级任意类型匹配），不要造词——工具会拒绝未知词表并回显合法值。
- `note`：用户原文描述，逐字保留。

### 3. 对账与回显

调用 `ops_audit_reconcile_checklist`。把返回的 `echo_lines` 原样回显给用户，明确标出：

- `missed`（用户说有问题但审核没报）与 `unmatched`（工单号不在期次）两类必须逐条请用户确认；确认有误就修正条目后重新对账（重复提交同一内容会自动去重，修正后内容哈希不同会形成新记录，这是预期行为）。
- 指标文本（"识别率：78%（14/18）"）原样转述，分子分母不许省略。

## 月度复盘（定时任务 / 手动触发）

### 1. 统计

调用 `ops_audit_retrospective_stats`（月份缺省为上一自然月；月度任务显式传 `enable_db_recheck: true` 执行通道3 回库分诊）。统计产物已归档，报告只消费返回的 `data`。

### 2. 报告契约（markdown，`ops_audit_retrospective_<月>.md`）

1. **开篇 KPI**：台账记录数、清单识别率、清单错误率（无全量声明时写"不适用"并说明）、面板确认率/排除率、滚动窗口指标。全部带分子分母。
2. **分流清单**（每项一个问题域，给证据）：
   - 口径问题：`db_recheck=verified` 且推翻集中的规则 → 建议校准方向；
   - 数据管道问题：`data_drifted` 聚合 → 建议回流数据管道清单，不改规则；
   - 候选新规则：`missed` 且 `rule_id=null` 的聚合（含样本工单号）；
   - 校准参考：`evidence_mismatch` 与置信度/结局交叉表。
3. **变更建议**：每条含证据链（台账计数+样本）、预期影响面（"采纳后影响 N 单/期"量级）、建议改动的配置文件路径。只建议，不实施。
4. 两通道指标背离（如面板排除率高但清单错误率低）单独点评，提示确认疲劳等解释。

### 3. 红线

- 不修改任何 `configs/*.yaml`；不调用 `ops_audit_run_rules`；台账与 metrics_history 只追加不重写。
- 小样本（分母 < 5）的比率必须标注"样本过小，仅供参考"。
- 漏报信号（missed）比误报更稀缺，报告排序优先。
- 历史记忆若提示某提案上月已被否决，除非本月有新证据，不重复提交同一提案。
