# 图表引用机制：统一到文件路径的策略讨论

> 历史讨论稿（2026-11-27）。本文保留改造前的数据、问题和评估。
> 最终的路径解析与资源 ID 交付协议见[会话正文图表引用](chart-aliases.md)。

## 1. 起因

2026-11-27 许昌部署，会话 `query_session_1795750683372_cb3e0485aba5` 的答复里三张
execute_python 生成的图没有渲染，正文留下 `[[chart:...]]` 原文。

- 不是模型输出问题：标记里的 ID 与资源目录中图片的 `metadata.visual_id` 完全一致。
- 直接原因：资源目录接口的 `resource_dto`（`app/api/session_resource_routes.py`）当时
  只对 `chart-spec`、`chart-image` 两类资源键透出 `visual_id`，而 execute_python 图片
  的资源键是 `primary:png`，接口返回的 `visual_id` 为空；前端按 `visual_id` 匹配占位符
  落空，占位符原样留在正文里。
- 来源：b265fa28（2026-11-11）给图片产物分配了 `visual_id` 并放宽了前端匹配，但漏改了
  中间这层序列化，也没有测试覆盖这一层。
- 修复：80657d1d（DTO 改为 `metadata` 带 `visual_id` 即透出，并补契约测试），合入
  xuchang 为 071bd7c4。

由此引出的问题：现行的图片 ID 机制是否走在正确的方向上，要不要统一到文件路径。

## 2. 现行机制

一张图在系统里有四个名字：

| 身份 | 例子 | 谁产生 | 谁使用 |
|---|---|---|---|
| 文件路径 | `backend/backend_data_registry/python_generated_files/x.png` | 工具写文件 | 模型、报告包、DAG 交接、微信推送 |
| `resource_id` | 32 位哈希 | 资源目录发布 | 目录主键；按"会话 + 资源组 + 版本 + 资源键"哈希，跨会话重新发布后会变 |
| `visual_id` | `matplotlib_hojgj2u7x1` | 发布时分配 | 落库后的占位符，Web 与 App 的匹配键 |
| 短别名 | `chart_3` | 执行器绑定额 | 模型抄写 |

链路：工具返回图，执行器为带 `visuals` 的结果绑定短别名，并在摘要里给出可复制的标记行；
模型写 `[[chart:chart_N]]`；finalizer 在落库和下发前还原成 `[[chart:<visual_id>]]`，
并把误填的 `resource_id` 归一化，接口层另对抄错的 ID 做编辑距离修复；Web 从资源目录
接口按 `visual_id` 找到资源，渲染成图片或交互图卡片；App 用正文标记去附件列表里按
`visual_id` 或 `file_id` 找图。

"什么算可内联的图"这条规则分散在至少 5 处，用了 3 种判据（资源键、`renderer`、
`metadata.visual_id`）：资源声明、目录 DTO、前端 `inlineChartImages.js`、App 资源
描述符、`run_agent_workflow` 的 `published_charts`。

前后四起事故是同一个模式，即某一层没认出另一个名字：

1. 早期：ID 用纳秒时间戳，并允许中文和点号进入 ID，模型抄错或占位符匹配失败。
2. 2026-10-13 至 10-19：模型抄错 `visual_id`，6 个标记未解析，随后引入短别名。
3. 2026-11-11：图片产物没有视觉身份，模型把 `resource_id` 填进占位符，3 个标记未解析。
4. 2026-11-27：目录 DTO 漏字段（本次）。

### 3.3 DAG 子图

父会话目录里有 `run_agent_workflow` 发布的子图的会话共 66 个。其中 18 个有最终答复，
16 个调用了 `create_report_package`，16 个有报告包资源，最终答复里引用子图 0 次。也就是
说，跨 Agent 传图在生产上走通的是文件路径：子图按路径写进了报告包。

`published_charts` 让父 Agent 用子会话 `resource_id` 引用的指示从未被使用。按代码它也
无法翻译：子会话的资源重新发布到父会话后 ID 已变，而 `normalize_chart_placeholders`
只按本会话的 `resource_id` 匹配。这是潜在缺陷，优先级低。

### 3.5 存储

- 非截图类在册图片所在目录：`python_generated_files/` 543 张，`uploads/` 53 张，其余
  零散在各工具目录（`weather/charts` 16 张，`images` 12 张等）。
- `python_generated_files/` 是所有会话共用的平铺目录。
- 被多个会话引用的同一路径有 104 个，主要是 DAG 把子会话的文件重新发布到父会话；
  其中文件大小变过的有 1 个。
- 注册表内的文件在发布和跨会话重新发布时路径不变。注册表外（上传、临时目录）的文件
  发布时会被拷贝，路径会变。

### 3.6 协议铺开面

提到 `[[chart:` 的文件：`backend/app` 37 个，`backend/tests` 9 个，`backend/docs` 2 个，
`frontend/src` 9 个（其中源码 5 个），安卓 4 个。

### 3.7 模型自发写图

最终答复里出现过 5 处 markdown 图片语法，全部是 `![](文件路径或旧图片地址)`，在现行
协议下均不渲染。

## 4. 评估

有效的部分：模型手里有短别名时（问数、专家模式的直接对话），引用工作良好，标记解析率
为 97%（317/326）。

结构性成本：

1. 一张图四个名字，靠人工在各层之间翻译维持一致，四起事故都是翻译断了。
2. 短别名是"绑"出来的，不是图自带的：只有经过执行器的工具结果才有；Redis 不可用时
   退回让模型抄高熵 ID，正是已知会出错的方式。
3. 规则分散、判据不一，没有测试把它们钉在一起。
4. 协议与模型的天性相反：没有标记可抄时，模型写的是 markdown 图片加路径。

## 5. 方向

讨论意见（未定）：把文件路径作为模型唯一可见的引用身份，`visual_id` 退为服务端和
客户端的内部句柄。

路径是产物自带的身份：工具结果里有它，DAG 交接传的是它，报告和微信推送按它取图；它在
发布和跨会话重新发布时不变。

设计原则：

- 模型写标准 markdown 图片，路径用工具返回的值。
- 服务端在 finalizer 落库前统一解析：先精确路径，其次会话内唯一文件名，最后编辑距离
  容错；解析结果改写成现有的内部标记。Web、App 会话、定时任务三条管线都在这一处覆盖。
- 落库的是解析后的句柄而不是路径，避免文件被覆盖后旧答复跟着变。
- 客户端拿到的仍是不透明地址，不按路径读文件。安全模型不变，Web、App、微信推送不用改。
- "什么算可内联的图"收成一个判定函数，并加跨层契约测试。
- 解析不了的引用显示成可见的破图，不悄悄消失。

不做成什么样：不让前端和 App 按路径取图。那要把路径下发给客户端，改前端 5 个源码
文件、安卓 4 个文件并发 APK，后端须先于 APK 发布，未升级的旧 APK 在升级前不出图；
收益只是少一个内部字段。

## 6. "一步到位"的两种范围

| | 只统一模型侧 | 传输层也统一 |
|---|---|---|
| 模型写法 | 只有路径 | 只有路径 |
| 客户端 | 不变，收到的正文和附件与现在一致 | 按路径匹配资源 |
| 历史数据 | 不迁移，已落库的 326 个标记照常解析 | 永久兼容旧标记，或做数据迁移 |
| 改动面 | 约 20 个后端文件：提示词与手册 4 个，设计文档 2 个，短别名相关 6 个，finalizer 解析与资源声明，以及部分工具的说明文字 | 另加前端、安卓、APK 发版，微信推送与分享页核对 |
| 发布 | 重启 web 和 worker | 多端协同 |

两种范围共同的前提：

1. 图片发布时做快照。路径成为身份后，同名覆盖会让旧答复换内容。
2. 上传与临时目录的文件发布时会被拷贝，要记录模型看到的源路径。
3. 容错解析，并打点精确、文件名、容错、未解析各占多少。
4. 单一判定函数与跨层契约测试。
5. 一个开关（模型侧引用方式：路径或标记），按未解析率决定保留还是切回。

未知数：模型抄长路径的准确率没有数据。

## 8. 容易误判的点

- "DAG 子图没有被正文引用"不是故障：父 Agent 的交付物是报告包，子图按路径进了报告。
- 其他模式（custom，以及没有模式标记的会话）里图为 0 引用，同样不能当失败率。
- 问数和专家模式里未进正文的图，包含被重新生成的旧版本和中间图。
