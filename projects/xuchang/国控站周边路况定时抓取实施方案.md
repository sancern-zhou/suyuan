# 许昌国控站周边路况定时抓取与历史回填实施方案

> 状态：设计定稿，待远端服务器实施。数据源与工具代码已在 xuchang 分支
> `backend/app/tools/xuchang/traffic_status/`（commit 07397baf）落地并通过实测。
> 本文面向在服务器上实施定时抓取脚本的开发者。

## 1. 背景与目标

- 通过百度地图实时路况查询 API（Traffic API），按固定节奏抓取 7 个国控空气监测站周边的路况，
  回填项目 Postgres，积累成历史时序，用于"交通活动对站点空气质量的扰动"类历史分析。
- **核心认知：百度只返回查询时刻的状态，路况历史无法回补。** 定时抓取从上线那一刻开始积累，
  worker 停机造成的时隙缺口是永久缺失，因此抓取进程的存活优先级要按业务 worker 同级对待。

## 2. 配额约束与分配

约束：**日调用量 2000 次/日，峰值并发 3 次/秒**（按 AK 计）。

| 用途 | 计算 | 日用量 | 占比 |
|---|---|---|---|
| 核心时序：每站每 6 分钟，全天 240 时隙 | 6 站 × 240 | 1440 | 72% |
| 道路级补充：8 条主干道 × 早晚高峰各 2 时点 | 8 × 4 | 32 | 1.6% |
| 当轮失败重试缓冲 | — | 80 | 4% |
| 实时调取（专家/问数 agent 按需） | 硬预留 | 50 | 2.5% |
| 应急余量 | — | 298 | 15% |
| 合计 | | 1900 | 95% |

- **国控站实测 6 个**（2026-10-10 中台核对：1003A/1005A/1008A/1009A/1011A/1012A；1011A 挂建安区
  areacode=411003，查询须用 `4110%` 前缀，初版"7 站"口径已修正）。6 分钟节奏下余量充足；
  6 站如改 5 分钟需 1728 次/日，配额上可行但重试与应急余量收窄，暂维持 6 分钟。
- 计数器硬顶 **1900**；优先级只有两档：实时永远放行（50 次用完才拒），其余全部归定时任务。
- 若将来实时与定时互相挤占，可向百度申请第二个 AK（配额按 AK 独立计算）做隔离。
- 降级预案：若百度调低配额，把夜间 22:00–06:00 降到 30 分钟间隔即可腾出约 190 次/日，分析价值几乎无损。

## 3. 数据源接口与鉴权

### 3.1 接口

| 接口 | 用途 | 关键参数 |
|---|---|---|
| `GET https://api.map.baidu.com/traffic/v1/around` | 站点周边圆形区域路况（主力） | `center=纬度,经度`（小数≤6位）、`radius=1000`（上限1000米）、`road_grade=0`、`coord_type_input=wgs84`、`coord_type_output=gcj02` |
| `GET https://api.map.baidu.com/traffic/v1/road` | 指定道路双向路况（补充） | `road_name`、`city=许昌市` |

两个接口都必须带 `ak` 与 `sn`（SN 放参数最后）。返回坐标统一 gcj02。

### 3.2 返回结构（实测确认）

- `evaluation`：`status`（0未知/1畅通/2缓行/3拥堵/4严重拥堵）+ `status_desc`（如"双向畅通"）；
- `description`：语义化路况综述；
- `road_traffic[]`：范围内道路清单（`road_name`；无名道路为 `UNKNOW`，属正常归档）；
  其 `congestion_sections[]` 含 `status`、`speed`（km/h）、`congestion_distance`（米）、
  `congestion_trend`（较10分钟前：加重/持平/缓解）、`section_desc`。
- **注意：车速/拥堵距离/趋势明细只在存在拥堵路段时返回**，全畅通时 `congestion_sections` 为空数组，
  这是数据口径，不是故障。高峰时段的真实样本质量需上线后专项核查（见 §9）。

### 3.3 SN 签名（复用已提交代码）

官方算法：对 `路径?参数串`（参数按 key 字典序、值为原文、sn 不参与）做
`quote(safe="/:=&?#+!$,;'@()*[]")` → 拼 SK → 整体 `quote_plus` → MD5 十六进制。
**签名过的坑：最外层 quote_plus 不能漏，否则恒报 status=211。**

服务器上直接复用分支内实现，不要再手写一遍：

```python
from app.tools.xuchang.traffic_status.client import BaiduTrafficClient  # 内含 SN 与错误码提示
from app.tools.xuchang.traffic_status.signing import build_signed_url    # 如需裸构造 URL
```

凭证读环境变量 `BAIDU_MAP_AK` / `BAIDU_MAP_SK`（本地 `backend/.env` 已配置，服务器需同步）。

## 5. 数据库设计（项目 Postgres，`DATABASE_URL`）

```sql
CREATE TABLE traffic_snapshot (
    id              BIGSERIAL PRIMARY KEY,
    station_code    TEXT        NOT NULL,            -- 国控站编码（中台 station.code）
    slot_at         TIMESTAMPTZ NOT NULL,            -- 时隙起点（UTC，时隙 = 对齐到 6 分钟栅格）
    queried_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    evaluation_status SMALLINT,                      -- 0未知/1畅通/2缓行/3拥堵/4严重拥堵
    evaluation_desc TEXT,
    description     TEXT,                            -- 百度语义化综述
    road_count      SMALLINT,
    congestion_section_count SMALLINT,
    raw             JSONB,                           -- 原始响应；体积敏感时可只存拥堵时隙
    UNIQUE (station_code, slot_at)                   -- 幂等去重：重试不产生重复计费
);
CREATE INDEX traffic_snapshot_slot_idx ON traffic_snapshot (slot_at);

CREATE TABLE traffic_section (
    id                   BIGSERIAL PRIMARY KEY,
    snapshot_id          BIGINT NOT NULL REFERENCES traffic_snapshot(id) ON DELETE CASCADE,
    road_name            TEXT,
    section_desc         TEXT,
    status               SMALLINT,
    speed_km_h           SMALLINT,
    congestion_distance_m INTEGER,
    congestion_trend     TEXT                        -- 加重/持平/缓解
);
CREATE INDEX traffic_section_snapshot_idx ON traffic_section (snapshot_id);
```

小时聚合视图（历史分析对接面，与空气质量小时表按 `station_code + hour` join）：

```sql
CREATE OR REPLACE VIEW v_station_traffic_hourly AS
SELECT s.station_code,
       date_trunc('hour', s.slot_at)                       AS hour_ts,
       COUNT(*)                                            AS samples,
       AVG(s.evaluation_status)::numeric(4,2)              AS avg_status,
       MAX(s.evaluation_status)                            AS max_status,
       SUM(s.congestion_section_count)                     AS congestion_sections,
       AVG(sec.speed_km_h)::numeric(6,1)                   AS avg_speed_in_sections
FROM traffic_snapshot s
LEFT JOIN traffic_section sec ON sec.snapshot_id = s.id
GROUP BY 1, 2;
```

数据量：1680 快照/日 ≈ 61 万行/年；明细表只在拥堵时膨胀；建议按月分区（实施时可先不分区，千万行级以内单表无压力）。

## 6. 调度设计

### 6.1 节奏与并发

- 系统 cron：`*/6 * * * *` 触发**一次性脚本**（进程跑完即退），`flock` 防重叠：

```cron
*/6 * * * * cd /path/to/suyuan/backend && /usr/bin/flock -n /tmp/xuchang_traffic_collect.lock \
  /path/to/conda/envs/backend_py311/bin/python -m scripts.xuchang_traffic_collect \
  >> /tmp/xuchang_traffic_collect.log 2>&1
```

- 每轮：6 站串行 + 每请求间隔 3 秒（约 18 秒/轮），峰值 0.33 QPS，给实时留 2.5+ QPS；
- 时隙对齐：`slot_at = floor(now / 6min) * 6min`，同一时隙内重复执行被 UNIQUE 挡住，天然幂等；
- 道路级 32 次：拆进早晚高峰（如 08:00、08:30、18:00、18:30 四个时点各 8 条，脚本内按 slot 判断触发）。

### 6.2 配额计数器（Redis，复用 .env 的 REDIS_* 配置）

- key：`baidu_traffic:quota:{YYYYMMDD}`，`INCR` 后 `EXPIRE 172800`；
- 每次调用前 `INCR`，返回值 > 1900 则放弃本次调用并告警日志；
- 每轮开始预检查：剩余额度 < 10 则本轮直接跳过；
- 实时路径（agent 工具）与定时路径**共用同一个计数器**，实时不 pre-check 上限（优先放行），超 1900 才拒。

### 6.3 失败处理与补采口径

- 仅网络异常/5xx/超时重试一次（30 秒后），计入重试缓冲；业务错误码（2/101/102/211 等）不重试，
  记 ERROR 日志并告警——211/101 属于凭证配置错误，需要人处理；
- **不做跨时隙补采**：6 分钟后拿到的是新数据，填进旧时隙是失真数据。错过的时隙就是缺失，
  分析侧按 `samples` 列识别可信度；
- 单日连续 3 轮全站失败 → 触发告警（进程/凭证/网络故障）。

## 8. 脚本骨架（backend/scripts/xuchang_traffic_collect.py）

```python
"""许昌国控站周边路况定时抓取（cron */6 一次性执行，flock 防重叠）。"""
import asyncio, json, os, time
from datetime import datetime, timezone

SLICE_SECONDS = 360  # 6 分钟时隙
REQUEST_INTERVAL = 3  # 秒/请求
QUOTA_KEY = "baidu_traffic:quota:{ymd}"
QUOTA_HARDCAP = 1900

def current_slot(now: datetime) -> datetime:  # 对齐 6 分钟栅格
    ts = int(now.timestamp()) // SLICE_SECONDS * SLICE_SECONDS
    return datetime.fromtimestamp(ts, tz=timezone.utc)

async def collect_round():
    stations = json.load(open("projects/xuchang/traffic_stations.json", encoding="utf-8"))
    slot_at = current_slot(datetime.now(timezone.utc))
    if quota_remaining() < len(stations) + 2:   # Redis 预检查
        return
    client = BaiduTrafficClient()               # 复用工具包：内含 SN、错误码提示
    for st in stations:
        if quota_incr() > QUOTA_HARDCAP:
            break
        try:
            payload = await client.query_around(latitude=st["lat"], longitude=st["lng"])
            save_snapshot(st["code"], slot_at, payload)   # UPSERT ON CONFLICT (station_code, slot_at)
            save_sections(payload)                        # 仅拥堵路段有明细，空数组跳过
        except Exception as exc:
            log_error(st["code"], exc)                    # 业务错误不重试；网络类 30s 后重试一次
        await asyncio.sleep(REQUEST_INTERVAL)
    maybe_collect_roads(slot_at)                          # 高峰时点触发道路级查询

asyncio.run(collect_round())
```

（Redis 计数、UPSERT、道路级触发按 §2/§5/§6 实现即可；告警接现有通知渠道。）

## 10. 风险与备注

1. **历史不可回补**：上线时间即数据起点；worker 停机=永久缺口，脚本要求 flock + 告警保活；
2. 百度配额口径可能调整（当前 2000/日、3 QPS 按 AK 计），计数器硬顶集中在常量 `QUOTA_HARDCAP`，改一处即可；
3. `UNKNOW` 道路名是百度对无名路段的归档，分析时按"其他道路"处理；
4. 站点坐标来源必须是中台镜像表（WGS84），脚本与工具均不兼容手工估算坐标；
5. 实时 50 次/日的额度大约支撑 3~5 次重度研判会话（每会话全站 7 次，双半径对比翻倍），
   超额时工具返回明确的"当日实时额度已用完"提示，不会挤穿定时预算；
6. 本方案与 `query_xuchang_traffic_status` 工具（07397baf）共用同一 BaiduTrafficClient 与计数器，
   工具侧行为变更需回归 §9 验收第 1、2 项。
