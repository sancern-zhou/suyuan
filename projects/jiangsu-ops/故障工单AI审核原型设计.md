# 江苏故障工单 AI 审核原型设计

> 版本：v0.3（212 张工单全量详单分析与方案原型）
> 数据窗口：2026-07-24 00:00:00 至 2026-08-24 23:59:59，按工单创建时间
> 数据来源：江苏运维平台故障工单清单、故障工单详单及附件元数据；所有查询均为只读
> 目标：以 AI 审核逐步替代省中心的重复性故障工单审核，同时独立判断受影响监测数据是否需要剔除

## 1. 结论摘要

最近一个月共取得 212 张故障工单，覆盖 75 个站点，清单与详单现在均已按完整工单号逐站点匹配。本文的总体分析范围是 212/212 张工单的 `orderTitle + orderContent + otherContent + details.submitRemark`，不是仅分析正文中提到数据剔除的 9 张。9 张只是清单正文明确写出剔除意见的子集；详单已扩展为 212 张全量，不再是 10 张校准样本。

当前真正处于“省中心审核”且工单状态为“处理中”的待审工单为 21 张；另有 149 张已在省中心节点完成，可作为历史回放和人工结论校准样本，不能计入当前待审积压。

基于 212 张的全部可用文本字段，第一层可解释规则分类如下。该分类用于路由证据和审核模板，不直接代替最终审核结论。

| 一级故障类型 | 工单数 | 占比 | 当前省中心待审 | 主要审核风险 |
| --- | ---: | ---: | ---: | --- |
| 自动质控/校准异常 | 88 | 41.5% | 7 | 质控失败原因、任务是否真实执行、复测是否合格、质控期间数据边界 |
| 监测数据异常 | 88 | 41.5% | 7 | 环境真值与仪器故障难区分，最容易误剔除真实污染过程 |
| 数据传输/平台离线 | 20 | 9.4% | 4 | 离线不等于无效；应先判断是否可补传、是否仅平台链路异常 |
| 仪器/辅机硬件故障 | 10 | 4.7% | 3 | 故障是否影响测量、影响哪个污染物、恢复时间是否有证据 |
| 其他/需语义分类 | 6 | 2.8% | 0 | 标题过短或现象特殊，需要详单和附件补证 |

212 张都能从清单或详单文本识别故障现象。在详单处置/复核提交意见中，文本抽取出 129 张明确原因、161 张明确处置动作、97 张有恢复或观察结果。133 张写出可闭合的时间区间。按详单文本抽取，116 张形成剔除候选、55 张表达保留或未见剔除、3 张表达补录/补传，38 张未写数据处置。这些是文本抽取的候选结果，不是平台最终有效性判定；“未写剔除”不等于“数据有效”。

原型建议采用“两项独立结论”：

1. `work_order_decision`：工单是否允许通过省中心审核；
2. `data_disposition`：受影响数据是保留、剔除、部分剔除、仅记缺失，还是证据不足。

第一阶段采用影子审核，不回写江苏平台。完成至少 2–4 周人工对照后，再开放低风险自动通过；涉及数据剔除的结论在证据链和回放指标达标前继续保留人工确认。

## 2. 当前江苏分支能力与缺口

### 2.1 已有能力

- `jiangsu_fetch_fault_work_orders`：按创建时间、工单节点、节点状态、工单状态和站点筛选故障工单清单，并在工具内部完成分页。
- `jiangsu_fetch_fault_work_order_detail`：按完整工单号精确获取 `wo`、处置流程 `details`、故障项、检查项、设备、流程和附件；不会用同站其他工单替代。
- `jiangsu_fetch_station_data`：查询站点 5 分钟、小时、日数据，支持原始/审核、工况/标况。
- `jiangsu_fetch_qc_task_history/status/run_logs/monitoring_curve`：查询质控任务、执行状态、日志和响应曲线。
- `jiangsu_fetch_station_alarm_logs`、`jiangsu_fetch_alarm_records`：查询设备告警和平台告警记录。
- `jiangsu_fetch_station_environment_history`：查询温湿度、电流电压、钢瓶压力和采样参数。
- `jiangsu_fetch_auto_inspection`：查询站点自动巡检快照。
- 现有反馈循环可以记录 AI 建议、人工接受/修改/驳回、业务动作和后续验证结果。

### 2.2 当前边界

- 当前“工单审核模式”只读查询和辅助人工复核，不创建、修改、关闭或正式审核工单。
- 当前通用 `ops_work_order_audit` 主要面向巡检/RF 表单、流程和附件规则，不等同于故障工单省中心审核，也没有覆盖“是否剔除监测数据”的完整证据链。
- 当前故障工单清单与详单接口依赖统一 Token 服务；本次抽取中出现过临时 503 和慢响应。接口失败或详单缺失必须是自动审核硬阻断条件。
- 当前站点数据工具面向普通分析时会压缩部分审核标记字段。AI 审核服务必须保存原始字段及 `_Mark`、有效性状态等审核字段，不能只消费面向对话的压缩结果。
- 仓库中尚未实现省中心 `FaultApprove` 节点的正式回写适配器；上线前需要平台侧确认审核 API、字段、幂等键、权限账号和回滚机制。

### 3.4 212 张全量详单与处置分析

本次已验证 `take` 参数可按站点返回更大的近期详单窗口，但接口本身仍不是按工单号直查；正式原型仍需平台提供按完整工单号直查的详单接口，或提供可分页、可校验总数的站点历史详单接口。

### 3.5 代表性详单

样本工单 `FA260823178749183735684` 当前位于省中心审核节点：

- 故障现象：NO 偏高波动；
- 现场原因：仪器内部管路冷凝水；
- 处置：零气吹管、调整站房温控；
- 恢复声明：仪器恢复，零跨和精度检查正常；
- 运维建议：14–21 时高值数据作无效审核；
- 详单包含创建、故障处理、运维单位复核 3 条历史流程和 2 个现场附件。

该样本不能因运维文字中出现“无效审核”就自动剔除 14–21 时数据。AI 还必须验证：

1. 原始 5 分钟/小时 NO、NO2、NOx 数据的异常起止；
2. 数据标记和仪器报警是否与候选区间一致；
3. 邻近站和同城站是否存在同步升高，排除真实区域污染；
4. 站房温湿度、采样参数和冷凝水证据是否支持因果关系；
5. 处置后零跨/精度结果和数据恢复是否成立；
6. 候选区间内应影响 NO、NO2、NOx 中的哪些指标，而不是默认整站全因子剔除。

本轮进一步只读核验了该站点 2026-08-23 12–23 时的原始工况和审核工况小时数据。结果显示：

- 原始数据 14–16 时 NO 从 17 上升到 36，17 时为 `42(H)`；18–20 时回落到 9、5、0，21 时为 `5(H)`，22 时后恢复为无标记低值；
- 审核数据中 14–16、18–20 时主要表现为 `NO2_Mark=RM`，17 和 21 时 NO、NO2、NOx 均为 `H`；
- 审核状态是“分指标、分小时”的，不等价于把 14–21 时 NO、NO2、NOx 全部统一剔除；
- `RM`、`H` 的平台业务字典和最终有效性含义仍需平台侧确认，在字典未确认前不得由 AI 自行解释或重复写标记。

因此原型对该样本的安全输出应是“工单材料基本完整；已检测到现有分指标审核状态，禁止按正文整段重复剔除；待确认标记字典、邻站对比和最终平台审核结果”，而不是直接自动通过并再次剔除。

## 4. AI 审核所需数据

### 4.1 P0：缺失即禁止自动审核

| 数据域 | 必需字段/内容 | 用途 |
| --- | --- | --- |
| 工单主表 | 工单号、站点、设备、污染物、标题、正文、紧急程度、创建/完成时间、当前节点、工单/流程状态 | 确认对象、状态和基础时间线 |
| 处置详单 | 创建、处理、运维单位复核、省中心节点；处理人、开始/结束时间、处置说明、提交状态 | 验证流程完整性和处置闭环 |
| 故障对象 | 故障项、设备编号、品牌型号、设备状态、是否换机 | 确定影响对象和适用规则 |
| 原始监测数据 | 故障前、故障中、故障后 5 分钟及小时数据，保留数值、状态、标记和原始时间戳 | 判断异常、变点、恢复和候选剔除区间 |
| 审核监测数据 | 同范围审核数据及有效性状态 | 防止重复剔除，验证历史人工结果 |
| 现场证据 | 附件元数据、图片/视频/文档内容、拍摄时间和站点水印 | 验证到站、设备状态、维修动作和复测 |

建议默认取数窗口为“候选故障开始前 6 小时至候选恢复后 6 小时”；无明确时间时先取创建前 24 小时至处理完成后 12 小时，再由变点检测缩小范围。

### 4.2 P1：按故障类型强制取数

| 故障类型 | 必需补充证据 |
| --- | --- |
| 自动质控/校准异常 | 质控任务历史、任务状态、运行日志、监测曲线、失败步骤、复做任务及结果、标气/零气/校准仪告警 |
| 监测数据异常 | 同污染物邻近站/同城站数据、本站关联指标、原始标记、设备参数、告警和历史基线 |
| 数据传输/平台离线 | 设备本地数据是否存在、通信/网络/平台告警、恢复/补传记录、离线期间其他因子是否同步缺失 |
| 仪器硬件故障 | 设备告警、维修前后参数、备件/换机记录、恢复后的零跨/精度或流量检查 |
| 站房环境/供电/采样系统 | 温湿度、电压电流、采样总管温湿度/流量、泵状态、烟感/水浸，多污染物同步性 |

### 4.3 P2：用于提高置信度

- 同设备最近 30/90 天故障历史和重复故障次数；
- 同型号设备的正常参数范围和常见故障知识；
- 运维单位、站点和故障类型的历史审核修改率；
- 气象条件和污染过程信息；
- 人工最终审核意见及最终实际无效数据区间；
- 后续 6–24 小时是否再次异常或工单复开。

P2 数据只能用于校准和风险路由，不得因某站点或运维单位的历史表现直接推断当前工单违规。

## 5. 输出契约

每张工单必须生成结构化、可追溯、可重复计算的审核结果。禁止只输出一段自然语言。

  "fault_class": {
    "primary": "monitoring_data_anomaly",
    "secondary": ["condensation", "nox_analyzer"],

## 6. 审核逻辑

### 6.1 总体流程

```text
发现省中心待审工单
  → 精确拉取详单和附件
  → 规则分类故障类型
  → 按类型编排监测/QC/告警/动环证据
  → P0/P1 完整性门禁
  → 确定性规则检查
  → 时间序列与邻站对比
  → 多模态附件核验
  → LLM 仅做语义一致性与解释
  → 独立生成工单结论和数据处置结论
  → 风险路由
  → 人工确认或受控自动审核
  → 记录平台回执和后续恢复结果
```

### 6.2 工单通过规则

满足以下条件才可建议 `approve`：

1. 工单号、站点、设备和污染物可唯一定位；
2. 创建、故障处理、运维单位复核流程完整且时间顺序合理；
3. 现象、原因、处置、恢复四部分至少能从正文、流程或附件中交叉还原；
4. 处置动作与故障原因相匹配；
5. 有恢复验证，且恢复数据没有立即复发；
6. 数据影响范围已明确，或明确证明不影响监测数据；
7. 文本、时间序列、告警、质控和附件之间不存在关键冲突。

以下任一条件应 `reject` 或退回补充：

- 站点、设备或工单号不一致；
- 仅写“已处理/正常”而无原因、动作或恢复证据；
- 处理时间早于故障/创建时间，或附件时间明显不在现场处置窗口；
- 声称恢复但处置后数据、告警或质控仍异常；
- 声称需要剔除数据但没有污染物、起止时间或故障因果证据；
- 将通信离线直接写成“删除数据”，没有先判断补传和原始数据可用性；
- 附件站点、设备、时间或读数与工单不符；
- 详单、关键数据或上游接口缺失。

### 6.3 数据剔除判断

先生成候选影响区间，再判断是否剔除；不能从工单创建时间直接推导剔除区间。

候选边界来源按优先级排序：

1. 设备告警/状态变化、质控任务开始结束、通信中断恢复等系统时间；
2. 原始 5 分钟数据的显著变点、恒值、零值、负值、断点和恢复点；
3. 现场维修开始结束、换件、重启、校准和复测时间；
4. 工单正文中抽取的时间；
5. 工单创建/处理时间只作为兜底外边界。

数据处置矩阵：

| 场景 | 默认结论 | 必须验证 |
| --- | --- | --- |
| 仪器故障导致数值偏高/偏低/恒值/零值 | `partial_exclude` 候选 | 故障因果、邻站不同步、原始标记、恢复验证、精确污染物和区间 |
| 区域污染导致本站与邻站同步变化 | `keep` | 邻站/同城同步性、气象/污染过程、仪器参数正常 |
| 自动质控注入或校准过程 | `partial_exclude` 或按平台既有质控标记处理 | 任务日志、任务起止、目标浓度、复测结果，防止扩大到非质控时段 |
| 平台/网络离线但仪器本地数据可补传 | `missing_no_delete`，等待补传 | 本地缓存、补传结果、时间戳连续性 |
| 仪器断电/采样泵停止且无有效测量 | `missing_no_delete` 或 `partial_exclude` | 原始值是否已经缺失；若存在伪值，再剔除伪值区间 |
| 站房供电/采样总管故障 | 多污染物 `partial_exclude` 候选 | 多因子同步异常、动环和采样参数、恢复时间 |
| 仅有“数据带标记”文字 | `needs_evidence` | 标记码含义、原始值、审核状态、设备和告警证据 |
| 无法证明环境真值还是仪器故障 | `needs_evidence` | 不允许用模型置信度强行二选一 |

自动剔除的硬条件：

- 影响对象精确到站点、污染物和时间区间；
- 至少两类独立证据支持仪器/系统故障，其中至少一类来自系统数据而非人工文字；
- 邻站或同城对比未发现足以解释该异常的真实污染过程；
- 候选区间前后有恢复或稳定证据；
- 原始与审核数据状态可读取，未发生重复审核；
- 无关键冲突、无 P0/P1 缺失；
- 规则版本、数据快照和证据引用全部落审计日志。

若只满足部分条件，AI 可以给出区间建议，但 `route` 必须是 `human_confirm`。

### 6.4 LLM 与确定性逻辑的边界

确定性代码负责：

- 状态、枚举、字段完整性、时间顺序和流程节点；
- 数据拉取范围、原始/审核口径和记录覆盖率；
- 时间序列变点、缺失率、恒值、零/负值、邻站相关性；
- 质控任务、告警、设备和附件身份匹配；
- 输出 schema、幂等键、路由门禁和回写权限。

LLM 负责：

- 从自由文本提取故障现象、原因、处置、恢复和候选时间；
- 判断说明是否与当前证据相关、充分且无矛盾；
- 对图片中的现场动作、设备面板和水印进行语义解释；
- 生成面向审核人的简短理由。

LLM 不负责直接修改监测数据、不独立决定时间区间、不绕过证据门禁，也不在缺失数据时用常识补齐事实。

## 9. 灰度路径与验收指标

### 阶段 A：影子审核

- 对所有省中心待审工单生成 AI 结果，但不展示正式操作、不回写平台；
- 将 AI 结果与人工省中心最终结论、最终无效数据区间对齐；
- 至少运行 2–4 周，覆盖主要故障类型、设备品牌和 13 个设区市。

### 阶段 B：辅助审核

- 页面展示 AI 建议，人工一键接受、修改或退回；
- 所有数据剔除必须人工确认；
- 对证据缺失、接口失败和冲突样本强制转人工。

### 阶段 C：受限自动审核

- 先开放“工单材料完整且明确不涉及数据剔除”的低风险自动通过；
- 再按故障类型逐项开放经过回放验证的确定性规则；
- 数据剔除仍使用单独开关和更高门槛，不随工单自动通过一起开放。

核心指标：

| 指标 | 说明 |
| --- | --- |
| 工单结论准确率 | AI 通过/退回/补证与人工最终结论一致率 |
| 数据处置 precision/recall | 以“站点 + 污染物 + 时间粒度”比较 AI 与人工最终无效区间 |
| 区间边界误差 | AI 起止时间与最终起止时间的分钟/小时偏差 |
| 误剔除率 | AI 建议剔除但人工最终保留的有效数据比例，必须作为最高优先级风险指标 |
| 漏剔除率 | 人工最终剔除但 AI 未识别的区间比例 |
| 人工修改率 | 按故障类型统计 AI 结论和区间被修改的比例 |
| 证据闭环率 | 能关联清单、详单、监测数据、附件、人工结论和平台回执的事项比例 |
| 自动审核节省时长 | 每单人工耗时和整体积压下降情况 |
| 复开/追溯异常率 | 自动审核后工单复开、数据追溯或申诉比例 |

上线门槛不应只看总体准确率。任何故障类型样本不足、误剔除率不可接受、来源覆盖不完整或平台回写无幂等保护，都不得进入自动审核。
