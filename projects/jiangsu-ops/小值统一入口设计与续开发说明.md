# “小值”统一入口设计与续开发说明

> 项目：江苏省运维审核管理服务平台  
> 分支：`project/jiangsu-ops`  
> 文档用途：产品设计基线、当前实现说明及后续开发交接  
> 更新日期：2026 年 8 月 16 日

## 1. 一句话定义

江苏智能运维平台不再以“7 个智能体供用户选择”为首页核心，而以“小值”作为统一的智能值班入口：用户先表达目标，小值理解任务、组织专业能力、汇总全局态势并跟踪业务闭环；只有进入具体业务手工操作时，才切换到专业智能体工作区。

## 2. 背景与问题

原有运维管理平台已经提供了大量页面、菜单、工具和操作流程。智能体平台如果继续复制传统后台的页面层级，或只把 7 个智能体做成新的功能菜单，会产生三个问题：

1. 用户仍需先理解系统能力，再决定进入哪个工具，智能化价值有限。
2. 数据、告警、人员、工单和诊断分散在不同页面，缺少全局态势与统一闭环。
3. 对话与页面割裂，对话得到的判断不能自然转成待办、审核、处置和复查。

因此，本项目的目标不是再造一套更重的运维后台，而是在既有业务系统之上增加一层轻量、主动、面向目标的智能交互层。

## 3. 已确认的设计理念

### 3.1 从“选工具”转向“说目标”

首页首先提供自然语言入口。用户可以直接提出“生成今天的运维态势”“找出当前最值得关注的站点”“分析人员覆盖情况”等目标，不必先判断应该使用哪个智能体。

### 3.2 “小值”是统一入口，专业智能体是能力层

“小值”代表全局值班与统筹角色，不是第 8 个孤立智能体。它负责：

- 理解用户目标、对象、时间范围和业务口径。
- 调用或转交给合适的专业智能体。
- 汇总不同能力的结果，形成面向管理者的判断。
- 把异常、证据、建议、任务和复查状态组织成闭环。
- 在需要具体手工操作时，带着上下文进入专业工作区。

7 个专业智能体继续保留，但弱化为二级入口：

| 专业能力 | 主要职责 |
| --- | --- |
| 运维智能体 `ops` | 工单审核、规则筛查、证据复核、报告生成 |
| 江苏问数生图 `jiangsu_query` | 监测及气象数据查询、统计分析、图表生成 |
| 专家分析 `expert` | 污染过程、来源与传输等综合研判 |
| 智能巡检 `smart_inspection` | 全网异常概览、站点巡检与告警排查 |
| 运维操作分析 `operations_analysis` | 人员到站、覆盖、调度线索分析 |
| 设备反控 `device_control` | 授权设备状态查询及受控操作 |
| 站点故障诊断 `station_fault_diagnosis` | 断数、恒值、告警、质控等故障取证与诊断 |

### 3.3 首页不是固定大屏，而是可生成的工作台

首页需要同时支持两种形态：

- 稳定底座：固定呈现统一输入、重点关注、运行状态和专业能力入口。
- 按需工作台：根据用户问题动态生成指标、站点列表、趋势图、地图、人员调度、工单进度和简报等内容。

动态页面不能让模型直接输出任意 HTML。正确方向是由模型或编排服务输出受控的结构化工作台描述，再由前端白名单组件渲染。每个数据块必须带数据口径、更新时间和来源，避免生成“看起来合理但无法追溯”的大屏。

### 3.4 从被动问答转向事件驱动

小值首页不仅等待用户提问，还应持续接收后台巡检、告警和定时任务产生的事件，将它们转成“重点关注事项”。用户看到的是已经整理过的业务对象，而不是原始告警流。

### 3.5 AI 给建议，人对关键动作负责

自动化边界保持明确：AI 可以取证、归纳、诊断、给出处置建议和生成工单草案；人工负责规则审核、责任认定、派单确认、设备控制和最终关闭。所有结论都要保留证据、不确定性和操作记录。

### 3.6 渐进式替换演示数据

当前阶段优先证明架构和场景，不提前固化尚未明确的业务规则。真实接口、指标口径和闭环规则成熟一个接入一个，页面结构和交互主线保持稳定。

## 4. 目标交互架构

```text
用户
  |
  v
小值首页（统一入口、全局态势、重点关注）
  |
  +-- 自然语言目标 --> 意图识别 / 任务规划 / 上下文补全
  |                         |
  |                         +--> 专业智能体与工具能力
  |                         +--> 定时任务与事件执行
  |                         +--> 数据、知识库和业务系统
  |
  +-- 关注事项操作 --> 补充取证 / 深入诊断 / 审核 / 处置 / 复查
  |
  +-- 手工专业操作 --> 带上下文进入具体智能体工作区
  |
  v
结构化结果、证据、产物和状态回流首页，持续跟踪到闭环
```

小值不应复制各智能体的完整界面。首页只保留完成全局统筹所需的信息，专业操作继续复用现有对话、资源、任务和管理面板。

## 5. 首页信息与交互设计

### 5.1 当前首页骨架

1. 小值身份区：角色、在线状态和“专业工作区”入口。
2. 统一命令区：自然语言输入和高频快捷任务。
3. 态势摘要：关注事项、高优先级、待人工审核、小值处理中等状态。
4. 重点关注区：展示事件、初判、置信度、证据和下一步动作。
5. 工作台区：展示简报、指标、活动过程等结构化内容。
6. 专业能力目录：需要手工操作时显式进入某个专业智能体。

### 5.2 推荐的主流程

#### 全局态势查询

用户提出目标，小值先确认必要口径，再组织查询与分析。结果优先在首页生成新的工作台视图；需要深入分析或产生大量成果时，再进入对应专业会话。

#### 重点事项处置

用户从关注卡片发起“补充取证”“深入诊断”或“开始审核”。系统应携带站点、事件、时间和已有证据进入专业流程，完成后把摘要、产物和状态回写到原事项。

#### 手工专业操作

用户主动打开“专业工作区”并选择智能体。这个路径适合规则配置、批量审核、复杂数据查询和设备控制等明确操作，不应成为普通用户的默认起点。

### 5.3 目标闭环状态

```text
新发现 -> 小值分析中 -> 待人工审核 -> 处理中 -> 等待复查 -> 已闭环
                 \-> 需要处理（失败、超时或证据不足）
```

状态变化必须来自真实任务或人工动作，不能只在前端临时修改。

## 6. 当前已经实现的内容

### 6.1 配置驱动的协调首页

江苏项目在 `projects/jiangsu-ops/project.yaml` 中配置：

- `agent_platform_layout: coordinator`，启用统一协调首页。
- 小值名称、角色、欢迎语、输入提示和默认模式。
- 4 个快捷任务和关键词到专业智能体的路由。
- 简报、指标、闭环示意等工作台区块。
- 3 条明确标注“场景演示”的关注事项。
- 需要纳入首页关注区的后台任务 ID。

共享项目仍默认使用原智能体门户布局，不受江苏配置影响。

### 6.2 前端首页与导航

- `frontend/src/components/coordinator/CoordinatorHome.vue`：小值首页视图、关注卡片、工作台和专业能力入口。
- `frontend/src/components/coordinator/coordinatorWorkspace.js`：路由、区块和关注事项的标准化逻辑。
- `frontend/src/components/agentPlatform/AgentPlatform.vue`：根据项目配置切换协调首页或原平台布局。
- `frontend/src/components/reactAnalysis/MainLayout.vue`、`frontend/src/views/ReactAnalysisView.vue`：把首页请求转入对应智能体会话。
- `frontend/src/components/AssistantSidebar.vue`：江苏左侧主入口显示为“小值首页”；从会话返回首页时回到根路由。

登录后访问根路径 `/` 即进入小值首页。江苏部署端口为 `5175`。

### 6.3 当前数据来源

首页关注事项由两类数据合并：

1. 实时执行记录：读取近期定时任务执行，只接收 `attention_task_ids` 白名单中的任务。目前配置为 `jiangsu_station_fault_diagnosis`。
2. 演示事项：真实事件不足时由项目配置提供，并在标题和描述中明确标注场景演示。

实时执行会被转换为统一的关注事项结构；运行中显示为“小值分析中”，成功完成显示为“待人工审核”，失败、超时或取消显示为“需要处理”。

### 6.4 已支持的数据契约

工作台区块当前支持：

| 类型 | 用途 |
| --- | --- |
| `metric-grid` | 指标网格 |
| `briefing` | 值班简报 |
| `attention-list` | 关注事项列表 |
| `activity` | 活动或闭环过程 |

关注事项主要字段为：`id`、`title`、`summary`、`severity`、`status`、`station`、`occurred_at`、`diagnosis`、`confidence`、`evidence`、`actions`。动作支持 `ask`、`open-agent` 和 `open-task`。

### 6.5 已完成验证

- 项目清单和前端配置测试通过。
- 智能体平台集成测试通过。
- 协调首页路由及数据标准化测试通过。
- 江苏后端项目配置测试通过。
- 江苏 standalone 前端构建通过。
- 5175 Nginx 已挂载 `frontend/dist`，实际返回的 bundle 包含“小值”和 `coordinator` 布局。

## 7. 当前明确未完成的内容

以下能力仍是后续目标，不能把当前演示误认为已经具备：

1. 自然语言目前通过关键词选择专业模式，还不是具备规划、澄清和多智能体编排能力的小值后端。
2. 首页工作台区块目前来自静态项目配置；自然语言请求会进入专业会话，尚不能直接重组首页大屏。
3. 指标中的 `--` 是真实接口和业务口径的占位，不应使用模拟数值替换。
4. 关注事项尚未接入统一事件 API，目前只有指定定时任务执行和演示事项。
5. 关注卡片动作可以启动专业会话，但专业会话结果尚未自动回写原事项。
6. 派单、审核、处置、复查和关闭尚未形成统一持久化状态机。
7. 人员调度还缺排班、路网、技能、区域责任和实时可用性等数据，不可仅凭签到推导调度结论。
8. 设备反控服务尚未开通；即使后续开通，也必须保留权限校验、二次确认、幂等和审计。
9. 当前“小值”形象主要是名称、角色和界面符号，尚未建设完整的品牌视觉、语气规范与状态表达。

## 8. 后续实施路线

### 阶段一：接入真实首页数据

优先建立一个面向首页的聚合接口，统一返回态势摘要、关注事项和更新时间，不让前端分别拼接大量业务接口。先接入已有且口径清晰的数据：站点异常、任务执行、待审核工单和人员到站汇总。

交付标准：演示事项可关闭；每个指标和事项都有来源、时间、口径及详情入口；空数据与接口失败有明确状态。

### 阶段二：实现按需生成工作台

建立受控的 `WorkspaceSpec` 协议。小值根据用户目标生成区块描述，前端按白名单渲染。建议逐步增加 `chart`、`table`、`map`、`station-list`、`personnel-schedule` 等组件，同时限制查询范围、组件数量和数据体量。

交付标准：用户可以生成、修改、刷新和恢复一个工作台；任何展示数据都可追溯；模型不能注入任意页面代码。

### 阶段三：建设小值编排服务

将当前关键词路由升级为后端协调能力，负责意图识别、必要信息澄清、能力选择、任务拆解、并行取证、结果合并和失败降级。专业智能体仍保持各自工具白名单和提示词边界。

交付标准：同一业务目标可以组织多个专业能力，过程可观察、可取消、可恢复，并且不会越权调用工具。

### 阶段四：打通业务闭环

建立统一的关注事项与处置记录，关联事件、会话、任务、证据、资源、人工审核和复查结果。专业工作区处理完成后回流小值首页，形成可审计的状态迁移。

交付标准：每个事项都能回答“怎么发现、用了什么证据、谁确认、执行了什么、如何复查、为何关闭”。

### 阶段五：完善生产质量

补充权限、审计、性能、可观测性、异常恢复、数据新鲜度、移动端适配和真实用户验收。用业务闭环时间、人工操作次数、建议采纳率和误报率评价价值，而不是只统计对话次数。

## 9. 下一轮建议优先任务

下一轮开发建议从“真实首页聚合接口”开始，而不是继续增加静态卡片：

1. 梳理站点异常、待审核工单、人员覆盖和任务执行的真实数据源与业务口径。
2. 定义首页摘要及 `AttentionItem` 后端响应模型和 API。
3. 将 `CoordinatorHome.vue` 的实时数据读取改为调用聚合接口，并保留任务执行适配层。
4. 为加载、局部失败、无权限、数据过期和空结果补齐状态。
5. 用真实数据替换一个演示事项，完成“发现 -> 诊断 -> 人工审核 -> 回流”的最小闭环。

在业务口径尚未确认前，应优先完成接口契约、适配器和状态流，不在前端写死判断规则。

## 10. 工程与部署约束

### 10.1 分支归属

- `frontend/src`、`backend/app` 等共享能力先提交到 `main`。
- `projects/jiangsu-ops/**`、江苏专用工具、测试和配置提交到 `project/jiangsu-ops`。
- 工作顺序：`main` 完成共享改动，江苏分支合并 `main`，再叠加江苏项目改动。

### 10.2 运行与测试

后端使用 conda 环境 `backend_py311`。前端常用验证命令：

```bash
cd frontend
npm run test:project-config
npm run test:agent-platform
node --test src/components/coordinator/coordinatorWorkspace.test.js
PROJECT=jiangsu-ops npm run build:standalone
```

后端项目配置验证：

```bash
conda run -p /root/miniconda3/envs/backend_py311 \
  pytest backend/tests/project_config/test_loader.py -q
```

### 10.3 江苏前端部署

正式前端产物唯一目录为 `frontend/dist`，禁止生成或维护第二套 `dist-*` bundle。江苏服务使用 5175 端口：

```bash
cd frontend
PROJECT=jiangsu-ops npm run build:standalone

cd ..
grep -R "resources?presentation_type=document" frontend/dist/assets
! grep -R "/office-documents" frontend/dist/assets
! grep -R "/visualizations" frontend/dist/assets

docker compose -p suyuan-nginx-jiangsu \
  -f deploy/nginx/docker-compose.jiangsu-ops.yml up -d --force-recreate
```

部署后检查：

```bash
curl -fsS http://127.0.0.1:5175/
docker inspect suyuan-nginx-jiangsu \
  --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}'
```

需要在同一服务器并行部署不同项目时，应使用独立工作树或部署目录，每个目录仍只维护自己的 `frontend/dist`。
