# 江苏分支反馈循环试点设计与实施说明

> 目标：把 Agent 的质量反馈嵌入原有业务流，以业务结果而不是用户主动评分作为主要迭代依据。
>
> 当前试点：站点故障诊断、运维工单审核。

## 1. 设计原则

江苏分支不要求操作人员额外填写“好用/不好用”。系统自动关联以下业务对象：

```text
告警/工单/审核数据
  → Agent 建议（带证据和版本）
  → 人工确认、修改或驳回
  → 原业务系统动作
  → 后续业务结果和复查
  → 事项标签与评估指标
  → 规则、工具、提示词和模型迭代
```

用户文字反馈仍可保留，但只用于解释原因，不作为主要准确率指标。

## 2. 统一事项和事件流

后端服务位于 `backend/app/services/jiangsu_feedback_loop.py`，使用项目共享的
`DATA_REGISTRY` 保存追加式事件日志：

```text
backend_data_registry/jiangsu_feedback_loop/events.jsonl
```

每个事项使用稳定的 `case_id`，事件包括：

- `case_created`：业务事项首次出现；
- `agent_recommendation`：Agent 生成诊断、问题清单或建议；
- `human_review`：人工接受、修改、驳回或要求补证；
- `business_action`：创建工单、正式审核或其他业务动作的结果；
- `verification`：现场、平台或数据恢复结果。

事项状态为：

```text
new → analyzing → awaiting_review → processing
                                  → awaiting_verification
                                  → closed / reopened / needs_followup
```

每次状态变化由后端事件产生，不能由前端临时改写。Agent 的重跑会追加新事件，不覆盖旧版本。

## 3. 当前两个试点

### 3.1 站点故障诊断

已接入以下节点：

1. `jiangsu_prepare_fault_work_order` 生成草案时，自动创建 `station_fault_diagnosis` 事项并记录证据引用、站点、设备、故障现象和验证标准。
2. 操作人员确认草案时，自动记录 `accepted` 或 `modified`，并保存修改字段。
3. 运维平台创建成功或失败时，自动记录 `business_action`。
4. 现场或数据复查完成后，通过验证接口写入 `verification`，形成关闭或重新打开结果。

对应接口：

```text
POST /api/jiangsu/work-order-drafts/{draft_id}/verification
GET  /api/jiangsu/work-order-drafts/feedback/cases?scenario=station_fault_diagnosis
GET  /api/jiangsu/work-order-drafts/feedback/metrics?scenario=station_fault_diagnosis
```

复查请求示例：

```json
{
  "outcome": "resolved",
  "source_record_id": "WO-20260822-001",
  "details": {
    "root_cause_confirmed": "通信模块掉线",
    "recovery_at": "2026-08-22T14:30:00+08:00",
    "recurred": false
  }
}
```

首批指标：

- 草案人工采纳率、修改率、驳回率；
- 工单创建成功率；
- 复查通过率；
- 首次处理闭环率；
- 重新打开率；
- 发现到关闭的中位时长。

### 3.2 运维工单审核

`ops_audit_run_rules` 生成 `final_issue_list` 时，自动创建
`ops_work_order_audit` 事项，并保存稳定的问题项 ID。人工完成最终问题清单复核后，调用：

```text
POST /api/jiangsu/work-order-drafts/feedback/cases/{case_id}/review
GET  /api/jiangsu/work-order-drafts/feedback/metrics?scenario=ops_work_order_audit
```

复核请求的 `payload` 至少包含：

```json
{
  "ai_item_ids": ["WO-1|RF_REQUIRED|备注|..."],
  "final_item_ids": ["WO-1|RF_REQUIRED|备注|...", "WO-2|RF_RANGE|流量|..."]
}
```

服务自动计算：

- 问题项 precision；
- 问题项 recall；
- F1；
- 人工接受/修改/驳回比例。

当样本量达到最低门槛且指标明显偏低时，`metrics` 响应还会返回
`optimization_actions`，提示应优先检查证据、规则或处置方案；这些建议只进入校准评审，不会自动修改线上 Agent。

最终问题清单仍以现有审核技能和人工复核协议为准，反馈服务不改变正式报告口径。

## 4. 其他模式的接入契约

统一服务先覆盖高风险、结果可验证的模式，其他模式按以下业务结果接入：

| 模式 | 业务结果来源 | 主要评估指标 |
| --- | --- | --- |
| 江苏问数生图 | 原始查询重放、口径修正、正式导出物 | 数值正确率、数据新鲜度、重算率 |
| 知识问答 | 后续规程审核、知识库版本修订 | 引用准确率、正确拒答率、过期答案率 |
| 专家分析 | 正式研判、后续监测过程、专家复核 | 证据支撑率、专家一致率、过度确定性率 |
| 智能巡检 | 实际巡检记录、现场确认、有效工单 | 可行动异常率、现场确认率、重复告警率 |
| 运维操作分析 | 排班/调度变化、覆盖和跨市结果 | 核查确认率、覆盖改善、误导性线索率 |
| 设备反控 | 指令回执、操作后状态、回退记录 | 状态一致率、失败率、异常回退率 |

没有可关联的业务结果之前，不把该模式的“满意度”当作正式质量指标。

## 5. 迭代和发布流程

每周从事件日志和原业务系统生成评估样本，按问题归因：

1. 数据源、覆盖率、新鲜度或站点映射问题；
2. 规则阈值、去重或业务口径问题；
3. 工具参数、接口或编排问题；
4. 提示词、证据组织或不确定性表达问题；
5. 模型推理或格式稳定性问题。

变更不得直接在线自动生效。每次变更记录模型、提示词、工具、规则和数据快照版本，先做固定样本回放，再小范围灰度，最后根据指标决定发布或回滚。

## 6. 试点评估门槛

第一阶段只要求“闭环数据完整”，不提前设定脱离基线的绝对目标：

- 至少 90% 的试点事项能关联来源、Agent 产物、人工决策和业务结果；
- 关键状态变化有可审计事件；
- 站点故障事项能区分关闭、复开、误报和证据不足；
- 工单审核事项能拿到人工最终问题清单；
- 每周能输出按场景分组的评估指标和待迭代问题清单。

完成两到四周基线采集后，再按场景设定准确率、闭环时长、误报率和人工修改率的改进目标。
