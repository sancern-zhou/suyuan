# 例行运维工单审核报告输出规范

生成正式审核报告、QMD 报告或报告包前，完整读取并执行本规范。本规范与共享版运维工单审核报告口径一致：正文只有两个章节，证据写入明细行，不设统计章节。

## 唯一数据口径

- 问题明细只使用本轮 `jiangsu_ops_audit_run_rules` 返回的 `report_input_path` 指向的条目（`items`）。
- `summary.report_ready=false`（存在 `pending_semantic_reviews` 或 `pending_review_items`）时不得生成正式报告，先交付待核验清单，并说明未复核条数与原因。
- 被排除项（`enable_semantic=false` 时未复核的候选、`FORM_UNMAPPED` 未纳入审核的检查项）不得写成确定问题。
- 不得使用语义候选、抽样结果、旧报告或历史输出补充问题。
- 报告可以整理、分组和改写已有问题，但不得重新判断、发现或新增问题。
- 规则命中与语义复核结论都是审核线索；涉及违规认定、责任归属、数据剔除的结论必须标注待人工确认。

## 目标读者与表达方式

- 报告面向环境管理人员、运维管理人员和站点负责人，不面向开发人员或审核规则维护人员。
- 使用中文业务名称和完整句子，读者无需了解表名、字段列名（如 stringN/bool_N）或审核实现细节即可理解问题。
- 每条问题回答三个问题：哪里有问题、检查项/表单要求是什么、需要核对什么。
- 原始字段列名（`string3`、`bool_6`、`detailId` 等）、规则 ID 只作为必要定位信息附带展示，不作为问题主体；机器证据只保留在 `evidence`，不要直接复制到正文。

## 报告结构

除报告标题外，正文仅包含以下两个章节，顺序固定：

```markdown
# 江苏例行运维工单审核报告

## 审核范围

## 问题工单明细
```

“审核范围”简要列明数据来源（江苏运维平台接口）、工单类型、筛选时间字段、时间范围、节点/工单状态、其他实际筛选条件和纳入审核的工单数量。

不输出数据覆盖情况、总体结论、审核规则与口径、证据摘要、独立统计汇总、整改建议或附录。核查所需证据直接写入对应问题明细，不另设章节。不得把未验证候选写成确定结论。

没有保留问题时，在“问题工单明细”中写明“本次审核未发现需保留的问题工单”，不增加总结章节。

## 问题明细分组

- 必须按 `operation_unit_name` 运维单位分组，每个单位单独列表。
- 运维单位缺失时归入“未关联运维单位”。
- 每个 `report_input.items` 条目单独占一行；不得把同一检查项的多个 `source_issue_ids` 拆成多行。
- `summary.report_issue_count` 是合并后的问题数量；`summary.retained_count` 等复核计数是规则命中项数量，不能称为独立问题数量。
- 必须完整列出所有保留问题，不按固定条数截断，不询问是否继续，不使用“另有 N 条略”“待补查”“需通过工具补全”等占位表达。

每个分组使用以下列名和顺序：

| 站点 | 检查表单 | 工单号 | 问题描述 | 原始备注/说明 | 命中规则 |
|---|---|---|---|---|---|

字段来源：

- `站点`：使用 `station_name`；缺失时明确标记“站点缺失”，不猜测。
- `检查表单`：使用 `rf_form_name`（平台检查项中文名）；不得向用户展示内部 `rule_item_tag`。
- `工单号`：使用完整 `working_order_code`。
- `问题描述`：优先使用本条 `display_evidence` 组织为面向用户的可核查事实；`evidence` 仅用于必要时核对原始值，不得逐项展开其中的机器字段。数值问题统一写成“字段名：实际值 X，参考范围 Y，超出/低于方向”，不得输出 `stringN`、`actual_column` 等内部键名。异常事实、说明审核结论与语义复核结论写在同一行。
- `原始备注/说明`：使用 `remark_context.entries` 中与当前异常相关的字段及原文，格式为“字段显示名：备注原文”；空值写“未填写”，多条用 `<br>` 分隔。`remark_context.status_label` 为 `provided` 表示已填写（不等于说明合理）；`missing` 表示应填未填；`unavailable` 表示该表单无备注字段、备注信息未取得；只有明确的 `not_applicable` 才表示不适用。禁止因元数据缺失写“未涉及备注审核”。不得只把备注藏在 `evidence` JSON 中。
- `命中规则`：完整列出 `rule_ids`，不得只展示代表条目的 `rule_id`。
- 语义复核结论不单设章节：`semantic_note` 的理由并入“问题描述”同一行（如“语义复核：……”），`severity` 已按语义结论降级的条目需保留“语义复核”标注，便于读者理解严重度变化。

## 问题描述约束

- 引用具体字段名和值，使读者可以直接对照原始表单。
- 日期问题列出相关日期及其先后关系；数值问题列出实际值、参考范围及偏差方向。
- 缺失问题列出缺失字段或附件类型及其所在检查项。
- 不使用“时间异常”“数值不合理”等无法核验的笼统描述。
- 行式检查项问题必须同时列出结论值、实际值和参考范围（来自 `display_evidence`），避免只展示处理后的值。
- `TASK_DEVICE_INCOMPLETE` 必须逐项列出已填写与缺失的设备信息（品牌/型号/编号），便于判断是漏填还是表单本就不要求。
- 依赖语义复核的规则（`TASK_FIELD_MISSING`、`TASK_VALUE_OUT_OF_RANGE`、`TASK_ABNORMAL_NO_REMARK`、`TASK_DEVICE_INCOMPLETE`）必须在同一行展示原始备注/说明与语义复核结论，便于用户直接判断。

## 问题描述示例

推荐写法：

```text
多气体动态校准仪校准检查记录：检查项已完成，设备品牌、设备编号未填写（已填写设备型号）。需运维单位补充设备台账信息。
```

```text
氮氧化物分析仪运行状况检查记录“满量程的80%”：检查项标注完成，但完成时间为空。语义复核：该表单日期字段已承载检查日期，时分字段未填不构成缺失，建议人工确认。
```

```text
QC分析仪器状态检查表“反应室基座温度”：实际值 40.7℃，参考范围 45~55℃，实际值低于范围下限。异常处理记录：未填写。语义复核：备注仅记录填报操作，未说明偏离原因或复测处置。
```

不推荐写法：

```text
string1=41.6；bool_2=True；reference_limit=(45~55℃)；status=mismatch
```

```text
问题：记录不完整。证据：见 JSON。
```

不推荐写法的问题在于：只展示程序状态和内部列名，没有告诉环境管理人员具体哪个检查项、哪个业务信息缺失或偏离，也没有给出可直接核对的表单值。

## 生成与验收

1. 必要时读取同轮 `dataset_path` 补充审核范围，但不改变问题明细。
2. 组织完整 `report.qmd`，调用 `create_report_package` 生成报告包。
3. 检查正文只有“审核范围”和“问题工单明细”两个章节；明细行数等于 `summary.report_issue_count`，每个 `source_issue_ids` 只属于一行；不额外生成统计图表。
4. 调用 `render_report_package` 渲染所需格式（HTML/Word）。
5. 调用 `validate_report_package` 验收 QMD、图片引用和 HTML 预览；失败时修复后重新验收。
6. `publish_report` 发布后交付：说明右侧面板可预览并下载 QMD 或 Word，不把本地绝对路径作为主要交付内容，不手工拼接下载链接。
