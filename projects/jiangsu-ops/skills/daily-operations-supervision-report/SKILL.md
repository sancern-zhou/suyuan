# 日常运维监管月度报告

## 适用场景

- 用户提出"本月/上月全省日常运维情况""人员到站与覆盖""故障处置时效""工单超期/重复故障""告警积压""站点数据获取率/有效率""质控合格率""巡检完成率""考核指标异常站点""日常监管报告"等需求时使用。
- 目标是回答：基础运维工作是否落实到位、哪些站点/单位/人员指标异常、需要省站介入什么。
- 不适用：重污染窗口期/飞行检查类风险线索（使用 `operations-risk-prevention-report`）、单点故障诊断、工单审核。

## 报告面向普通环境业务管理用户（强制）

报告的读者是负责运维统筹、绩效考核和资源安排的**环境业务管理用户**，不是技术人员：

- 正文只讲业务事实、管理指标、问题清单、管理建议，用日常业务语言（如"本月到站记录缺失的站点""处理超过 72 小时的工单"）。
- 严禁出现接口名、字段名、表名、SQL、脚本、文件路径等技术语言；技术过程留在内部执行。
- 统计口径用业务语言说明；取数清单、逐站明细只放附录。

## 工作原则

通用原则：

1. **不编数字**：所有数字来自真实取数或基于取数的确定性统计；可用 `execute_python` 复算，不心算。
2. **数据和结论必须可回溯**：每个结论能回到具体站点、人员、时间和记录；原始数据先留存本地，不做二手转述。
3. **区分事实与判断**：确定问题与待核查线索分开表述（见「结论边界」）；结论按「事实 / 推断 / 建议」三种强度表述。
4. **量化优先**：优先用数字说话，避免"较多、明显、严重"等模糊词；确实无法量化时说明原因。
5. **先结论后论证**：金字塔结构——先给核心指标总览与结论，再逐链路展开论点与数据佐证。

报告特有原则：

6. **如实披露**：数据缺失、结果为空必须说明业务影响，禁止把空结果表述为"无异常"；未接入的数据在"数据盲区"列明，不得推测补造。

## 标准工作流程（九步方法论）

按 Define → Frame → Collect → Validate → Analyze → Synthesize → Compose → Review → Deliver 推进。**流程可按需裁剪**：快问快答类需求只需第 2、5 步（拆解问题 + 分析给数）；正式报告走全程。各步是并行/迭代关系而非严格瀑布——分析中发现口径、边界或数据问题，回到第 1 步重新定义后再继续。

1. **明确任务边界（Define）**：报告给谁看、要回答什么问题、支撑什么决策（如绩效考核、资源安排）、口径与范围（统计周期、站点范围）、交付格式（Word/PPT/HTML/Excel）、截止时间。不确定的地方先给假设并在报告中标注。
2. **拆解问题结构（Frame）**：把大问题拆成可验证的子问题，搭出报告骨架（金字塔：结论先行、论点支撑、数据佐证）；确定所需指标体系与计算口径（对照「口径速查」与统计阈值建议）。
3. **数据获取（Collect）**：本地数据优先——统计、趋势、排名类问题按「数据能力地图」查宽表；平台统计口径（两率/排名/浓度）优先 `jiangsu_query_statistics`，不要拉明细自算；单据明细与实时状态走平台接口。其次联网检索（WebSearch/WebFetch）与连接器（Agent Mail、腾讯文档、资料库）；必要时调用专业数据源。原始数据落地保存，不做二手转述。
4. **校验与清洗（Validate）**：检查缺失值、异常值、口径一致性、时间对齐、单位统一；关键数字交叉验证（至少两个来源或两种算法，如 SQL 聚合与 `execute_python` 复算互核；本地统计与平台统计口径冲突时以平台为准并说明）。这一步经常决定报告可信度。
5. **分析（Analyze）**：描述性统计 → 对比/趋势/结构/归因 → 必要时建模或量化估算（敏感性分析、区间估计）。用 Python/SQL 实际算，不靠感觉给数。
6. **提炼结论（Synthesize）**：从数据到洞察到建议。每个结论必须有数据支撑并标注出处；区分「事实 / 推断 / 建议」三种强度（对应确定问题 / 待核查线索 / 管理建议）。
7. **成稿与可视化（Compose）**：先写结构再写文字；图表服务于论点（不是堆图），每图配一句管理解读；文字量化、避免模糊词；按「报告结构」组织成稿，面向业务管理用户的语言要求（严禁技术语言）不变。
8. **质检（Review）**：自检清单——数字前后一致、单位一致、图表和正文对得上、结论能回答最初的问题、无未标注的假设、无遗留下一步的 TODO；确定问题与待核查线索未混级；空结果未表述为"无异常"。
9. **交付（Deliver）**：输出到指定格式与路径，附上数据来源与口径说明、关键假设、局限性（含数据盲区）；需要的话同时给出可复用的取数/统计脚本或表格。

## 数据能力地图（按需取用）

**本地历史数据集** `execute_jiangsu_mart_sql`（只读 SELECT 带 LIMIT；自 2026-07-01 起；返回带数据截至时间）——**跨单统计、趋势、排名类问题的首选**，秒级聚合：

| 链路 | 数据集 | 一行含义 / 关键内容 |
| --- | --- | --- |
| 工单 | `mart_work_order_analysis` | 一张工单：状态/城市/响应时长/超期/30天重复故障 |
| 告警 | `mart_alarm_event_analysis` | 一条告警：级别/状态/持续时长/24h关联工单 |
| 站点 | `mart_station_device_health` | 一个站点：近30天工单/超期率/告警/风险分级（当前态势首选） |
| 趋势 | `mart_station_daily_profile` | 站点×日：工单与告警计数，趋势对比 |
| 质控 | `mart_qc_execution_analysis` | 一条质控结果：合格判定（约23个试点站） |
| 质控安排 | `mart_qc_arrangement_analysis` | 一条安排任务：完成状态/过期未完成 |
| 巡检 | `mart_inspection_analysis` | 一条巡检任务项：周期类型/完成/超期/转工单 |
| 考核 | `mart_performance_analysis` | 站点×月：两率+评分（**窗口内无实际填报，查询基本为空**） |
| 停电 | `mart_blackout_analysis` | 一张停电报备单（仅65行） |
| 维度 | `dim_station` / `dim_device` | 站点名录与城市归属 / 设备台账（无备机与生命周期字段） |

质控的历史结果、任务状态与合格统计统一查上面两张质控宽表（原平台质控接口 `jiangsu_fetch_qc_task_history`、`jiangsu_fetch_qc_task_status` 已被其替代，不再列入）；单站运行日志/监测曲线取证在故障诊断模式下查询。

**平台接口**（实时状态与单据明细）：

- 到站签到 `jiangsu_fetch_attendance_records`；工单清单与明细 `jiangsu_fetch_fault_work_orders`、`jiangsu_fetch_fault_work_order_detail`；到站轨迹 `jiangsu_analyze_work_order_tracks`
- 获取率/有效率/接收率等**平台统计口径** `jiangsu_query_statistics`（此类问题必须优先用它，不要拉明细自算）；站点数据 `jiangsu_fetch_station_data`
- 站房告警与动环/供电历史 `jiangsu_fetch_station_alarm_logs`、`jiangsu_fetch_station_environment_history`（先定位异常站点与时段，再按最小窗口取数）
- 原始告警逐条复核（兜底）`jiangsu_fetch_alarm_records`（站点名称必填、≤24小时）；站点目录与组织人员 `jiangsu_fetch_station_directory`、`jiangsu_query_operations_graph`

**事件中心** `execute_smart_event_sql_query`（告警与处置的结构化聚合，只读带 LIMIT）。

## 可开展的分析（指引，非全集）

按监管目的自由组合。**分析中发现异常线索可随时下钻和扩展**——单站明细、逐日/逐时细分、扩大或移动时间窗、跨数据集关联、调平台接口取证——不受本清单限制：

1. **人员到站**：到站覆盖率与次数分布、分单位/分城市对比、签到距站异常（签到接口 + 站点目录做分母）。
2. **故障处置**：工单量与类型构成、响应/处理时长、超期与长期未闭环、30天重复故障站点、分单位排名、工单必填信息缺失（工单宽表；单张工单处置过程用接口明细核对）。
3. **告警与处置**：告警量/级别/状态分布、未处理积压排名、告警→工单转化率、逐日趋势（告警宽表 + 事件中心）。
4. **数据质量**：获取率/有效率/接收率（平台统计口径）、质控合格率与不合格站点排名、质控任务过期未完成（质控两宽表）。
5. **巡检落实**：各周期类型完成率、超期未完成清单、按人员/单位完成量、巡检转工单率（巡检宽表）。
6. **站点设备**：风险分级分布与高风险站点清单、成因下钻（工单/告警明细）、设备构成核对（站点健康 + 维度表）。
7. **停电合规**：停电报备时段核对（停电单表，覆盖有限须注明）+ 动环供电历史佐证。
8. **考核指标**：两率达标与评分排名（考核宽表——2026-07 起窗口内无实际填报，当前只能说明数据现状，不得用占位值构造结论）。

## 口径速查

- 工单：超期按计划完成时间；响应=派单→到站（节点代理口径）；重复故障=同站同设备30天（未填设备按站点并自解释）；平台存在大量长期未闭环单，超期率偏高属数据现状，须说明。
- 质控：仅约23个试点站，结论不得外推全网；合格判定用平台原文（合格/不合格）；单站下钻（日志/曲线）走平台接口（故障诊断模式）。
- 巡检：状态 未开始/处理中/已完成（语义推断，待业务确认）；超期=计划周期结束仍未完成。
- 统计阈值建议（可按用户要求调整）：获取率<95%、有效率<98%、质控合格率<80%、故障处理>72小时（电力与通信类故障不计超时）。
- 所有统计类问题先查本地数据集，单据核实与实时状态走平台接口；两者结论冲突时以平台接口为准并说明。

## 报告结构（建议，可按内容调整）

执行摘要 → 核心指标总览 → 各链路发现 → 问题与异常站点清单 → 附录数据来源与口径。图表服务论点，每图配一句管理解读；先结论后论证。

## 结论边界

- 只做只读分析，不创建或变更工单，不修改监测数据，不认定责任。
- 确定问题与待核查线索分开表述；建议可执行、可跟踪。
-门禁进站记录（平台实测无数据）、备机备案与设备生命周期起止、排班与人员证书/技能、运维计划管理、报备审批、停运管理、数据补录明细、站点在线离线历史状态。
