# 故障工单月度分析

确定性计算必须通过 `execute_python` 调用 `app.services.jiangsu_operations_reports.build_fault_monthly_report`。脚本开头必须执行 `import sys; sys.path.insert(0, "/home/xckj/suyuan/backend")`，再导入函数；禁止直接导入而不设置路径。读取接口外置 JSON 时必须先判断根结构：`rows = payload if isinstance(payload, list) else payload.get("data", [])`，不得对可能为数组的根对象直接调用 `.get()`。禁止由 Agent 临时重写聚合、异常剔除或时长统计规则；计算返回值直接写入 `report_data.json`。`execute_python` 在隔离沙箱运行，禁止读取相对路径或报告参考文档；不要在脚本中读取 `backend/app/tools/report/report_package/references/index.md`。脚本只做数据标准化、调用上述函数和输出 JSON；如计算脚本失败，记录错误并停止重试，不得重复生成不同脚本。

## 执行顺序

1. 使用江苏部署环境文件（`backend/.env.jiangsu-ops`）调用 `jiangsu_fetch_fault_work_orders`，查询上一个自然月 `Fault + Finish` 工单；必须使用 `fetch_all=true`，记录接口、请求范围、`total_count`、`returned_records` 和 `source_data_complete`。
2. 先做字段质量检查：站点、城市、运维单位、设备编号、工单标题、创建时间、完成时间、工单号缺失分别计数；没有创建/完成时间的记录不得参与时效统计。
3. 统一故障类别：优先使用平台故障类型字典；当前接口只有标题时，按稳定关键词映射为站点断数、仪器断数、浓度超量程、供电/通信、其他，并保留原始标题。未命中的标题进入“其他/待归类”，不得强行归类。
4. 计算总体、站点、城市、运维单位和设备维度：数量、占比、站均故障量、平均/中位处理时长、长尾工单数、设备品牌/型号分布。
5. 异常剔除：同站点、同类断电/停电/断数/通信/离线事件，连续间隔不超过 24 小时且至少 3 条，从总体统计、时效均值和单位排名剔除；必须单列站点、时间范围、数量、工单号和剔除前后指标。若未命中，只能写“本期未识别满足规则的连续簇”，不能写“没有重复故障”。
6. 对 TOP15 站点和高长尾单位调用工单详情，核对响应、到场、维修、闭环节点和 RF/性能检查附件；不能仅凭列表字段推断维修质量。
7. 生成正式报告，至少包含：统计口径、数据质量、故障结构、高频站点、重复故障专项、处理时效、单位/城市对比、设备维修轨迹、RF 覆盖、同比（上月数据可得时）、结论和建议。
8. 严格按 `create_report_package -> render_report_package(docx) -> validate_report_package(require_html=true, require_docx=true) -> publish_report` 收口。校验失败不得发布；接口失败、数据不完整或关键字段缺失时生成数据门禁说明，不得输出“无异常”。

## 面向省站管理用户的正式报告输出要求

正式报告的读者是省站负责运维统筹、考核和资源安排的管理用户，不是技术人员或 IT 运维人员。报告必须帮助读者在短时间内回答“本月总体是否变好、风险集中在哪里、哪些问题需要省站介入、下一步谁在何时完成什么动作”，不得把接口字段、脚本过程或逐条工单流水账当作主体内容。

### 管理阅读路径

报告正文按“结论先行—证据支撑—行动闭环”组织，首页或执行摘要必须给出：

- 本期工单总量、涉及站点、平均/中位处理时长，以及与上月相比的方向和幅度；同时明确数据完整性和统计口径。
- 不超过 5 条核心发现，每条包含影响范围、变化幅度和管理含义；不能只写“排名第一/数量较多”。
- 需要省站优先关注的风险清单，按“高频重复、影响范围、长时间未闭环、维修后缺少性能验证”等管理优先级排序，并标注站点、城市、运维单位、工单数和证据状态。
- 需要决策或督办的事项，例如专项排查、资源调配、运维单位帮扶/对标、跨单位协同或数据补齐；每项都要有建议责任对象、完成时限和验收证据。

### 必须呈现的管理信息

1. **全省态势**：用总量、站点覆盖面、站均故障量、故障结构和处理时效说明运行态势。数量变化必须同时给出占比、基数和环比/同比，避免把站点规模差异误读为管理质量差异。
2. **风险优先级**：除 TOP 站点外，单列重复故障、长尾工单、同一城市或单位的集中风险，并说明筛选规则、影响范围、是否剔除连续簇及剔除前后变化。对“高频但已快速闭环”和“频次一般但长期未闭环”要区分处置优先级。
3. **区域和单位对比**：城市、运维单位排名同时展示工单量、覆盖站点数、站均工单量、平均/中位时长和长尾比例；样本量过小时标注“样本有限”，不得仅凭单一平均值作考核结论。需要解释城市与运维单位高度绑定、规模差异或数据缺失对排名的影响。
4. **趋势与变化解释**：有上月数据时，至少说明总量、故障结构、处理时效和重点站点的变化；对突增、突降或结构剧变给出“已证实事实、待核查原因、所需补证”三部分，不能用季节性、设备老化等推测替代证据。
5. **闭环质量**：说明响应、到场、维修、恢复、复测和 RF/性能检查的覆盖情况，突出“已完成工单但证据不足”的管理缺口。报告应回答哪些维修类型必须补充性能验证，而不是只罗列附件数量。

### 结论、图表与行动表达

- 每个结论使用“事实（数量/比例/时间范围）—影响或管理含义—下一步核查/动作”的句式；结论和建议分开，事实不足时明确写“待核查”，不认定违规、造假或责任归属。
- 图表优先服务于比较和决策：趋势图、结构占比、站点/单位对比、时效分布和风险清单应配一句管理解读；禁止只有图没有结论，也禁止用技术字段堆砌图表。
- 建议必须可执行、可跟踪，至少形成“问题/对象—建议动作—责任对象—时限—验收证据—下月跟踪指标”表。建议推广经验时说明可复制的做法和适用边界，提出单位帮扶或资源调整时保留人工决策边界。
- 正文控制技术细节的篇幅；接口原文、工单号、字段缺失明细、剔除边界和逐单证据放入附录或证据清单，正文只保留能支持管理判断的汇总信息。

## 输出和案例要求

- 报告结论只写事实、统计异常和待核查线索，不直接认定违规、造假或责任归属。
- `report_data.json` 必须保存源接口元数据、字段缺失统计、原始工单数量、纳入数量、剔除数量、规则参数、重点清单和报告版本。
- 任务执行结束后写入一条任务案例，记录周期、接口总量、数据完整性、剔除结果、报告 ID、失败/修复点和下一期检查项；案例用于下一次执行的质量复盘，不替代本期数据。
