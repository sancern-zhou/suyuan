# 统一任务审核与待办

所有后台任务使用 `submit_task_review` 提交人工事项。工具从执行上下文取得任务和执行身份；模型提供稳定业务编号、分类、标题、摘要、结论、检查项、数据影响、证据、处置建议和详情区块。后端严格校验后保存到当前 `DATA_REGISTRY_DIR/task_reviews`。

任务执行成功、普通回复非空或回复中的 JSON 块均不生成待办。工单审核、智能事件与故障诊断遵守同一协议，没有旧工具别名或专用审核渲染器。

- `/api/task-reviews` 提供待办分类列表；详情与人工操作使用同一资源 ID。
- 同一执行重复提交同样结果是幂等的；修改已提交结论须新一轮执行。
- 新一轮结果更新业务事项并保留历史版本；人工操作带版本校验，防止确认过期结果。
- 待确认、处置中事项进入列表；归档、退回事项移出。
- 数据剔除建议必须提供区间、边界来源与合理性；单小时记录允许开始结束为同一时间，逆序区间禁止提交。
- 人工反馈由通用 `task_review_feedback` 抓取器写入来源任务的案例与长期记忆；新一轮结果不会覆盖尚未消费的历史反馈。
- 智能事件页面只投影通用审核记录及其人工状态，不维护另一套确认归档接口。

## 历史数据处理

采用清空历史结果后重新研判的方式，不迁移旧审核记录，不兼容旧工具。江苏部署已于 2026-09-10 清理旧工单审核结果、审核卡片资源、事件研判结论、内部研判任务、相关执行与去重记录及历史学习结果。

保留原始事件、告警线索、工单附件、证据包和定时任务配置；事件恢复为“未研判”。后续重新执行研判，只有通用工具校验并保存成功的结论才生成待办。

前端已按江苏项目构建发布，web 与 worker 已成对重启。工单数据查询、证据采集与人工派单接口继续作为业务能力使用。
