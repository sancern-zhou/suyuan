# 江苏智能事件中心开发计划与实施说明

## 1. 目标与范围

本项目把江苏运维平台现有的告警、监测、合规和任务能力汇聚为“智能事件中心”。事件是长期保存的业务事实，任务是围绕事件产生的一次处理工作，对话是任务的交互工作区。

第一阶段受平台事件接口和规则配置接口仍在完善的约束，先建设稳定的内部数据契约和适配层：

- 使用现有告警查询接口生成 V3.0 兼容的待研判事件；
- 保留原始告警作为证据和线索标签，不在系统生成阶段自动定类；
- 提供事件列表、事件详情和规则配置的后端契约；
- 为任务卡片进入 AI 对话、右侧调度事件列表和详情页预留 `event_id`、`task_id`、`conversation_id` 关联；
- 平台事件接口稳定后，只替换数据适配器，不改变前端和 Agent 的事件契约。

不在第一阶段直接实现自动 AI 定类、自动派单或自动归档。AI 研判结果必须经过结构化提交和人工确认后才进入事件闭环。

## 2. 用户工作流

```text
告警接口返回线索
  -> 线索标准化
  -> 生成待研判事件
  -> 创建 AI 研判任务卡片
  -> 进入任务对话，或打开事件详情
  -> Agent 调度右侧事件列表/详情/证据焦点
  -> 提交结构化 AI 研判结果
  -> 人工确认、派单、反馈、归档
```

固定页面与动态工作区的分工如下：

| 页面 | 责任 |
| --- | --- |
| 事件中心 | 查询、筛选、排序、批量管理事件 |
| 事件详情 | 展示证据、监测数据、AI 结果和闭环记录，是最终事实页 |
| 任务卡片 | 提醒当前要处理的任务，携带 `event_id` 和 `task_id` |
| AI 对话 | 处理追问、补充证据和研判过程 |
| 右侧工作区 | 由 Agent 调度事件列表、详情、对比和证据焦点 |

Agent 只能调度查看内容；派单、反馈、归档和修改研判结果必须调用业务接口并经过用户确认。

## 3. 第一阶段实施结果

本次实施包含：

1. `backend/app/services/jiangsu_smart_event.py`
   - 告警记录到 V3.0 事件的标准化；
   - 初始事件名称和“未研判”状态生成；
   - 事件列表筛选和详情查询；
   - 规则配置的默认值、读取和持久化；
   - 平台适配状态和能力声明。
2. `backend/app/api/jiangsu_smart_event_routes.py`
   - `GET /api/jiangsu/smart-events`：事件列表；
   - `GET /api/jiangsu/smart-events/{event_id}`：事件详情；
   - `GET /api/jiangsu/smart-events/config/current`：线索与 AI 配置；
   - `PUT /api/jiangsu/smart-events/config/current`：管理员保存配置。
   - `POST /api/jiangsu/smart-events/sync`：从当前告警接口同步事件并生成任务卡片；默认只同步，不派发 AI，显式传 `dispatch_ai=true` 才发布事件驱动任务；
   - `GET /api/jiangsu/smart-events/tasks`、`GET /api/jiangsu/smart-events/tasks/{task_id}`：查询任务卡片；
   - `POST /api/jiangsu/smart-events/{event_id}/tasks`：为事件创建 AI 研判任务。
   - `POST /api/jiangsu/smart-events/{event_id}/ai-judgments`：保存结构化研判结果并支持人工确认；
   - `POST /api/jiangsu/smart-events/{event_id}/operations`：记录反馈、派单等人工操作审计；
   - `POST /api/jiangsu/smart-events/{event_id}/archive`：确认后归档并锁定事件。
3. `frontend/src/services/jiangsuSmartEventsApi.js`
   - 前端统一调用封装，后续事件中心和右侧工作区共用。
4. `frontend/src/services/jiangsuSmartEventWorkspace.js`
   - Agent 调度右侧事件列表、详情、证据焦点、对比和任务上下文的命令协议。
5. `backend/tests/services/test_jiangsu_smart_event.py`、`backend/tests/api/test_jiangsu_smart_event_routes.py`
   - 覆盖标签保留、初始命名、筛选、配置持久化和接口契约。

第二阶段已补充事件存储和任务卡片：同步告警会将事件写入 `DATA_REGISTRY_DIR/jiangsu_smart_events/store.json`，同一事件只自动保留一个 AI 研判任务，并通过现有事件驱动定时任务服务按供电、数采网络、站房环境、仪器四类线索触发对应任务。每个任务沿用故障工单审核已经落地的任务专属案例库和长期记忆配置；任务 Agent 的最终回复由执行完成回调写入事件详情的 `ai_judgment.final_response` 和 `ai_diagnosis_note`，任务卡片同步保留执行 ID 和最终回复。用户仍可手动创建新的研判任务。

当前适配器的能力边界：

- 已接入：江苏运维告警/电话记录接口；
- 已实现：告警接口支持无站点编码的全省查询，并按实时站点目录筛选全部省控站点；告警记录映射为“报警”线索标签和待研判事件；
- 待平台接口稳定后接入：平台事件查询、事件归并结果、视频/数据/断数/超限/合规标签、平台规则字典；
- 已实现：结构化 AI 研判字段的人工确认提交、处置操作持久化和归档锁定；

## 4. 数据契约

事件对象使用以下稳定字段，平台适配器可以逐步补充字段而不影响页面：

```json
{
  "event_id": "alarm:12345",
  "site_id": "5006A",
  "site_name": "示例站点",
  "event_start_time": "2026-09-09T08:00:00+08:00",
  "event_end_time": "2026-09-09T08:00:00+08:00",
  "initial_event_name": "示例站点报警线索待研判事件",
  "event_name": "示例站点报警线索待研判事件",
  "event_status": "未研判",
  "event_type": "待 AI 研判",
  "clue_tags": [],
  "clue_count": 1,
  "ai_event_type": null,
  "ai_data_impact": "待确认",
  "ai_suggested_level": null,
  "evidence": {}
}
```

事件、任务、对话的关系为：

```text
event 1 --- N task 1 --- N conversation
```

AI 对话必须通过结构化提交更新事件，聊天文本不能直接覆盖事件结论。当前接口使用：

- `POST /api/jiangsu/smart-events/{event_id}/ai-judgments`
- `POST /api/jiangsu/smart-events/{event_id}/operations`
- `POST /api/jiangsu/smart-events/{event_id}/archive`

## 5. 配置契约

配置保留 V3.0 语义，不再配置“疑似雾炮喷淋”等系统自动定类规则：

- `event_merge_window_minutes`
- `event_before_extend_minutes`
- `event_after_extend_minutes`
- `video_tag_confidence_threshold`
- `station_missing_factor_threshold`
- `multi_instrument_threshold`
- `initial_naming_priority`
- `ai_event_type_dictionary`
- `data_anomaly_threshold_pct`
- `pm_rise_threshold_pct`

第一阶段配置文件位于 `DATA_REGISTRY_DIR/jiangsu_smart_events/config.json`，由后端接口读写。平台规则配置接口稳定后增加 `PlatformSmartEventAdapter`，优先读取平台配置，失败时保留最后一次有效快照并返回来源状态。

## 6. 分阶段计划

### 阶段一：接口适配和事件基础模型（当前）

- 接入告警查询接口；
- 实现标准事件契约；
- 提供列表、详情和配置接口；
- 完成单元测试和路由测试。

### 阶段二：平台事件与规则接口接入

- 接入平台事件列表和详情接口；
- 接入平台规则配置读写接口；
- 保留字段映射、版本号、来源和降级状态；
- 增加分页、游标和增量同步。

### 阶段三：任务和 AI 对话闭环（本轮落地事件驱动执行）

- 从事件生成 AI 研判任务；
- 按告警线索类型匹配现有 `ScheduledTaskService.publish_event`，由事件驱动定时任务执行 Agent；
- 任务定义启用任务专属案例库、长期记忆和主动历史检索，配置方式与故障工单审核一致；
- 任务完成后把最终 Agent 回复持久化到事件详情，并在任务卡片中保留执行状态；
- 建立 `event_id/task_id/conversation_id` 上下文；
- Agent UI Command 调度右侧列表、详情、证据焦点；
- 结构化提交 AI 结果和重新研判版本。

### 阶段四：固定事件中心页面与 Agent 右侧工作区（本轮落地）

- 江苏分支侧栏进入固定事件中心，列表和详情在同一工作区展示；
- 事件中心刷新默认同步全省省控站点近 24 小时告警并展示，任务卡保持“待执行”，不自动触发 AI 研判；
- 详情页展示 AI 最终回复、研判状态和关联任务，任务卡片可进入现有任务执行工作区；
- Agent 可调用 `jiangsu_smart_event_workspace` 输出结构化 UI 命令，调度事件列表、固定详情、证据焦点、事件对比、操作历史和任务工作区；
- 对话消息中的工具结果由前端解析为右侧工作区命令；事件列表、固定详情和任务工作区仍由页面组件负责加载和渲染，Agent 不直接修改业务数据；
- 六项污染物时序、小时数据表和区域差异图；
- 证据标签、AI 摘要、参数快照和操作历史；
- 任务卡片与事件详情双向跳转。

### 阶段五：人工处置闭环（基础能力已落地）

- 结构化研判确认、反馈/派单操作审计、确认后归档锁定接口；
- 固定详情页提供人工确认和归档入口；
- 待接入真实派单/反馈平台接口，当前操作记录先保存在事件存储中；
- 更细粒度的角色权限、平台侧审计回写和归档锁定策略；
- P0/P1 队列、超时提醒和统计；
- 平台回写与结果复查。

## 7. 验收标准

- 告警记录可以转换为稳定的事件对象；
- 事件生成后状态为“未研判”，类型为“待 AI 研判”；
- 原始告警不丢失，至少生成一个带来源、对象、时间和原始编号的标签；
- 事件列表可以按站点、状态、关键词和时间筛选；
- 平台接口不可用时，接口返回明确的 `source` 和 `capabilities`，不能伪装成完整平台事件；
- 配置保存后可重新读取，配置文件位于显式数据目录；
- 事件详情、任务卡片和对话使用同一个 `event_id`；
- 归档和处置动作在后续阶段必须要求人工确认并产生审计记录。

## 8. 风险与取舍

平台事件接口尚未稳定时，不能把告警记录直接宣称为完整智能事件。当前返回的数据应明确标记为 `alarm_adapter` 来源，并限制为“待研判事件”。这样可以先让页面、任务卡片和 Agent 工作区联调，同时避免把临时字段固化为最终业务口径。
