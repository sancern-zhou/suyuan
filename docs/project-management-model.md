# 项目管理与交付模型

## 目的

本仓库将项目按代码归属和升级方式分为两类。该分类用于决定代码组织、发布、知识库和平台能力同步方式，避免以长期分叉替代项目配置。

| 类型 | 标识 | 适用场景 | 当前示例 |
| --- | --- | --- | --- |
| 共享 Main 项目 | `shared-main` | 项目差异主要是配置、提示词、工具、数据源或品牌；需要持续获得平台升级 | 江苏运维、江西噪声 |
| 独立项目 | `standalone` | 客户交付、发布节奏、合规边界或架构已长期显著分叉，不能跟随平台自动升级 | 许昌 |

## 共享 Main 项目

共享 Main 项目以 `main` 为唯一平台代码基线。项目差异必须优先放在下列位置：

- `projects/<project>/project.yaml`：模块、工具白名单、数据抓取器、定时任务和前端特性。
- `projects/<project>/prompts/`、`skills/`：项目提示词和技能。
- `backend/app/tools/<project>/`：项目专属工具；由项目清单显式启用。
- 项目专属数据源、密钥和部署配置：按部署环境隔离，禁止提交凭据。

通用平台层（例如 Agent 运行时、会话资源、知识库、任务调度、权限、安全修复和工具框架）只在 `main` 演进。项目需求若确需修改该层，必须按跨项目能力实现并补充回归测试，不能为单个共享 Main 项目维护完整平台 fork。

共享 Main 项目可独立部署，但部署版本必须记录所使用的 `main` 提交或正式发布版本，以便升级、回滚和问题追踪。

## 独立项目

独立项目拥有独立 Git 历史、发布节奏和运行边界，不自动吸收 `main` 变更。`main` 与独立项目之间不执行直接合并；需要同步时按功能评估后手工移植或 cherry-pick，并在目标项目完成回归测试。

独立项目中的改进如果具有跨项目价值，应先识别稳定边界、去除项目耦合，再以独立变更回迁 `main`。禁止把独立项目的整批历史直接合入平台主线。

许昌当前属于此类：其远端分支与 `main` 没有共同 Git 祖先，因此所有同步均按功能迁移处理。

## 知识库与数据隔离

知识库采用“共享库 + 本地库”的存储策略：

- 共享知识库的向量文件位于云端，可由经授权的管理员维护；检索时与本地库并发执行。
- 本地知识库的向量文件仅保存在项目/工作区本地，用于项目特有、临时或不应共享的数据。
- 共享 Main 项目可以使用同一云端共享库，同时保留各自本地库和 `local_scope` 隔离。
- 独立项目默认使用独立知识库、对象存储和向量存储；只有明确获得授权并完成兼容性评估时，才能接入共享库。

任何项目不得仅因名称相同而读取其他项目的本地知识库或数据源。

## 变更与发布规则

1. 新项目先确定类型，再创建部署、项目清单和知识库配置。
2. 共享 Main 项目的平台变更在 `main` 开发、测试和发布；项目差异通过清单和专属目录实现。
3. 独立项目的同步申请必须列出来源提交、迁移文件、风险、测试范围和目标版本。
4. 每个项目必须登记：项目类型、负责人、代码/部署位置、数据与知识库边界、当前平台基线及升级策略。
5. 发布或升级前，验证工具白名单、项目数据源、知识库访问范围和定时任务是否符合项目边界。

## 清单字段演进

当前 `project.yaml` 的 schema 尚未包含项目类型字段。后续需要让部署自动按类型执行策略时，将在 `ProjectManifest` 中增加并校验以下字段，而不是先在严格 schema 的 YAML 中写入未识别字段：

```yaml
delivery:
  type: shared-main # 或 standalone
  platform_baseline: main@<commit-or-release>
  owner: <team-or-role>
```

在该 schema 和加载逻辑完成前，以本文件的“当前项目登记”作为项目类型的权威记录。
