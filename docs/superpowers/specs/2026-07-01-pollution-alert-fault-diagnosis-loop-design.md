# Pollution Alert To Fault Diagnosis Loop Design

## Goal

Build the first-stage closed loop for pollution process alerts:

1. A scheduled pollution alert conclusion task detects pollution events and writes a conclusion plus evidence package.
2. A separate scheduled fault diagnosis task consumes the latest suspicious fault conclusions, uses cognitive maps to decide what data to collect, and writes probable fault causes plus a second evidence package.

The first release does not create or update external work orders, does not send notifications, and does not require a new frontend dashboard. The deliverable is a reliable file-backed diagnostic pipeline that later product surfaces can consume.

## Current Foundations

The implementation should reuse existing project components:

- `PollutionEventMonitorService` in `backend/app/services/pollution_event_monitor.py` already detects city pollution events, merges event lifecycle state, gathers evidence, and writes event artifacts.
- `CityPollutionEventFetcher` in `backend/app/fetchers/city_pollution_event_monitor/city_pollution_event_fetcher.py` already schedules pollution event detection every two hours.
- `AirQualityDataQualityMonitorService` in `backend/app/services/air_quality_data_quality_monitor.py` already checks station-level data quality using peer deviation, persistent bias, trend inconsistency, PM2.5/PM10 co-change, and NO2/O3 pattern rules.
- Cognitive map tools and APIs already support entity/relation lookup and graph-guided analysis for station, device, work order, fault, root cause, and quality rule concepts.
- Operations SQL tools already expose station, device, work order, RF form, and quality calibration tables through whitelisted read-only queries.

## Architecture

### Task 1: Pollution Event Conclusion Task

The existing pollution event monitor remains the detection source. Add a conclusion stage after evidence collection.

Responsibilities:

- Read each detected pollution event and its evidence pack.
- Produce a deterministic first-level classification:
  - `normal_pollution`
  - `suspected_device_or_data_fault`
  - `insufficient_evidence`
- Persist a standardized conclusion package for each event.
- Mark each package as available for downstream fault diagnosis when classification is `suspected_device_or_data_fault`.

This stage should remain mostly deterministic. It may use rules and evidence already present in the event package, but should not run a free-form Agent loop.

### Task 2: Fault Diagnosis Task

Add a separate scheduled task that consumes first-stage conclusion packages.

Responsibilities:

- Find recent unprocessed `suspected_device_or_data_fault` conclusion packages.
- Use the event's city, stations, pollutant, time window, observed abnormal pattern, and available evidence as cognitive map hints.
- Ask the cognitive map guidance layer for diagnostic paths and required evidence.
- Actively collect supporting data through existing query services:
  - station hour data around the event window
  - peer city/station comparisons
  - station/device metadata
  - recent work orders for involved stations/devices
  - quality control and calibration records
  - RF form records where a relevant table mapping is known
- Run or reuse data quality checks where the first-stage event has enough station-level data.
- Rank probable fault causes and write a structured diagnosis package.

The second task may use LLM-assisted reasoning only after deterministic evidence collection. Its output must identify which conclusions are supported, contradicted, or still missing evidence.

## Data Flow

```text
city_pollution_event_fetcher
  -> city/hour monitoring data
  -> pollution event detection
  -> evidence_pack.json
  -> event_conclusion.json

fault_diagnosis_fetcher
  -> read latest event_conclusion.json classified as suspected_device_or_data_fault
  -> cognitive_map_guidance
  -> supplemental data collection
  -> data quality checks
  -> fault_diagnosis.json
  -> fault_evidence_pack.json
  -> fault_diagnosis.md
```

## File Layout

Reuse the existing pollution event output root and the existing event directory generated by `PollutionEventMonitorService._collect_event_evidence`:

```text
backend/backend_data_registry/pollution_process_events/
  {city}/
    {run_id}/
      run_manifest.json
      detected_events.json
      event_{event_id}/
        evidence_pack.json
        analysis_request.md
        event_conclusion.json
        fault_diagnosis/
          fault_diagnosis.json
          fault_evidence_pack.json
          fault_diagnosis.md
          diagnosis_manifest.json
```

The actual event directory is the `event_dir` returned in each `run_manifest.json` event artifact. Implementations must discover conclusion inputs from the manifest or by finding directories that already contain `evidence_pack.json`, not by reconstructing event paths from string assumptions.

## Event Conclusion Schema

`event_conclusion.json`:

```json
{
  "schema_version": "pollution_event_conclusion/v1",
  "event_id": "event_...",
  "city": "广州",
  "main_pollutant": "PM2_5",
  "time_range": {
    "start": "2026-07-01 08:00:00",
    "end": "2026-07-01 12:00:00"
  },
  "classification": "suspected_device_or_data_fault",
  "classification_confidence": "medium",
  "reason_codes": [
    "single_station_dominant",
    "peer_trend_inconsistent"
  ],
  "summary": "事件主要由单站异常拉动，同城站点未同步升高，需进入故障诊断。",
  "evidence_refs": [
    {
      "type": "file",
      "path": "evidence_pack.json",
      "description": "污染事件原始证据包"
    }
  ],
  "downstream": {
    "requires_fault_diagnosis": true,
    "processed_by_fault_diagnosis": false
  },
  "created_at": "2026-07-01T10:00:00+08:00"
}
```

Classification rules for release one:

- Classify as `suspected_device_or_data_fault` when the event is dominated by one or very few stations, peer stations do not show similar trends, pollutant relationships are physically weak, or data quality issues are already present.
- Classify as `normal_pollution` when multiple stations or nearby areas show coherent concentration increases and meteorological/process evidence supports real pollution accumulation or transport.
- Classify as `insufficient_evidence` when records are missing, peer comparison is unavailable, or the event package is internally inconsistent.

## Fault Diagnosis Schema

`fault_diagnosis.json`:

```json
{
  "schema_version": "fault_diagnosis/v1",
  "source_event_conclusion": "event_conclusion.json",
  "event_id": "event_...",
  "diagnosis_status": "completed",
  "diagnosis_window": {
    "start": "2026-07-01 02:00:00",
    "end": "2026-07-01 14:00:00"
  },
  "cognitive_map": {
    "used": true,
    "map_ids": ["cm_..."],
    "entity_hints": ["广州", "PM2_5", "采样系统", "站点A"]
  },
  "most_likely_causes": [
    {
      "cause": "采样系统异常",
      "cause_type": "device_or_facility",
      "confidence": "medium",
      "supporting_evidence": [
        "站点 PM2.5 与 PM10 协同关系偏弱",
        "同城站点未出现同步升高"
      ],
      "contradicting_evidence": [],
      "missing_evidence": [
        "采样流量校准记录"
      ],
      "recommended_action": "核查采样流量、采样管路和最近维护记录"
    }
  ],
  "queried_data": [
    {
      "name": "station_hour_data",
      "status": "available",
      "path": "fault_evidence_pack.json"
    }
  ],
  "summary": "该污染告警更可能由站点设备或数据异常引起，首要核查采样系统。",
  "created_at": "2026-07-01T10:10:00+08:00"
}
```

`fault_diagnosis.md` should be a readable report generated from the JSON, not a separate source of truth.

## Scheduling

Task 1:

- Continue using `city_pollution_event_fetcher` cadence initially: every two hours.
- Add conclusion generation to the same run, or register a new fetcher that wraps the existing monitor and conclusion writer.

Task 2:

- Register `fault_diagnosis_fetcher`.
- Run every 10 to 30 minutes, or immediately after Task 1 if a scheduler hook is available.
- Use idempotency: if `diagnosis_manifest.json` exists and references the same `event_conclusion.json` checksum, skip reprocessing.
- Support manual triggering through the existing fetcher API for backfills and debugging.

## Error Handling

- Task 1 should still write a conclusion package when classification cannot be made, using `classification = "insufficient_evidence"`.
- Task 2 should write `fault_diagnosis.json` with `diagnosis_status = "failed"` or `partial` when some data sources fail.
- Missing cognitive map data should not block diagnosis. The task should fall back to deterministic data quality checks and mark `cognitive_map.used = false`.
- All supplemental query failures should be recorded in `queried_data` and `missing_evidence`.

## Testing

Unit tests:

- Classification rule tests for normal pollution, suspected fault, and insufficient evidence.
- Idempotency tests for the fault diagnosis fetcher.
- Schema validation tests for `event_conclusion.json` and `fault_diagnosis.json`.

Integration tests:

- Use fixture evidence packs to run Task 1 conclusion generation.
- Use a fixture suspected-fault conclusion to run Task 2 with mocked cognitive map and query services.
- Verify output files are created in the expected event directory and contain evidence references.

Manual verification:

- Trigger `city_pollution_event_fetcher` through `/api/fetchers/trigger/city_pollution_event_fetcher`.
- Confirm suspected fault conclusions are discovered by the second task.
- Inspect the generated Markdown and JSON packages for a real recent event.

## Out Of Scope For First Release

- Creating or updating external work orders.
- Sending WeChat, WeCom, DingTalk, or SMS notifications.
- A dedicated frontend dashboard.
- Full video inspection and image OCR for station room evidence.
- Automatic rule learning or knowledge graph mutation.

## Open Implementation Notes

- Prefer adding small services under `backend/app/services/` rather than expanding `pollution_event_monitor.py`.
- Keep file-backed outputs for now. A database-backed event center can consume the same schemas later.
- The second task should be designed so an Agent-driven implementation can be swapped in later, but the first implementation should keep deterministic evidence collection explicit and testable.
