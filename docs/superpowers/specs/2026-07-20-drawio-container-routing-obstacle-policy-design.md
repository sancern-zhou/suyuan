# Draw.io 容器节点自动避让分类设计

## 背景

画板模式会在 AI 候选 XML 保存前为正交连线生成显式路径。路由器将普通节点扩张一定安全距离后作为障碍物，以防连线穿过业务节点。

分层架构图中的泳道和容器用于表达“接入层”“应用服务层”等布局区域，而不是独立业务节点。跨层连线必须能够穿过这些区域。当前实现已经忽略泳道和容器主体，但仍将泳道标题栏单独加入障碍物集合，导致用户到网关、网关到服务等跨层连线为了绕过较长的标题栏而产生不必要的大幅折返。

## 目标

自动路由必须按节点语义区分布局容器和业务节点：

- 布局容器的主体和标题栏均不参与自动避让；
- 普通业务节点继续作为障碍物；
- 跨层连线保持简洁、确定性的正交路径；
- 路由后的碰撞复核使用与路由阶段完全相同的障碍物分类。

## 节点分类规则

节点分类只使用 Draw.io XML 中的显式样式语义，不根据节点名称、尺寸或位置猜测。

以下顶点属于布局容器，整个几何区域均不作为障碍物：

- 样式标志包含 `swimlane`；
- 样式属性包含 `container=1`；
- 样式标志包含 `group`。

泳道的 `startSize` 和 `horizontal` 只影响标题栏的显示位置，不再用于生成标题栏障碍物。横向和纵向泳道采用相同策略。

以下顶点继续作为障碍物：

- 普通应用、服务、网关、数据库和决策节点；
- 普通文本框和注释节点；
- 包含徽标、端口或其他子节点，但自身未声明容器语义的普通父节点。

现有装饰元素规则保持不变：`pointerEvents=0` 的节点、无描边无填充的透明文本，以及符合现有背景约定的顶层背景节点不作为障碍物。

## 选择显式分类的原因

显式样式分类边界稳定，并与 Draw.io 的节点语义一致。名称包含“层”、节点尺寸较大或拥有子节点都不足以证明它是布局容器：依靠这些特征推断会错误放过大型业务节点，或者把带徽标的普通节点误判为容器。

因此，生成架构图时应通过 `swimlane`、`container=1` 或 `group` 明确表达布局容器。缺少这些样式的普通大矩形仍按业务节点避让。

## 路由数据流

处理流程保持不变，仅收紧障碍物构建策略：

```text
解析并规范化候选 XML
  -> 解析顶点绝对坐标
  -> 按显式样式语义分类顶点
  -> 仅为普通业务节点建立扩张障碍物矩形
  -> 生成或保留正交连线路径
  -> 使用同一障碍物分类执行序列化后碰撞复核
  -> 输出候选 XML 和路由指标
```

不改变端口选择、通道搜索、可见性图兜底、边线交叉统计和失败降级策略。

## 实现边界

障碍物判断应由单一节点分类规则负责。障碍物矩形构建不得再为泳道标题栏追加独立的 `#header` 障碍物。与 `#header` 标识相关的兼容清理可以保留，也可以在确认没有其他调用方依赖后移除，但不得扩大本次改动范围。

本次不增加根据标签或几何特征自动修复错误节点类型的逻辑，也不修改既有画板 XML。规则只影响进入 AI 候选自动路由流程的新候选。

## 测试设计

增加或调整聚焦测试以证明：

- 连线可以直接穿过横向泳道标题栏；
- 连线可以直接穿过纵向泳道标题栏；
- 跨越多个泳道或容器的连线不会因容器边界产生额外绕行；
- `container=1` 和 `group` 的整个区域不参与避让；
- 普通长矩形仍会触发正交绕行；
- 带子徽标的普通父节点仍作为障碍物；
- 序列化后的碰撞复核不会将泳道或容器报告为阻塞节点；
- 普通节点碰撞检测和现有路由指标保持有效。

## 验收标准

- 用户到网关、网关到服务等跨层连线能够穿过泳道主体和标题栏。
- 容器不会出现在 `blocking_node_ids` 或剩余节点碰撞统计中。
- 普通业务节点仍保持安全间距并被自动避让。
- 相同 XML 重复路由得到稳定结果。
- 现有路由测试与新增分类测试全部通过。
