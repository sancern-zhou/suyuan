# 场景驱动的知识库图谱自动发现与业务确认设计

## 1. 背景与目标

suyuan 的知识库服务于环境领域，但用户创建知识库时的具体场景并不固定，可能涉及大气、噪声、政策文件、技术规范、企业信息、监测站点、设备故障或其他业务主题。

本设计遵循以下边界：

- 一个知识库只对应一个业务场景，不在同一知识库内再划分领域层、场景层或任务层。
- 用户理解自己的业务场景和业务逻辑，但不要求用户掌握实体类型、关系类型、三元组约束等知识图谱建模概念。
- 系统必须基于用户输入的场景需求和至少一份代表性文档，自动发现适合该场景的抽取约束。
- 用户通过业务语言确认或修正系统理解，而不是直接编辑技术 Schema。
- 用户可以随时补充自然语言业务规则，也可以直接录入业务事实。
- 用户直接录入的业务事实默认是 `confirmed` 可信事实。
- 已确认的场景约束、业务规则和业务事实共同约束后续文档中的实体与关系抽取。

目标是让普通业务用户完成“描述场景—上传样本—确认业务理解—持续构建图谱”，同时保留后台可验证、可版本化的结构化 Schema。

## 2. 推荐方案

采用“自动发现 + 业务化确认 + 后台结构化编译”方案。

系统内部仍然使用严格的 `GraphExtractionSchema`，以保证抽取结果可校验；但不把 Schema JSON 暴露为主要用户界面。用户面对的是场景描述、业务对象、业务逻辑、自然语言规则和事实表述。系统负责将这些内容编译成内部实体类型、关系类型、合法方向、别名和抽取要求。

不采用以下方案：

- 固定领域模板：无法覆盖不固定的知识库场景，并容易把错误本体带入新场景。
- 用户手工编辑 Schema：门槛高，用户即使懂业务也未必懂图谱建模。
- 完全无 Schema 的自由抽取：短期容易使用，但实体类型和关系名称会持续漂移，最终难以检索和推理。

## 3. 用户流程

### 3.1 创建知识库并描述场景

用户填写：

- 知识库名称。
- 场景目标，例如“分析工业企业噪声投诉、排放来源、监测结果与整改措施之间的关系”。
- 希望系统回答或推理的问题，可选，例如“某类投诉通常关联哪些企业、噪声源和整改措施”。

场景描述作为后续自动发现和抽取的最高优先级语义约束之一。

### 3.2 上传代表性文档

进入自动发现前，用户必须上传至少一份代表性文档。代表性文档应真实覆盖该场景中的主要业务对象和逻辑关系。

系统完成文档解析和 Chunk 构建，但在用户确认场景模型前，不把自动抽取结果作为正式图谱发布。此时文档知识库检索可以正常建立，图谱处于 `discovering` 或 `awaiting_confirmation` 状态。

### 3.3 自动发现

系统综合以下输入进行场景分析：

1. 用户场景描述。
2. 用户希望回答的问题。
3. 代表性文档的标题、目录、摘要和抽样 Chunk。
4. 已录入的自然语言业务规则。
5. 已录入的业务事实。

系统输出面向业务用户的“场景理解草案”：

- 核心业务对象，例如“企业、噪声源、监测点、投诉事件、监测结果、整改措施”。
- 核心业务逻辑，例如“企业拥有噪声源”“投诉事件指向企业”“监测结果评价监测点”“整改措施处理噪声问题”。
- 关键别名，例如“厂界监测点/边界测点”。
- 建议忽略的内容，例如文档编制单位、页眉页脚等非业务对象。
- 可能存在歧义或证据不足的业务概念。

系统不要求用户确认 `Company --has_source--> NoiseSource` 这样的技术表达，而应展示为自然语言：

> 企业可以拥有一个或多个噪声源；投诉事件可以指向企业或具体噪声源。

### 3.4 业务化确认

用户可以：

- 确认系统理解。
- 删除不属于本场景的业务对象或逻辑。
- 修改对象名称。
- 用自然语言补充遗漏逻辑。
- 标记某条逻辑为“必须满足”“允许出现”或“禁止抽取”。

确认后，系统把业务表达编译为结构化 Schema，并生成新的 `schema_version`。首次确认后才能启动正式图谱抽取。

### 3.5 持续补充业务规则

用户可直接录入一条自然语言规则，例如：

> 工业企业的厂界噪声监测结果应按功能区类别和昼夜时段使用对应限值评价。

规则保存为独立的一等资源，而不是只拼接到一个不可追踪的 Prompt 字符串中。系统解析出：

- 规则适用对象。
- 条件。
- 业务关系或约束。
- 是否需要用户确认解析结果。
- 来源、创建人和版本。

用户提交规则后，系统显示简短的结构化理解供确认。确认规则参与后续抽取，但不自动把规则推导出的所有可能事实写入图谱。

### 3.6 直接录入业务事实

用户可以用自然语言录入事实，例如：

> 企业 A 的主要噪声源是 1 号空压机。

系统解析为候选结构：

```text
企业 A --拥有主要噪声源--> 1 号空压机
```

用户在提交界面确认解析结果后，该事实立即写入图谱，默认状态为 `confirmed`，并记录：

- 原始自然语言。
- 结构化实体和关系。
- 创建人和创建时间。
- 来源类型 `user_asserted`。
- 确认状态 `confirmed`。

如果实体已存在，系统执行实体链接；存在歧义时必须让用户选择已有实体或创建新实体，不能静默错误合并。

## 4. 场景模型与内部 Schema

### 4.1 双层表达

每个知识库维护两种等价但用途不同的表示：

1. `BusinessSceneProfile`：给用户阅读和编辑的业务表达。
2. `GraphExtractionSchema`：供抽取器和校验器执行的结构化约束。

示例业务表达：

```json
{
  "scene_goal": "分析工业企业噪声投诉和整改闭环",
  "business_objects": ["企业", "噪声源", "投诉事件", "监测结果", "整改措施"],
  "business_logic": [
    "企业拥有噪声源",
    "投诉事件可以关联企业或噪声源",
    "整改措施用于处理被确认的噪声问题"
  ],
  "ignored_content": ["页眉页脚", "文档编制格式信息"]
}
```

对应的内部 Schema 可以编译为：

```json
{
  "allowed_entity_types": [
    "Enterprise",
    "NoiseSource",
    "ComplaintEvent",
    "MonitoringResult",
    "RectificationMeasure"
  ],
  "allowed_relation_types": [
    "has_noise_source",
    "complaint_targets",
    "measure_handles"
  ],
  "allowed_relation_triplets": [
    ["Enterprise", "has_noise_source", "NoiseSource"],
    ["ComplaintEvent", "complaint_targets", "Enterprise"],
    ["ComplaintEvent", "complaint_targets", "NoiseSource"],
    ["RectificationMeasure", "measure_handles", "NoiseSource"]
  ]
}
```

### 4.2 自动发现不是一次性操作

场景模型可以随新文档和用户反馈演进，但系统不得静默修改已确认 Schema。

发现新类型或新关系时：

- 抽取器可以记录为 `schema_suggestion`。
- 管理界面说明建议来自哪些文档和 Chunk。
- 用户确认后生成新 Schema 版本。
- 新版本默认只影响后续抽取。
- 用户可选择对历史 Chunk 执行增量重抽取或全量重建。

## 5. 抽取流程

正式抽取使用以下上下文：

```text
场景目标
+ 已确认业务对象和业务逻辑
+ 已确认自然语言规则
+ 当前 Schema 版本
+ 领域别名和实体目录候选
+ 文档标题与章节路径
+ 当前 Chunk
+ 相邻 Chunk 摘要
```

抽取分为四步：

1. 实体、属性、别名和证据片段抽取。
2. 基于本轮实体局部 ID 抽取关系和证据片段。
3. Schema、方向、证据和业务规则校验。
4. 实体链接后写入候选事实和 Mention。

系统生成的文档事实默认保持 `candidate`，经用户审核后进入 `confirmed/published`；用户直接录入并确认的业务事实默认立即成为 `confirmed`。

业务规则只约束抽取和验证，不得在缺少文档证据时被当成文档事实。规则推理得到的结论如需持久化，应标记为 `inferred` 并保存推理依据，不能冒充原文事实。

## 6. 证据和可信度

每个自动抽取的实体 Mention 和关系 Mention 必须关联：

- 文档 ID。
- Chunk ID。
- 页码或章节。
- 精确原文片段。
- 字符起止位置。
- 抽取模型、Prompt 版本和 Schema 版本。
- 抽取置信度和校验结果。

系统必须验证证据片段真实存在于对应 Chunk。缺少证据、违反 Schema 或与已确认规则冲突的自动事实不能直接进入可信检索范围。

用户直接录入的事实使用用户输入文本作为证据，来源明确标记为 `user_asserted`。

## 7. Agent 使用方式

Agent 面向同一知识库获得两类能力：

- 知识问答：通过 Chunk 向量、关键词和重排序检索原文。
- 业务认知：检索 `confirmed/published` 实体、关系、规则和用户确认事实，执行有限深度的图遍历。

检索建议使用：

```text
问题
→ Chunk 混合召回
→ 实体和关系召回
→ 图遍历或图扩散
→ Mention 映射回原文 Chunk
→ RRF 融合
→ Reranker
→ 向 Agent 返回事实、业务规则和原文证据
```

Agent 必须区分：

- `document_fact`：有文档证据的事实。
- `user_asserted`：用户直接确认的事实。
- `business_rule`：约束或逻辑规则。
- `inferred`：根据规则和事实推导的结论。

## 8. 状态与版本

知识库图谱增加场景建模状态：

- `awaiting_documents`：缺少代表性文档。
- `discovering`：系统正在分析场景。
- `awaiting_confirmation`：等待用户确认场景理解。
- `ready`：Schema 已确认，可以正式构建。
- `building`：正在抽取。
- `partial`：部分 Chunk 失败。

需要版本化：

- `scene_profile_version`
- `schema_version`
- `rule_version`
- `prompt_version`
- `model_name/model_params`

修改场景模型、Schema 或规则时，系统应显示影响范围和是否需要重建，不得静默让新旧结果混用而无法追踪。

## 9. 异常处理

- 没有代表性文档：拒绝启动自动发现，提示至少上传一份文档。
- 文档覆盖不足：允许生成草案，但明确提示样本覆盖不足，并列出不确定概念。
- Schema 编译失败：保存业务输入，返回可理解的冲突说明，不启动正式构图。
- 规则存在歧义：要求用户确认系统解析，不直接生效。
- 事实实体存在歧义：要求用户选择已有实体或创建新实体。
- 自动抽取违反规则：记录校验失败和原始输出，进入待审核，不写入可信检索范围。
- Schema 更新：旧事实继续保留原版本标识；是否重抽取由用户明确选择。

## 10. 数据模型建议

在现有知识库图谱事实模型之外增加：

- `knowledge_scene_profiles`：场景描述、业务对象、业务逻辑和版本。
- `knowledge_schema_suggestions`：自动发现的新类型、关系及证据。
- `knowledge_business_rules`：原始自然语言、结构化解析、状态和版本。
- `knowledge_user_facts`：用户原始输入、结构化事实、实体链接结果。
- `knowledge_graph_extraction_runs`：原始模型响应、解析结果、错误、模型和版本信息。

现有实体、关系和 Mention 表继续作为图谱事实源；Qdrant 继续作为可重建索引，不引入新的图数据库依赖。

## 11. 测试与验收

至少准备三类不同场景测试，避免系统只适配空气质量：

1. 工业企业噪声投诉与整改。
2. 环境政策、技术规范与适用对象。
3. 监测站点、设备、异常指标与维护工单。

验收内容：

- 无需用户编写 Schema JSON 即可完成建模。
- 缺少代表性文档时不能开始自动发现。
- 场景描述能明显改变抽取对象和关系。
- 用户业务规则能约束后续抽取。
- 用户事实经确认后立即成为 `confirmed`。
- 自动抽取事实保持 `candidate`，并具有精确证据。
- Schema 建议不会未经确认自动改变生产图谱。
- Agent 能区分事实、规则、用户声明和推理结论。
- 修改 Schema 或规则后可以追踪新旧抽取版本。

离线质量指标至少包括实体与关系 Precision/Recall、实体链接准确率、证据支持率、重复实体率、Schema 违规率和多跳问题正确率。

## 12. 实施范围分解

该设计应拆分为三个连续实施阶段：

1. 场景自动发现与业务化确认：代表性文档门槛、Scene Profile、Schema 编译和版本管理。
2. 规则与事实录入：自然语言规则解析、业务事实确认、实体链接及可信状态。
3. 抽取与检索升级：动态 Prompt、精确证据、两阶段抽取、图检索融合和评测闭环。

三个阶段共享数据契约，但分别制定实现计划和验收测试，以控制单次改造范围。
