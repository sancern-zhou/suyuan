# Suyuan 多客户多业务代码管理设计

## 背景

Suyuan 由同一团队维护，但需要部署到济源、许昌等不同客户，并按部署组合大气、噪声、招投标等业务模块。项目差异不仅包含配置，还覆盖前端功能、后端工具、数据抓取脚本、Skill 文档、知识库定义和定时任务。

目标是在保持公共底座统一演进的同时，做到：

- 一个部署可以组合多个业务模块；
- 公共更新可以自然到达所有适用项目；
- 客户特有功能不会污染其他项目；
- 客户项目验证过的能力可以明确地上升为共享能力；
- 每个部署能够独立选择升级时间并复现其构建结果。

## 决策

采用“模块化 Monorepo + 声明式部署清单”，不使用客户长期分支管理产品差异。

`main` 是所有公共底座、业务模块和客户定义的集成主线。短期功能分支用于开发和评审，合并后删除。部署时通过项目清单选择模块及能力，而不是从客户分支构建不同版本。

## 代码边界

目标结构如下，实际迁移应渐进完成，不要求一次移动全部现有代码：

```text
suyuan/
├── core/
│   ├── backend/
│   └── frontend/
├── modules/
│   ├── atmosphere/
│   │   ├── backend/
│   │   │   ├── tools/
│   │   │   ├── fetchers/
│   │   │   ├── skills/
│   │   │   └── scheduled_tasks/
│   │   ├── frontend/
│   │   └── knowledge/
│   ├── noise/
│   └── bidding/
├── projects/
│   ├── jiyuan/
│   │   ├── project.yaml
│   │   ├── backend/
│   │   ├── frontend/
│   │   └── knowledge/
│   └── xuchang/
├── backend/
├── frontend/
└── deploy/
```

各层职责如下：

- `core`：身份认证、会话、模型调用、资源管理、模块加载等不依赖客户和领域的能力。
- `modules/<domain>`：可被多个客户复用的完整业务能力，例如大气分析页面、工具、抓取器、定时任务和知识库定义。
- `projects/<customer>`：部署清单、客户品牌、本地数据源参数及确实无法复用的客户覆盖代码。
- `backend`、`frontend`：统一运行和构建入口，负责读取清单、发现模块并组装应用。

依赖方向必须保持为：

```text
project -> module -> core
```

`core` 不得导入业务模块或客户代码；业务模块不得导入客户代码。跨模块协作通过公共接口或事件完成，不能直接读取另一模块的内部实现。

## 部署清单

每个部署由版本控制内的 `projects/<project>/project.yaml` 描述。例如：

```yaml
schema_version: 1
project: jiyuan

modules:
  - atmosphere
  - noise

frontend:
  theme: jiyuan
  features:
    pollution_trace: true
    noise_map: true
    bidding: false

backend:
  tools:
    - air_quality_analysis
    - noise_source_analysis

knowledge:
  collections:
    - common_environment
    - jiyuan_local_regulations

scheduled_tasks:
  - atmosphere_hourly_fetch
  - noise_daily_report
```

清单使用固定 schema，并在 CI 和应用启动时校验。清单只保存非敏感声明；密码、令牌、数据库地址等由部署环境注入，并按清单中的逻辑名称引用。

## 模块注册与应用组装

每个模块提供稳定的 manifest 和注册入口，至少声明：

- 模块标识与兼容版本；
- 前端路由、菜单项和功能标识；
- 后端工具、API 路由和权限；
- 抓取器及其配置 schema；
- Skill 文档及适用工具；
- 知识库定义和导入配方；
- 定时任务、默认调度和所需依赖。

构建或启动流程为：

```text
选择 PROJECT
  -> 读取并校验 project.yaml
  -> 解析已启用模块
  -> 校验模块依赖、配置和名称冲突
  -> 生成前端模块注册表
  -> 生成后端模块注册表
  -> 构建并启动部署
```

前端功能隐藏必须与后端权限和注册状态一致。隐藏菜单不等于禁用能力；未启用模块的路由、工具和任务必须在后端不可调用。

## Git 工作流

日常开发从 `main` 创建短期分支，并按所有权范围命名：

```text
feat/core-resource-api
feat/atmosphere-trace
feat/jiyuan-noise-report
fix/xuchang-fetcher
```

提交应按可传播边界拆分：

```text
feat(atmosphere): add generic air-quality report generator
feat(jiyuan): configure local stations and report template
```

目录决定改动的传播范围：

- `core/**`：所有部署共享；
- `modules/atmosphere/**`：所有启用大气模块的部署共享；
- `projects/jiyuan/**`：仅济源部署使用。

项目能力上升为共享能力时，应通过重构提交把通用逻辑移入对应模块，客户参数仍留在项目层。代码评审需要分别确认通用接口和客户配置。`cherry-pick` 仅用于尚未合并主线的紧急补丁，不作为常规同步方式。

## 发布与回滚

代码统一在 `main` 集成，但客户部署版本独立记录。每次部署保存以下信息：

- Git commit SHA；
- 项目清单内容或摘要；
- 前后端构建产物版本；
- 数据库迁移版本；
- 知识库配方版本。

可使用项目作用域标签标记正式部署，例如 `jiyuan/v2026.07.1`、`xuchang/v2026.07.2`。标签表示部署快照，不创建新的长期代码线。回滚使用已验证的构建产物和对应清单，不依赖重新构建浮动依赖。

## 知识库管理

Git 中保存知识库的可复现定义，而非运行期状态：

- collection 定义和元数据 schema；
- 文档清单及内容版本标识；
- 清洗、切分、嵌入和导入规则；
- 许可允许且体积可控的种子文档；
- 初始化和迁移脚本。

向量索引、运行期上传文件、客户生产数据及访问密钥放在对象存储、数据库或独立数据卷中。部署流程根据配方执行幂等初始化，并记录输入文档和嵌入模型版本。

## 失败处理

- 未知模块、依赖缺失、重复工具名或非法清单使构建直接失败。
- 单个抓取器或定时任务初始化失败时，默认阻止该模块就绪；明确标记为可选的能力可以降级，但必须产生告警。
- 客户覆盖只能覆盖 manifest 明确允许的扩展点，禁止通过动态路径替换任意公共代码。
- 数据库迁移必须向前兼容当前发布窗口；不可逆迁移需要单独的部署和回滚方案。
- 知识库初始化失败不允许静默使用过期索引，应用应报告实际加载的知识库版本。

## 测试与质量门禁

测试分四层：

1. `core` 单元和集成测试，验证公共契约。
2. 每个业务模块的独立测试，使用最小宿主加载该模块。
3. 每个项目清单的组装测试，验证依赖、路由、工具、任务和知识库定义无冲突。
4. 受影响项目的构建及冒烟测试。

CI 根据变更路径计算影响范围：

- 修改 `core` 时测试全部项目；
- 修改某个模块时测试所有启用该模块的项目；
- 修改客户目录时只测试该客户及相关公共契约；
- 修改清单 schema 或模块加载器时测试所有清单组合。

正式前端仍只能从 `/home/xckj/suyuan/frontend` 执行 `npm run build:standalone`，产物仍为 `frontend/dist`。模块化改造不得产生第二套前端 bundle；项目选择应通过构建参数和生成的注册表进入现有唯一构建入口。

## 渐进迁移

迁移按以下顺序进行：

1. 建立项目清单 schema、校验器和模块注册协议，不移动现有业务代码。
2. 选择一个边界清晰的业务作为试点，建议从抓取器或定时任务较独立的模块开始。
3. 为济源建立首个项目清单，使现有默认行为在清单驱动下保持不变。
4. 抽取第二个业务模块，验证一个部署组合多个模块。
5. 建立许昌清单，验证客户配置和业务模块正交组合。
6. 逐步把散落的客户判断迁移到项目配置或受控扩展点。
7. 最后启用按影响范围执行的 CI 和项目发布标签。

迁移期间，旧入口可以由兼容适配器注册到新协议，但新功能必须进入正确的 `core`、`modules` 或 `projects` 边界，避免继续积累隐式客户判断。

## 非目标

- 当前不拆分为多个独立 Git 仓库或发布内部包。
- 不为客户维护永久分支。
- 不要求一次性重写现有前后端目录。
- 不把生产知识库数据、密钥或客户上传内容纳入 Git。
- 不在第一阶段引入复杂的远程插件市场或运行期下载安装机制。

## 成功标准

- 新增客户主要通过清单和客户配置完成，无需复制公共源码。
- 一个部署可以可靠组合两个以上业务模块。
- 公共修复只合并一次，并由影响范围测试覆盖所有适用项目。
- 客户功能可以通过明确提交上升为业务模块能力。
- 任一正式部署都能由 commit、项目清单和数据配方复现。
