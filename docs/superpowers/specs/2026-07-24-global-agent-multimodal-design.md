# 全模式统一 Qwen 多模态机制设计

## 背景

项目已具备基于百炼 Qwen 的原生多模态运行机制，但 Agent 运行时仍通过模式白名单决定是否启用该机制。当前白名单只覆盖 `social`、`ppt`、`chart` 和 `board`；其余外部业务模式、内部模式、缺省模式及未来新增模式仍可能选择文本模型、丢弃运行时图片附件，或不开放工具图片回传能力。

本次改造将所有 Agent 模式统一到同一套多模态机制，并让多模态能力需求优先于用户显式选择的 Flash/Pro 模型档位。

## 目标

- 所有前端业务模式和后端内部模式默认启用原生多模态。
- 缺省、未知和未来新增的 Agent 模式自动继承多模态能力。
- 多模态模型 Profile 的优先级高于 Flash/Pro 档位。
- 继续通过配置选择具体模型，首选现有 `LLM_MULTIMODAL_MODELS` 中的百炼 Qwen。
- 复用现有图片附件、历史消息、工具截图和文件读取机制，不引入第二套多模态实现。
- Qwen 调用失败后允许使用配置中的后续候选，包括非 Qwen 或纯文本候选。

## 非目标

- 不把脱离 Agent 运行时的后台摘要、分类、结构化提取等独立 LLM 调用全部强制切换为多模态。
- 不改变前端模式列表、会话隔离策略或附件上传协议。
- 不在业务代码中硬编码 Qwen 模型名称、密钥或服务地址。
- 不新增自动识别回退模型视觉能力的模型注册表。
- 不在回退时静默删除图片并伪装成完整的视觉分析结果。

## 方案选择

### 采用：全局能力默认开启

保留 `supports_native_multimodal()` 作为统一能力边界，但移除模式白名单语义，使所有 Agent 运行模式都返回支持。该入口继续统一控制：

- Auto 模型能力 Profile；
- 用户图片附件透传；
- 历史图片消息恢复；
- 工具生成图片和截图的后续轮次输入；
- `read_file(as_multimodal_attachment=true)` 工具能力。

该方案改动集中，且未来模式无需额外登记。

### 未采用：扩充已知模式白名单

该方案可以显式列出当前模式，但内部模式分散在多个模块，未来新增模式容易漏接，不符合“所有模式统一”的长期目标。

### 未采用：删除能力抽象并在各层无条件处理

该方案会让相同策略散落到 Agent、运行时、工具适配和模型服务中，增加重复判断及后续维护成本。

## 架构设计

### 1. 全局 Agent 多模态能力

`backend/app/agent/runtime/mode_capabilities.py` 继续提供单一能力判断入口。该入口对具体模式名称不做白名单过滤，包括：

- 外部模式：`assistant`、`ppt`、`expert`、`query`、`report`、`chart`、`board`、`ops`、`graph` 和 `social`；
- 内部模式：`custom`、`memory_consolidator`、`deliberation_*`、子 Agent 和定时任务传入的运行模式；
- `None`、空字符串、未知模式及未来新增模式。

这些情况均按支持原生多模态处理。调用方仍使用能力函数，不自行判断模式名称。

### 2. 模型选择优先级

每次 Agent 运行均选择 `multimodal` Auto Profile。模型选择优先级调整为：

1. Agent 的多模态能力 Profile；
2. 用户选择的 Flash/Pro 档位；
3. 普通默认模型和默认回退链。

当 Flash/Pro 上下文已经存在时，`multimodal` Profile 必须覆盖该档位，并从 `LLM_MULTIMODAL_MODELS` 构建本次请求的候选链。模型档位可以保留在请求和日志中，但不得将 Agent 请求切换到非多模态主链。

具体提供商和模型仍完全由配置决定。当前配置首选 `bailian/qwen3.8-max-preview`，运行时代码只依赖 `multimodal` 能力名称。

### 3. 消息与附件数据流

数据流保持现有实现：

1. 路由接收用户文本、附件和已选会话资源。
2. ReAct Agent 将所有模式的有效图片附件交给运行时。
3. 运行时将有图片的用户消息构造成 Anthropic 兼容的文本与图片内容块；无图片时仍发送普通文本。
4. 会话持久化保存紧凑的附件信息，恢复会话时重建需要的多模态上下文。
5. 工具返回 `multimodal_attachment` 时，运行时捕获该图片并在下一次模型调用中提供。
6. 所有模式的 `read_file` 工具 schema 暴露显式的 `as_multimodal_attachment` 参数。

本次不改变附件格式、存储结构、大小限制或 URL/base64 转换规则。

### 4. 回退与错误处理

Qwen 或其他首选候选失败时，继续按 `LLM_MULTIMODAL_MODELS` 的配置顺序尝试后续候选。系统不因为候选来自非 Qwen 提供商或可能是纯文本模型而预先拒绝它。

回退请求保留原始消息语义和图片内容，不主动删除图片。若候选不接受当前内容格式，则沿用现有失败分类、冷却和继续回退机制；所有候选均失败时返回现有的聚合错误。这样允许运维人员配置降级候选，同时避免系统静默声称已分析实际未提供给模型的图片。

## 兼容性

- 现有 `social`、`chart`、`ppt` 和 `board` 行为保持不变。
- 原先文本模式只改变模型能力链和图片可用性，其 prompt、工具集合及会话模式不变。
- 无图片的文本请求不会生成空图片块，多模态模型按普通文本处理。
- 前端仍可发送 Flash/Pro，但对 Agent 请求而言它们不能覆盖多模态能力要求。
- `LLM_MULTIMODAL_MODELS` 未配置或配置无有效候选时，沿用明确的配置警告或错误，不静默切回默认文本链。

## 测试设计

### 能力边界

- 已知外部模式均支持原生多模态。
- `custom`、`memory_consolidator`、各 `deliberation_*` 等内部模式均支持。
- `None`、空字符串和任意未知模式均支持，证明未来模式默认继承。

### Agent 路由

- `assistant`、一个内部模式和未知模式均选择 `multimodal` Profile。
- 上述模式的图片附件均传入 ReAct 运行时。
- 无附件请求仍采用普通文本消息形态。

### 模型优先级

- 在 Flash 上下文中应用 `multimodal` Profile 后，实际主模型来自 `LLM_MULTIMODAL_MODELS`。
- 在 Pro 上下文中执行相同验证。
- 多模态候选失败时继续尝试配置的后续候选。

### 运行时回归

- 保留并运行社交、图表、PPT、画板的原生附件测试。
- 验证历史图片恢复、工具图片捕获、显式图片与旧画板上下文并存等现有场景。
- 验证所有模式的 `read_file` schema 均暴露多模态附件参数。

## 验收标准

- 不再存在决定哪些 Agent 模式可以使用原生多模态的模式白名单。
- 所有 Agent 模式及内部运行模式均选择 `multimodal` Profile。
- Flash/Pro 不再覆盖 Agent 的多模态模型链。
- 任意模式均可把用户图片和工具图片发送到运行时模型调用。
- 无附件的普通文本对话不受消息格式副作用影响。
- 配置文档不再声称多模态链只用于社交或图表模式。
- 相关单元测试和现有多模态回归测试在 `backend_py311` Conda 环境中通过。
