# 运维工单视觉证据归档与报告插图设计

## 目标

运维工单审核完成后，将已确认视觉问题、疑似问题和资料不足待人工复核项关联的全部照片保存到本次审核输出目录。生成报告时，每个问题最多展示 3 张照片，证据包仍保留全部原图，便于用户离线确认。

## 范围

本次覆盖以下视觉证据：

- 已进入 `final_issue_list` 的视觉问题；
- 带有 `needs_visual_review` 的视觉识别候选；
- `ATTACHMENT_MULTIPOINT_GRADIENT_REVIEW` 产生的疑似问题和资料不足项；
- `ATTACHMENT_FLOW_VISUAL_ERROR` 等视觉识别失败项中仍可定位的原始照片。

本次不改变规则启停配置、视觉模型提示词、问题晋级口径或 `final_issue_list` 的业务定义，也不把待复核项当作已确认问题。

## 总体方案

采用“审核阶段统一归档、报告阶段消费本地证据”的结构。

规则引擎完成视觉任务后、构建最终问题清单前，调用独立的视觉证据归档器。归档器扫描审核记录中的视觉问题，解析单图来源和 `reviewed_images` 多图来源，将所有可访问图片复制或下载到本次审核目录，并把结构化的 `evidence_images` 写回问题证据。

报告写入器继续以 `final_issue_list` 作为确认问题清单的唯一来源，同时从当前审核结果读取未晋级的视觉待复核项。报告不会从历史文件或目录搜索问题。

## 组件与职责

### 视觉证据归档器

新增 `backend/app/services/ops_audit/visual_evidence.py`，职责为：

- 从视觉问题证据提取 `source`、`attachment_local_path`、`attachment_url`、`attachment_original_path` 和 `reviewed_images`；
- 按规范化来源去重，但保留一张图片与多个问题之间的关联；
- 本地文件使用复制，远程 URL 或 `/WebFiles/...` 使用现有附件根目录/附件服务配置解析；
- 将文件保存到 `visual_evidence/<工单号>/<规则ID>/`；
- 使用安全文件名和来源摘要避免重名覆盖；
- 生成 `visual_evidence/manifest.json`；
- 将每项归档结果写回问题证据的 `evidence_images`。

`evidence_images` 每项包含：原始来源、原文件名、本地绝对路径、相对审核目录路径、状态和失败原因。下载失败不会中断整批审核。

### 规则引擎集成

`run_rule_engine` 在所有视觉任务完成并得到完整 `audit` 后执行归档。归档发生在 `build_final_issue_list` 之前，因此确认问题和待复核项共享同一份证据元数据。

归档清单路径通过规则引擎结果返回，便于后续报告工具或人工检查使用。

### 最终问题清单

`final_issue_list` 保持确认问题清单语义不变。对于已确认视觉问题，结构化条目透传 `evidence_images`，但不会因为图片下载失败而移除已经通过当前规则口径确认的问题。

待人工复核项不会写入 `final_issue_list.items`，而是保留在当前审核结果中，由报告写入器单独展示。

### 报告写入器

报告包含两个明确区分的区域：

1. 确认问题：数据来源仅为当前运行的 `final_issue_list.items`；
2. 视觉待人工复核：来源为当前审核结果中未进入确认问题清单的视觉候选。

每个条目最多插入 3 张成功归档的照片。照片使用相对报告文件的 Markdown 路径，并展示文件名或简短图注。关联照片超过 3 张时，报告注明“报告展示 3 张，证据包共保存 N 张”。

如果没有成功归档的照片但存在失败记录，报告显示“证据图片获取失败”及简短原因，不引用不可用文件。

## 数据流

1. 数据集抽取包含附件记录及来源路径。
2. 视觉规则执行并产生问题或待复核证据。
3. 归档器收集所有视觉问题的图片来源。
4. 归档器复制/下载全部图片，写入 manifest，并回填 `evidence_images`。
5. 规则引擎构建 `final_issue_list` 并持久化审核产物。
6. 报告写入器输出确认问题及视觉待复核项，每项引用最多 3 张本地图片。
7. 报告包工具复制报告所引用的图片并校验引用完整性。

## 错误处理

- 单张图片复制或下载失败只记录失败状态，不中断其他图片、其他问题或审核结果生成；
- 无附件根目录且无附件服务地址时，manifest 明确记录无法解析来源；
- 非图片扩展名不作为报告照片归档；
- 重复来源只保存一份文件；
- 报告只引用实际存在的成功归档文件；
- 图片路径计算失败时显示证据缺失说明，不生成越出报告/审核目录的相对引用。

## 测试策略

采用测试驱动开发，覆盖：

- 本地图片复制及 manifest 生成；
- `/WebFiles/...` 通过附件根目录解析；
- 远程图片下载；
- 多问题重复来源去重；
- 多点曲线 `reviewed_images` 全量归档；
- 下载失败降级且不抛出整批异常；
- `final_issue_list` 透传 `evidence_images`；
- 报告展示确认视觉问题；
- 报告展示未晋级的疑似问题/资料不足项；
- 单项证据包保留全部图片、报告最多引用 3 张；
- 报告对失败图片给出文字提示。

## 验收标准

- 任一视觉问题或待复核项关联的可访问照片全部存在于本次审核的 `visual_evidence` 目录；
- `manifest.json` 可从工单号和规则 ID 定位原始来源、本地文件及归档状态；
- 确认问题清单仍只包含当前口径下的确认问题；
- 报告明确区分确认问题和视觉待人工复核；
- 每项报告最多展示 3 张图片，证据包不丢弃第 4 张及以后图片；
- 缺图不会导致审核或报告生成失败；
- 相关自动化测试在项目指定的 Python 3.11 Conda 环境中通过。
