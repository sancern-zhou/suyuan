# 运城市事件任务改用助手模式设计

## 目标

运城市告警溯源事件任务直接使用助手模式执行分析，不再使用社交模式作为任务协调器。Agent 只负责生成报告与广播产物，事件任务服务继续负责向后台配置的微信用户广播，并把广播正文和附件写入各用户的社交主会话。

## 变更范围

1. 将 `task_yuncheng_alert_tracing_event` 的 `execution_mode` 从 `social` 改为 `assistant`。
2. 更新任务步骤提示词：助手直接读取并执行 `backend/docs/skills/yuncheng_alert_tracing_skill.md`，不再调用助手模式子 Agent。
3. 更新运城市告警溯源 Skill，删除“社交模式调用助手、助手返回社交模式、社交模式推送”的职责描述。
4. 保留助手同步调用气象和常规分析 `expert` 子 Agent 的流程。
5. 助手最终直接返回事件任务服务可解析的广播封装：

```json
{
  "success": true,
  "broadcast": {
    "message": "500字以内微信摘要",
    "media": ["/绝对路径/report.docx"]
  }
}
```

失败时返回：

```json
{
  "success": false,
  "error": "具体失败原因"
}
```

## 不变项

- 事件类型仍为 `yuncheng.alert.created`。
- 城市过滤条件仍为“运城市”。
- 任务仍为启用状态。
- 微信目标用户、多选能力和广播开关保持不变。
- Agent 不调用微信、广播或通知工具。
- 广播服务继续负责发送正文、Word 附件和按用户隔离持久化对话上下文。

## 执行数据流

1. 运城盯守服务发布真实告警事件。
2. 事件任务服务匹配并认领事件。
3. 助手模式 Agent 收到任务提示词和可信事件上下文。
4. 助手读取 Skill，校验资产，同步调用两个专家子 Agent，生成并验收 `report.qmd` 和 `report.docx`。
5. 助手返回广播封装，不直接投递。
6. 事件任务服务解析结果并向配置的微信用户广播。
7. 广播正文和附件分别写入每个接收用户的社交主会话，供后续连续对话使用。

## 验证标准

- 存储中的任务执行模式为 `assistant`。
- 任务提示词不再要求调用助手模式子 Agent或使用社交模式协调。
- Skill 不再把社交模式作为上游或下游执行者。
- Skill 的成功输出符合事件广播封装格式，并使用 Word 文件绝对路径作为唯一媒体附件。
- 任务仍保留原事件条件、接收用户和广播配置。
- 任务列表 API 返回更新后的执行模式和提示词。
