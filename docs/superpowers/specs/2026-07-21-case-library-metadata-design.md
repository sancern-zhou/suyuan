# 案例库列表元数据恢复设计

## 背景

案例标记保存在 Web 会话表 `sessions.metadata` 的 `is_case` 和
`case_marked_at` 字段中。统一会话鉴权改造后，`GET /api/sessions` 只使用
`conversation_catalog` 生成列表项。目录记录不包含案例字段，导致前端案例库按
`metadata.is_case === true` 筛选时得到空列表。

## 目标

- 已标记的可见 Web 会话在列表响应中保留案例元数据。
- 普通会话不会进入案例库。
- Knowledge QA、社交等非 Web 会话继续使用目录数据，不改变其访问控制和展示行为。
- 不通过前端逐条加载会话详情，避免 N+1 请求。

## 设计

会话列表仍以 `conversation_catalog` 作为可见性、所有权、来源、标题和排序的权威来源。
取得当前页目录记录后，提取其中 Web 来源的会话 ID，通过会话仓储一次批量查询对应的
轻量摘要元数据。响应组装时仅把列表功能需要的 `mode`、`is_case`、
`case_marked_at`、`source` 和 `channel` 合并进 Web 会话的 `metadata`。

目录字段继续覆盖身份和来源字段；会话元数据不能改变目录决定的所有权、只读状态或
来源。找不到对应 `sessions` 记录时返回目录原有数据，不让单条旧数据破坏整个列表。

前端继续严格使用 `metadata.is_case === true` 判断案例，不增加猜测规则或详情请求。

## 测试

先增加会话列表 API 回归测试并确认其在现有实现上失败，覆盖：

1. 可见 Web 案例在列表响应中带有 `is_case` 和 `case_marked_at`。
2. Web 普通会话保持非案例状态。
3. 非 Web 会话不触发 Web 会话元数据读取，目录字段保持不变。
4. 批量读取缺失记录时列表接口仍正常响应。

完成实现后运行会话路由、会话仓储相关后端测试，以及前端案例筛选测试。

## 非目标

- 不修改案例标记的存储位置。
- 不新增数据库迁移或向 `conversation_catalog` 双写案例状态。
- 不在本次改动中处理 200 条列表上限或案例专用分页。
